事主原文：

## 病灶定位（探針實證）

`CandidatePool4AppKit` 有兩個**行程級**的靜態範本 cell（`static var shitCell`／`static var blankCell`，用於量測最小 cell 尺寸與填充行）；`CandidateCellData4AppKit.init` 會依當下的 `unifiedSize`（＝偏好 `candidateListTextSize`）把 `textDimension` 算好**存進 struct**，此後 `updateMetrics` 只寫 `visualDimension`、不回寫 `textDimension`。於是範本 cell 一旦在字級 A 之下被初次存取，其 `textDimension` 便在該行程內定影於 A。

`lineStep`（「單行高度（horizontal matrix）」）原本寫成 `cellTextHeight + 2 * padding`，而 `cellTextHeight` 是 `let cellTextHeight = CandidatePool4AppKit.shitCell.textDimension.height`——**建池時的快照**。`lineStep` 只被橫向排版的捲動模型消費：

- `pageCandidateSize` 之橫向分支 → `lineStep × maxLinesPerPage`（＝捲動視口高度，即使用者所見的視窗最大高度）
- `maxScrollOffset` 之橫向分支 → `candidateOnlySize.height − lineStep × maxLinesPerPage`
- `scrollerThumbRatio`、`scrollByLines`、`snapScrollOffset`、`scrollToMakeLineVisible`

**橫向排版為何以快照式算式表達視口高度**（此即故障只落在此處之結構性原因）：

- TDK（非捲動）分支之視窗高度取自 `metrics.fittingSize`——由 `layoutCells` 逐一量測排出的 cell 高度相加，故必然跟隨字級。
- 縱向排版之捲動視口量的是 `candidateLines[page]` 各列**實測**寬度與高度，故亦必然跟隨字級。
- 唯獨橫向排版的捲動視口以 `lineStep` 這個**合成值**表達（設計意圖正確：視口恆為 `maxLinesPerPage` 行高，末頁不足行數時視窗不縮水），而該合成值取自定影快照 ⇒ 字級一變即與真實版面脫節。

**探針實證（35 個候選、`lines: 4`、`isExpanded: true`、`layout: .horizontal`；先在字級 16 之下定影範本 cell，再改字級）**：

- 字級 16：`unifiedTextHeight` 19.0、`lineStep` 23.0、`pageCandidateSize.height` 92.0、實測 cell 高 23.0、第二行原點 y 25.0 ✓ 一致。
- 字級 40（術前）：`unifiedTextHeight` 48.0（**已即時更新**）、`lineStep` **23.0（未動）**、`pageCandidateSize.height` **92.0（未動）**，而實測 cell 高 **42.0**、第二行原點 y **44.0**、`candidateOnlySize.height` **312.0** ⇒ 視口高度只有內容真實高度的三分之一弱，且 `maxScrollOffset` 反被算成 220.0（應為 104.0）——捲動範圍連帶失真。
- 字級 40（術後）：`lineStep` 52.0、`pageCandidateSize.height` 208.0、`maxScrollOffset` 104.0 ✓ 與實測行距 52.0 逐位吻合。

**GSI 視圖層之同一量測（`VwrCandidateGSI4AppKit.fittingSize`，`rendersInScrollMode = true`）**：字級 16 ⇒ `(350.0, 115.0)`；字級 40 術前 ⇒ `(746.0, 137.0)`（高度只多 22 行點——那 22 點是底部欄位隨字級長出來的部分，視口本身紋絲未動）；字級 40 術後 ⇒ `(746.0, **253.0**)`。此即事主所述「最大高度並沒有隨著 candidate font size 而遞增」之直接再現。

## 落點

`CandidatePool4AppKit.swift`：把 `cellTextHeight` 由 stored 快照改為計算屬性，即時讀取全域通用的字級換算（與 `CandidateCellData4AppKit.updateMetrics` 內 `cellDimension.height = unifiedTextHeight + 2 * padding` 同源），並在原地註明「不得自範本 cell 取值」之理由。

```swift
    /// 候選字 cell 的文字高度（跟隨偏好中的候選字字級即時浮動）。
    /// 不得自範本 cell（`shitCell`）取值：範本 cell 的 `textDimension` 只在該靜態成員初次
    /// 初始化時定影一次，行程存活期間更動字級不會更新它，一旦快照化即會讓行步進（連帶
    /// 捲動模式的視口高度）停在舊字級。
    var cellTextHeight: CGFloat { CandidateCellData4AppKit.unifiedTextHeight }
```

`lineStep`（`cellTextHeight + 2 * padding`）與其餘五個消費端一行未動——修在單一真源上，五處同步受惠。刻意**不**改 `pageCandidateSize` 之算式：`lineStep × maxLinesPerPage` 表達「視口恆為整頁高」這一設計意圖（末頁不足行數時不縮水）本身正確，病灶只在取值來源。

## 要解決的問題

事主原文：

> 1. GSI 捲動模式不繪製頂部 pane（unfinished reading）：溢成捲動模式時該 pane 靜默消失。
> 2. 候選字的 candidate key label 的顯示區域得設法保持成一個正方形的面積。不然的話，Candidate Font Size 越大，這 Candidate Key Label 越是顯得窄得誇張。

## 病灶

### 一、GSI 捲動模式之頂部 pane

非捲動模式（TDK 與 GSI 之普通模式）之 pane 走 `CandidatePool4AppKit.updateMetrics()`：該函式量出 pane 尺寸 `dimensionUnfinishedReading`、算出 `topPaneShift = 該高 + padding`、把**全體 cell 之 visualOrigin.y 下移**並把 `fittingSize.height` 加高，`metrics.unfinishedReading` 則記下 pane 之矩形。**三件事在捲動模式全都不成立**：

1. `VwrCandidateGSI4AppKit.drawScrollMode(...)` 從未繪製 `attributedDescriptionUnfinishedReading`（該函式只畫候選格、scroller 與底部欄位）。
2. 捲動模式之視窗高度走 `fittingSize` 之另一分支（`pad + page.height + extraHeight + bottom.height`），未含 pane。
3. 捲動模式之候選區幾何——`clipOrigin`、`drawOffsetX/Y`、`scrollerTrackRect`、`drawBottomFields(topY:)`、`findCell` 之命中點與視埠矩形——全以 `originDelta` 為基準，未計 pane。

且捲動模式之 cell 幾何來自 `computeCandidateOnlySize()`（自 `(0,0)` 起排、不經 `updateMetrics` 之 `topPaneShift`），故**連「cell 被下移」這個副作用都不會發生**：pane 就這樣無聲無息地消失。

### 二、選字鍵標籤之顯示區域

標籤以 `selectionKeyFont()`（monospaced 系統字、字級 `fontSizeKey = max(ceil(0.6 × 候選字字級), 11)`）繪製，其**呈現盒**＝字寬 × 行高（數字之 advance 約 0.6 em、行高約 1.17 em）——即盒之兩邊比約 **1 : 1.95**（窄高）。而顯示區域之橫向留白原為 `phraseDrawXOffset = ceil(size * 0.6)`（＝標籤字級、亦即其字寬），故**顯示區域恰好只夠容納「字寬」，比標籤自身之行高窄上一倍**：字級越大，這個「窄得誇張」的比例越顯眼。

實測（本機，非高亮格）：字級 12 ⇒ 盒 8.0 寬 × 13.0 高；24 ⇒ 15.0 × 17.7；40 ⇒ 24.0 × 28.3；96 ⇒ 58.0 × 68.3；196 ⇒ 118 × 139。

**耦帶發現（本 phase 一併收緊）**：既有之 cell 寬度算式（`textDimension.width + 4 × padding`）在**極大字級**下本就容不下「標籤 ＋ 候選字詞」——以字級 196 為例，候選字詞之起點（`2 × padding + 118`）＋字詞寬（測得 184.9）＝ 306.9 > 該格寬 297，即術前即已超格約 10 點（該算式之「餘裕」約 14 點，係按 1 字型紋理而非實測 advance 估的）。

## 落點

### 一、GSI 捲動模式之頂部 pane（`VwrCandidateGSI4AppKit.swift`）

新增兩個成員，把 pane 之幾何收攏成單一真源：

```swift
  private var topPaneDimension: CGSize {   // 空字串 ⇒ .zero（pane 隱藏）
    let strPane = thePool.attributedDescriptionUnfinishedReading
    guard rendersInScrollMode, !strPane.string.isEmpty else { return .zero }
    let rawDim = strPane.getBoundingDimension(forceFallback: true)
    return CGSize(width: ceil(rawDim.width), height: ceil(rawDim.height))
  }

  private var topPaneShift: CGFloat {      // pane 高 + padding；0 ⇒ 無 pane
    let dimension = topPaneDimension
    guard dimension.height > 0 else { return 0 }
    return dimension.height + thePool.padding
  }
```

六處幾何一併以 `topPaneShift` 下移：`fittingSize`（高＋shift；寬納入 pane 寬）、`drawScrollMode` 之 `clipOrigin` 與 `drawOffsetY`、`scrollerTrackRect` 之 y、`drawBottomFields(topY:)`、`findCell` 之命中點（`clickPoint.y -= topPaneShift`）與其視埠矩形（連同 cell 之 view 座標推算）。**軌道高度須與 pane 無關**（＝候選區高 − 上緣圓角留白）：軌道之頂端隨 pane 下移、底端仍貼齊候選區下緣——首版誤將高度亦減去 shift，令軌道短掉一個 paneShift（直立軌道；見〈驗證〉之複核記錄）。pane 本身繪於 `(originDelta, originDelta)`（與 `updateMetrics` 之 `rectUnfinishedReading` 同座標）——**不隨捲動移動**。另：clip path 之快取鍵補上 `lastClipOrigin`（pane 之出現／消失會平移裁切矩形，只比對尺寸會取到過期路徑）。

### 二、選字鍵標籤之正方形顯示區域（`CandidateCellData4AppKit.swift` ＋ 兩視圖）

```swift
    /// 選字鍵標籤之顯示區域：正方形，邊長取其自身之行高。
    var keyLabelBoxSide: CGFloat {
      let keyFont = selectionKeyFont()
      return ceil(keyFont.ascender + abs(keyFont.descender) + keyFont.leading)
    }
```

`updateMetrics` 內：`phraseDrawXOffset = keyLabelBoxSide`（候選字詞自正方形右緣起排）、`headerDrawXOffset = ceil((keyLabelBoxSide - 標籤字寬) / 2)`（標籤水平居中於其盒內）；並新增「標籤盒 ＋ 候選字詞」之硬約束：

```swift
      let keyAndPhraseWidth = keyLabelBoxSide
        + makeAttributedStringPhrase(isMatrix: false).size().width
      cellDimension.width = max(cellDimension.width, keyAndPhraseWidth + 2 * padding)
```

四處繪製點（TDK 1 處、GSI 3 處：捲動模式兩分支與普通模式）改用 `visualOrigin.x + 2 * padding + cell.headerDrawXOffset`；TDK 之候選字詞偏移由行內算式 `ceil(size * 0.6)` 改讀 `cell.phraseDrawXOffset`（與 GSI 一致）。

### 補記（2026-09-19）：標籤之墨跡光學居中（事主複驗回報之追加修正）

事主回報原文：

> 空間倒是騰出來了，但這個 candidate key text glyph 的位置看上去卻是在這個空間的 center-trailing 位置對齊的。換言之，center-leading 過大、center-trailing 過小。我在懷疑是不是需要從 NSAttributedString 組裝的角度干涉這個：candidate key text 左側的 space 的 fontsize 變小一些、candidate key text 右側的 space 的 fontsize 變大一些。

**量測（先確認現象，再動手）**：以離屏渲染掃描非高亮格之標籤墨跡，量其於正方形區域內之左右留白：

| 字級 | 區域邊長 | 左留白 | 右留白 | 差（正＝偏右） |
|---|---|---|---|---|
| 24 | 18.0 | 5.5 | 4.5 | **+1.0** |
| 40 | 29.0 | 9.5 | 7.5 | **+2.0** |
| 96 | 69.0 | 20.5 | 20.0 | +0.5 |

Tekkon 需要一個 API 來檢證任何 StringProtocol 對象「是否是按照正確順序打出來了一個 plausible 的注音/拼音讀音」。

### 程式碼變更

**`vChewing-LibVanguard/Sources/Tekkon/Tekkon_SyllableComposer.swift`**（`git diff --stat` 實測 **＋82 行**，內含 doc comment）：

- 新增 `public func isSequentiallyTypedRawKeyOrder(_ input: some StringProtocol, suffixOnly: Bool = false) -> Bool`，置於既有之 `isPronounceable` 一帶之後（`grep -n` 實測方法宣告於第 494 行；`git diff -U0` 之新增區塊起於 472 行、長 82 行）。
- **語意（五條件）**：以當前注音排列逐字元重播進一份影子注拼槽——①每字元須為該排列之合法按鍵且被引擎接受；②重播後須 `isPronounceable`；③最終仍填著之各槽，其「**最終值首度出現之鍵序**」須隨 聲→介→韻→調 單調不減；④重播期間若曾鍵入聲調，最終不得失落該聲調；⑤**於靜態注音排列、且非 `suffixOnly` 時，不得以另一鍵改寫既有之槽值**（即不接受「按錯再按對」之覆寫修正）。
- **手法**：`var shadow = self` ＋ `shadow.clear()` ＋ `shadow.enforceCSVTOrdering = false`（槽序由本函式自行觀測，故不啟用引擎自帶之 CSVT 順序強制），逐 scalar 先 `inputValidityCheck(charStr:)`、再 `receiveKey(fromScalar:)`；以 `[[String: Int]]`（四槽各一張）記「該槽之值 → 該值首度出現之鍵序」，並以 `previousValues` 過濾「值未變」之迭代；另以 `lastWritingKeyBySlot` 記各槽現值之**寫入者（鍵面字元）**，供條件五判定「是否以另一鍵改寫」；收尾以 `latestFirstSeen` 對四槽之**最終值**做單調檢定，另以 `toneEverTyped` 鎖「曾鍵入之聲調不得失落」。整段只寫入 `shadow`、不觸自身（呼叫不改自身已由測項鎖定）。

**病灶一：動態注音排列在混打下失效。** 原碼以「**鍵數 == 佔用槽數**」作「整段為單一音節」之代理量（`hasNoDestructiveOverwrite` 與 `bufferIsSingleSyllablePhonetic` 之末行），該等式**預設一鍵一槽**；動態排列之合法編碼本即跨鍵改寫槽值（大千26 之 `qquu`＝ㄅㄚ 為 **4 鍵 2 槽**），故該式對動態排列恆不成立。原碼對此之因應是**兩處區域豁免**——`case .ofDachen26: 6 // 這是酷音大千26鍵的顯著缺點`（`maxSingleSyllableKeyCount`，僅放寬上限）與兩道 `guard handler.composer.parser != .ofDachen26 else { return false }`（直接把檢查整條停用）。豁免本身即是病灶之證：停用之後，大千26 使用者打純注音（`qquu`）不但沒被吸收、反而**整串滯留為 ASCII 並於 Space 時被當英文遞交**。**手法**：改以 `handler.composer.isSequentiallyTypedRawKeyOrder(fullInput)` 為動態排列之判準——該 API 之條件五對動態排列本不生效、條件三又只以「最終值首見鍵序」為準（正為動態排列之合法多寫編碼而設；Phase 233 曾以五個動態排列、7337 筆語料於 `suffixOnly: true` 下逐筆檢證零誤殺）。兩道豁免一併移除。

**病灶二：短英文 token 之亂序判定缺位。** `shouldPreferASCIIWordPath` 原以「非前進式槽消耗」之**計數**為英文證據，並內建 `count >= 3` 護欄，故**兩字母之純英文字母緩衝永遠不會走 ASCII 偏好路徑**；於是 `ls` 這類「槽序上不可能這樣打」的 token 被 `bufferIsSingleSyllablePhonetic` 收為單一音節（`l`＝ㄠ 佔韻母槽、`s`＝ㄋ 佔聲母槽；引擎層因 CSVT 未強制而容忍，`isPronounceable` 又只看「三槽有無內容」）。**手法**：於該函式新增**第二項證據**——`isNotSequentiallyTypedReading(_:)`（`!isSequentiallyTypedRawKeyOrder(text)`，僅對「全為 ASCII 英文字母且長度 ≥ 2」者有定義）。兩項證據以 OR 結合，任一成立即偏好 ASCII。

**證據二之適用範圍一併收窄至靜態排列**：動態排列之合法編碼本即跨鍵改寫槽值，計數無意義（`qquu` 之計數為 2，若不放行則會反過來阻斷病灶一之修正）。故該計數僅於 `!parser.isDynamic && !isPinyinMode` 時計算。

### 術中發現：「冗餘鍵」在混打語境下不可放行（關鍵，且與 Phase 233 PostReport 之建議相左）

PostReport §8 曾建議「**替換**（第一階）／收斂（第二階）」條件五 ↔ 長度代理量，並在 §3.1 指出現行七處近似之收斂價值。實作後**測項 `test_IH400_MixedAlnumKanjiInputTest_Izanami`（前綴 `ai`）當場紅 4 筆**（ㄛˊ 之 `aii6`、ㄨˇ／ㄨˊ／ㄨˋ 之 `aij3`／`aij6`／`aij4`），症狀為「`ai` 前綴未被遞交、整段 `ㄇㄛˊ` 被當成單一讀音「模」」。

**根因**：`aii6` 之鍵序為 `a`(ㄇ) `i`(ㄛ) `i`(ㄛ，**同值重寫**) `6`(ˊ)——其**冗餘鍵**（第 3 鍵未佔新槽）在 P233 之條件五下**不構成違規**（「同值之重寫不留下可觀測之變化、亦不影響判定」，此為該 API 之明定界線、且為動態排列所必需），故 P233 判其為合格讀音；然在**混打語境**下，該冗餘鍵恰恰是「ASCII 前綴 ＋ 注音後綴」之分界證據（此即使用者打出 `ai`＋`i6` 而非 `ai6` 的原因），放行即令切分消失。

**處置**：**靜態注音排列維持「鍵數 == 佔用槽數」**（該式即「無冗餘鍵」，比引擎層判準略嚴——另含同鍵之重寫），僅**動態排列**改委由引擎層判準。此一分工同時滿足三項約束：動態排列之合法多寫編碼得放行、靜態排列之冗餘鍵分界得以保留、兩者共用同一份權威（`isSequentiallyTypedRawKeyOrder` 之條件三／五及其 `isDynamic` 分流）。**教訓**：`isSequentiallyTypedRawKeyOrder` 回答的是「這是否為一個打得出來的讀音」；混打所要問的是「這是否為**這一整段**讀音（nothing else）」——兩者對「同值重寫」之寬容度不同，不可直接互換。

### 三、閂滯行為（本次手術之核心）

**上鎖（進入閂滯）**：於 `Typewriter_MixedAlphanumerical.handle(_:)` 算出 `fullInput` 之後，若 `isLatchedAlnumStateEnabled`（兩開關皆開）且 `isNotSequentiallyTypedReading(fullInput)` 為真，即以 `commitLatchedAlnum(_:session:)` 即刻遞交整段並上鎖。**上鎖點由事主指定為 `isNotSequentiallyTypedReading == true`**；「覆寫修正」之優先級低於英文判定，係事主明示之取捨。

**閂滯態之按鍵處置**：`handle(_:)` 之**最前端**（在波浪符號鍵、Shift+Space、Space、中文標點查詢之前）加一道分支：以 `resolveVisibleInputText(_:)` 解析可見文字，若為單一可列印 ASCII（`0x20...0x7E`）即即刻遞交並回 `true`；否則回 `nil` 交還既有流程（故 Option+字母之非 ASCII 替換字符仍落到既有之 `resolveLiteralASCIIMainAreaText` 路徑、遞交其基底 ASCII）。此即「標點規則發生在中文標點查詢之前」之落實——`matchesCJKPunctuation` 在閂滯態下**根本不會被求值**，其 `return nil` 陷阱由構造上消除；另於該計算式加一項 `!isLatchedToAlnum` 之前提作**防重構**（兩層；主機制為次序、次層為自衛）。

**Space 之遞交路徑（實作時發現之分派缺口）**：`InputHandler_TriageInput` 之 Space 分支原以 `!mixedAlphanumericalBuffer.isEmpty` 為前提，而閂滯態之緩衝**恆空** ⇒ Space 會繞道至一般組字區送字邏輯、而非即刻遞交半形空格。已將該前提放寬為 `!mixedAlphanumericalBuffer.isEmpty || mixedAlnumConfig.isLatchedToAlnum`。

**四個解除鍵**（皆置於各函式之 `.ofInputting` 護欄**之前**——閂滯態之 state 恆為 `.ofEmpty`，否則根本進不到）：

|---|---|---|---|
| Enter | `handleEnter(input:readingOnly:associatesData:)` | **不攔截**（回 `false`）——閂滯時緩衝恆空、無物可遞交，攔截會令使用者在終端機情境下喫不到換行 | 帶 StatusUI 提示 |
| BkSp | `handleBackSpace(input:)` | **攔截** | 帶 StatusUI 提示 |
| Option+BkSp | 同上（同一分支內判別修飾鍵） | **不攔截** | 帶 StatusUI 提示 |

> 「提示」一欄之載體為 StatusUI 一過性提示（Wave 10 定稿；不經 `state`）——見 §十·一。

**靜默解除**（不發提示）：

**（仍待事主裁定）**
4. **`InputHandler.clear()` 是否改為帶參數之函式、以參數決定 `isLatchedToAlnum` 是否受影響**——本文**建議不採**，理由見下：
   - `clear()` 之呼叫面廣（`switchState(.ofAbortion/.ofCommitting/.ofEmpty)` 之共同分支為其**每鍵**必經之路，另有 `refreshState()`／`handleDelete()`／`handleEsc()` ×2 等直接呼叫）。加參數即意味著**每個呼叫端都要為閂滯語意表態**，而其中唯一正確的值（熱路徑）就是「不動閂滯」——該參數在熱路徑上屬死重。
   - 現行設計將決策**留在 config 之兩個具名粒度**（`resetContent()`／`resetAll()`），並將解除收斂到**唯一具名方法** `releaseLatchedAlnumState(announce:)`（全倉共六處呼叫：四個解除鍵 ＋ 兩處靜默會話邊界）。具名方法可 grep、可審計；布林參數則否。

   - **若仍欲加厚防護**，本文建議改採**更強之機制**而非參數：令 `MixedAlnumConfig.isLatchedToAlnum` 成為 `private(set)`，並只提供 `latchAlnum()`／`releaseAlnum()` 兩個具名 mutator（此二名係換稱後之寫法；本文原提案作 `latchEnglishAlnum()`／`releaseEnglishAlnum()`，見 §十一·五）——如此任何 `= false` 之賦值在編譯期即被擋下。

## 病灶

Phase 232 把標籤之顯示區域自「標籤字級」擴為「標籤行高」（正方形，`keyLabelBoxSide = ceil(ascender + abs(descender) + leading)`）之後：標籤右緣右移了 `keyLabelBoxSide − fontSizeKey`（`fontSizeKey = max(ceil(0.6 × 字級), 11)`，即舊制之顯示區域寬度；僅字級 ≤ 18 者受其 11 點地板影響），而**緊隨該右緣起排**的候選字詞（`phraseDrawXOffset = keyLabelBoxSide`）連帶右移同一個量。

惟 `CandidateCellData4AppKit.updateMetrics` 之 cell 寬度算式於該 phase 僅新增「標籤盒 ＋ 候選字詞 ＋ 2 × padding」之**下限**——其中 `2 × padding` 即繪製時之**前端內距**（`visualOrigin.x + 2 × padding + …`），**尾端一側未獲任何內距** ⇒ 該增量全數由尾端內距（候選字詞右緣至該格右緣之留白）吸收。實測（本機，單行橫排、非 matrix）：二字以上之候選字詞於字級 ≥ 40 時尾端內距**恰為 0.00 點**（字詞貼齊該格右緣）；單字候選者亦逐級短少（見〈驗證〉之三欄對照表）。

## 落點（定版）

`CandidateCellData4AppKit.updateMetrics`（cell 寬度之單一真源；排版與兩視圖皆經此）：

```swift
      cellDimension.width = ceil(cellDimension.width)
      cellDimension.height = Self.unifiedTextHeight + 2 * padding
      // 標籤之顯示區域自「標籤字級」（＝舊制之顯示區域寬度）擴為「標籤行高」之正方形後，
      // 標籤右緣、連帶緊隨其右緣的候選字詞，一齊右移了兩者之差；該差須由該格之總寬度一併
      // 吸收（補償），否則被吃掉的是尾端內距、候選字詞會貼齊該格右緣。
      cellDimension.width += keyLabelBoxSide - fontSizeKey
      // 選字鍵標籤之正方形區域與候選字詞必須同時放得進該格，且尾端一側亦得留足內距：
      // 內容自 2 × padding 起算、依序為標籤盒與候選字詞，尾端另留 4 × padding（經實機目視定案）。
      // （既有算式在極大字級下本就容不下「標籤 ＋ 字詞」，此處一併收緊。）
      let keyAndPhraseWidth = keyLabelBoxSide
        + makeAttributedStringPhrase(isMatrix: false).size().width
      cellDimension.width = max(cellDimension.width, keyAndPhraseWidth + 6 * padding)
```

兩道手續：①**補償**——該格之總寬度追加「標籤盒 − 標籤字級」，即「整個 candidate cell（key ＋ value）之區域」隨標籤之繪製空間一併擴大（初版即此，與定版同）；②**尾端內距入硬約束**——舊有之 `keyAndPhraseWidth + 2 × padding` 僅含前端那一份，**定版改為 `+ 6 × padding`**：前端 2 × padding＋內容＋**尾端 4 × padding**（初版曾取 `+ 4 × padding`、即尾端 2 × padding，經實機目視判為不足）。故尾端內距恆 ≥ `4 × padding`（＝8 點）。

## 附註

- **術語定調（事主 2026-09-21）**：「trailing inner padding」一律作「**尾端內距**」（不寫「尾隨內距」）；本文與程式碼、測試內之對稱詞作「**前端內距**」（自 `visualOrigin.x` 起算之 2 × padding 一份）。
- **額度之定案（事主實機目視）**：尾端內距 ＝ **4 × padding（8 點）**。初版之 2 × padding（4 點）雖與**前端內距**（2 × padding）對稱，惟實機目視仍嫌不足——故本 phase 之定論為「尾端一側需較前端一側寬」（前端 2 × padding ＋ 尾端 4 × padding ＝ 硬約束之 `6 × padding`）。
- **補償之參照值取 `fontSizeKey`（而非復辟 `ceil(0.6 × 字級)`）**：`fontSizeKey = max(ceil(0.6 × 字級), 11)` 即「標籤自身之字級」，亦係「標籤盒相對之舊制值」在現行碼內之表達式。字級 ≤ 18 時其 11 點地板生效 ⇒ 補償量較歷史值略小（字級 12：補 2 而非 5）——**屬保守側**（寧少補不多補）；該字級下之尾端內距（13.08 點）遠高於新設之 8 點地板，故無實害。
- **只作補償而不只加地板之理由**：若僅加地板而不作補償，**單字候選之既有算式（`textDimension.width + 4 × padding` 之 1.4 紋理餘裕）本就不觸發該約束**，其尾端內距仍停在術前水準（如字級 32 之 5.65 點）——與事主「對整個 cell 之區域作總體擴大」之要求不符。故補償須加在**基礎寬度**上（無條件、逐格），地板則負責托底（定版下單字候選之實測值 12.15～36.05 點即兩者疊加之結果）。
- **相鄰未修（已量測、未動）——橫排多行（matrix）路徑**：該路徑之 cell 寬由 `cellWidthMultiplied(minCellWidth:)` 覆寫（以 `blankCell.cellLength()` 之倍數為單位），**不經**上述硬約束、亦不吃本 phase 之補償（四行視窗寬於初版與定版逐點相同，即其證）。其實測尾端內距（單候選、四行）：中文候選 4.16～59.58 點；**拉丁候選於字級 12 者僅 0.92 點**（該例之格寬 45.0 與標籤盒無涉，惟候選字詞之起點受標籤盒影響——舊制偏移 8 對今 13 ⇒ 該例之尾端內距自 5.92 點降至 0.92 點）。此係該路徑以「全形空白之最小格寬」為單位所致；本 phase 依最小變更原則未動之。**事主裁定（2026-09-21，實機目視）：「沒什麼故障，先不動了」——本項不另立工作、暫不處置。**

### 一、三項決定性發現

1. **★ JSON 偏好匯入匯出機制已存在，且恰為本提案所需之格式。** `UserDef.exportAsJSON()`／`importFromJSON(_:)`（`Sources/Shared/UserDef/UserDef.swift:242／:258`）已提供：118 條鍵之逐鍵處置、**6 條黑名單**、逐型別值域驗證、逐筆成敗回報。另有 GUI 入口（設定畫面「開發道場」頁，含**拖放匯入**）與 CLI 入口（`--dump-prefs-json`／`--import-prefs-json <path>`）。
   ⇒ **第二階段無須等待第一階段。** 助手產出的 JSON 現行唯音已經能吃（「下載設定包 → 拖入設定畫面」）；深層連結只是磨掉最後一哩的摩擦。
2. **★ `vChewing://` 是全新、從零設計的攻擊面。** 全工作區（含 git 歷史）零 `CFBundleURLTypes`（IME 側）、零 `NSAppleEventManager`、零 `application(_:open:)`、零呼叫端簽章驗證。唯一的 scheme `vchewingdbg` 屬**不隨發行版出貨**的 `vChewingDebuggable` 診斷 App。

### 二、第一階段之設計要點

- **註冊**：唯一落點為 `Sources/vChewingIME_macOS/Resources/Info.plist`（**實體檔、非模板**，兩條建置路徑皆讀它；新增字面 `CFBundleURLTypes` 無須改動任何 substitution）。
- **派送點**：建議於 `AppDelegate.applicationWillFinishLaunching`（`AppDelegate.swift:92`）最前段安裝 `NSAppleEventManager` 之 `kAEGetURL` 處理器。**刻意不採 `application(_:open:)`**：該檔同時服務 legacy 發行版（部署地板 macOS 10.9），而 `NSAppleEventManager` 路徑自 10.9 起即存在，單一碼路同時滿足兩側。
- **URL 語法**：`vchewing://prefs/apply?data=<percent-encoded minified JSON>[&v=1][&nonce=<32-hex>]`；另有 `revert` 與（dev 用）`ping`。**動詞族永久限定為 `prefs/*`**，明確拒絕日後把辭典／檔案／shell 等能力加進 scheme。
- **傳輸**：助手產物天然稀疏（只輸出使用者答過的題，典型 15–30 鍵），全包 encoded 後 < 1.5 KB ⇒ **v1 不需壓縮**；設 64 KiB（解碼後）／128 KiB（encoded）上限。
- **⚠ 匯入後的行為缺口（本次新發現）**：`UserDef.importFromJSON` 直接寫 `UserDefaults`、**不經 `PrefMgr` 的 `@AppProperty` setter**，故 13 條帶 `didSet` 副作用之偏好（`didAskForSyncingLMPrefs`、`didAskForRefreshingSpeechSputnik`、`didAskForSyncingShiftKeyDetectorPrefs`）一概不觸發；而 IME 進程是**長駐**的。既有 import 路徑之收尾只有 `fixOddPreferencesCore()`（值域與正規化面已顧及，**推式同步未顧及**）。⇒ 規格要求新增一次「匯入後和解」（`fixOddPreferencesCore()` ＋ 對 13 條鍵自我賦值以觸發 `didSet` ＋ `synchronize()`），並建議**一併修既有 import 路徑**。
- **有序化（事主明示之要求）**：新增 `@MainActor final class PrefsDeepLinkBroker`（全部狀態在主執行緒，與 `Notifier`／`UserDefaults`／`NSAlert` 之執行緒要求天然一致，**不需要** actor 或鎖）。四道護欄：**單槽待辦（latest-wins 合併，且合併只作用於尚未開始者 ⇒ 已受理者仍嚴格 FIFO）**、最小間隔 0.3 s、相同載荷 3 s 內去重、10 s 內受理 > 8 筆則丟棄並回報。解析失敗者**即時回報、不進佇列**，故佇列不可能被垃圾撐爆。核心邏輯應以「注入時鐘與套用器」之方式做到純函式可測。
- **飄窗回饋**：沿用 `Notifier.notify(message:)`（`Packages/vChewing_NotifierUI`，螢幕右上、可見區頂端下方約 100 pt、右緣內縮 20 pt）——**此即事主所指之「畫面右上角飄窗提示」**。須遵守其五項限制（≤3 張卡、0.3 s 去重、顯示 1.3 s、**空訊息直接丟棄**、`ignoresMouseEvents = true` ⇒ **不可能有按鈕**）。
- **防濫用（六層；事主明示之要求）**：
  1. **沿用既有**：`UserDef` 黑名單（擋掉檔案路徑與介面語言）＋ 逐型別值域驗證 ＋ 未知鍵一律拒絕 ＋ 大小上限。
  2. **一次性 nonce 交握**：IME 於使用者主動按下「配置助手……」時生成 128-bit nonce，**僅存記憶體**、TTL 10 分鐘、單次使用；以 `NSWorkspace` 開啟 `<主站>/assistant/#nonce=<hex>`（置於 fragment ⇒ 不進伺服器日誌）。**誠實界定其效力**：它提高「盲呼與網頁順手牽羊」之門檻，**不是密碼學保證**（nonce 曾出現於 URL）。
  3. **無（有效）nonce ⇒ 一律經 `NSAlert` 確認**：列出「將變更 N 項」與逐項可讀摘要，照既有慣例（`activate(ignoringOtherApps:)`、`runModal()`、`NSApp.popup()`、已有 modal 則不重開、`pendingUnitTests` 短路）。⇒ 任何未經使用者本機主動授權之變更皆不可能靜默發生。**不提供「今後不再詢問」之永久豁免**——受信任的路徑就是那顆按鈕本身，而它是逐 session 生效的。
  4. **可還原**：每次成功套用前，**僅在記憶體**留存「本次實際變更之鍵 × 先前值」之單筆快照；出口為 IME 選單新增之「還原上次由配置助手套用的變更」與 `vchewing://prefs/revert`。⇒ 即使第 3 層被社交工程繞過，損害仍一鍵可逆；此層亦同時免除「給飄窗加按鈕」之死路。
  5. **紀律**：scheme 不擴權、不新增任何 entitlement（**特別是不得**加入 Apple Events 相關者——接收 `kAEGetURL` 不需要），受理與拒絕皆 `vCLog` 留痕（不含完整載荷）。
  6. **不建議**實作呼叫端簽章驗證（`keySenderPIDAttr` ＋ `SecCodeCopyGuestWithAttributes`）：網頁點擊之送出者是瀏覽器、終端機之送出者是 shell，白名單在此無意義，而它會引入本倉零先例且需長期維護的安全程式碼面。
- **落點清單**：`Info.plist`、`AppDelegate.swift`、新增 `DeepLink/`（Broker ＋ NonceStore）、`PrefMgr_Utilities.swift`（和解）、`IMEMenuSputnik.swift`（兩顆選單項）、`SettingsUIHostWiring.swift`、四語系 `.strings`。

### 六、派送方式之定案（剪貼簿路線）

**事主原話如下**：

> 或者先不用管開發道場了：
>
> 在「偏好設定 -> 一般設定」「我姓ㄅ」按鈕下方新增按鈕「點此從剪貼簿匯入（由配置助手生成的）配置資料」，運作機理與「我姓ㄅ」差不多：用 NSAlert 知會使用者「有哪些與當前設定不同的選項會被改」，讓使用者決定是否正式套用。
>
> 注意：這個交換格式裡面除了剛才提到的 json 代碼以外，還需要一個欄位來顯示這個交換格式所導入的配置的總體目的是什麼（比如說「這套配置會讓輸入法在行為方面盡量對齊XXX」）。NSAlert 在顯示 descriptions 時，先顯示總體目的，然後 `\n\n` 接續一個清單、顯示被改過的 UserDef 條目的標題。

**落點已實查**：「我姓ㄅ」按鈕位於 `Packages/vChewing_SettingsUI/…/SettingsUI/VwrSettingsPaneGeneral.swift:92`，其機理為 `ActiveAlert` enum 之兩段式 alert（`:103-175`：確認 → `applySCPCPreset()` → 成功；另有 `fartWarning`），套用函式見 `:182-214`；AppKit 之對位實作見 `…/VwrSettingsPaneCocoaGeneral.swift:137-184`。**新按鈕即複製此形態**，差別只在資料來源為剪貼簿、且確認訊息由**差異清單**動態生成（`UserDef.metaData.shortTitle` 之本地化標題）。`NSPasteboard` 在本倉**已有先例**（服務設定頁之複製功能）；設定視窗與 IME **同進程**。

**交換格式之中介辭典**：**單一**根層中介鍵 **`__UserDefMeta`（辭典型別，成員值皆為 String）**，供放置 `title`（配置短名，作 alert 之標題）與 `description`（**總體目的**，作 alert 訊息之第一段）等內容，餘為保留。**保留前綴為雙底線 `__`**：`UserDef` 之 118 條 rawValue **已有 2 條以單底線起頭之真偏好鍵**（`_DebugMode`／`_FailureFlag_POMObservation`），而**無一條以 `__` 起頭**（實測 0）。**處理序**：以 `NSJSONSerialization` 解為辭典 → **無條件摘除根層所有 `__` 起頭之鍵**（故形狀異常者亦不會落進逐鍵驗證而報 `Unknown key`）→ 其餘內容交付逐鍵驗證。**`Shared` 之唯一必要擴充**：把現行 `importFromJSON` 之逐鍵迴圈**原封不動抽成 `UserDef.importFromDictionary(_:)`**，`importFromJSON` 改為「解碼 → 交 `importFromDictionary`」之薄殼（**既有呼叫端與語意不變**）；另新增 `destructureExchange(_:)`／`importFromExchangeJSON(_:)`／`diffAgainstCurrent(_:)` 等專用 API。**alert 之訊息組版**：「`description` → `\n\n` → 被改之 `UserDef` 條目標題清單」。**硬性前提（事主 2026-09-24 明示）**：`UserDef` 之 rawValue **不得以 ASCII 雙底線 `__` 開頭**（否則該鍵會被無條件摘除、永遠無法匯入）——須明文寫入 `UserDef.swift` 之 `enum` doc comment，並以單元測試守住；單底線 `_` 不在此限。**權威規格見〈研究報告〉§三。**

**差異之判定**（易錯處）：須以「**該鍵會被實際寫入、且寫入後之值與當前值不同**」為準——即先過黑名單與值域驗證，再與當前值比較，且兩側先對齊同一表示法；**不得**以「JSON 內有出現該鍵」為準（否則會出現「明明一樣卻列為不同」之偽陽性）。

**評估**：理由（web scheme 之完整設計與其獨有價值存於〈研究報告〉附錄 A）：

1. **它消滅本文大部分之風險與複雜度**——R1／R2／R9／R10、S1／S2／S11／S12／S13、以及 §3.8 之 nonce 與確認層**皆隨之消失**（不是被緩解，而是**不存在**）。
2. **「使用者同意」變成結構性的**：使用者親手按下按鈕、並在 alert 內看清「哪些選項會被改」，即是同意——比任何 nonce 都強。
3. **和解回到同行程之單純形態**：設定視窗與 IME 同進程，故 13 條 `didSet` 就地可觸發，跨行程分散式通知整個不需要。
4. **第二階段-α 之價值即可變現**：整條路徑只差**一個按鈕**。
5. 代價（多幾步、失去「一鍵」與「可分享連結」）與 OOBE 之一次性性質不成比例。

**仍須做**：① 新按鈕 × 2 介面，且與既有之檔案／拖放路徑**共用抽出之 `applyPrefsJSONFromData(_:)`**（順帶修好既有 import 之 `didSet` 缺口）；② 五態 alert（`confirmApplying`／`succeeded`／`noDifferences`／`failedToParse`／`clipboardEmpty`）；③ 訊息組版照事主明示——總體目的 → `\n\n` → 被改條目之標題清單；④ 抽出差異計算（見上）；⑤ 套用後呼 `reconcileAfterExternalPrefsImport()`；⑥ 剪貼簿讀取之沙盒確認（〈研究報告〉§六 S14）；⑦ 助手最終頁改為「複製設定包 → 引導使用者開『偏好設定 → 一般設定』→ 按鈕」（**不可再引入 scheme 代開設定視窗**，否則等於把 scheme 從後門請回）。**原 scheme 設計不刪、原位保留為選配。**

（本項即〈研究報告〉§〇.2 定案表之「派送方式」一列；web scheme 之相關構想不屬本計畫。）

### 八、施工過程之附註（工具層實錄，供後續 phase 參考）

- 本 phase 之施工以 3 個並行／串行 worker ＋ 協調者複驗行之。**工具層之寫入權限以「spawn 時之 `cwd` ＋ `write_roots` 疊加」解析**：凡 `write_roots` 誤以工作區根相對路徑給定者，實際會落在 `cwd` 之下而全數失效（本 phase 實測：L1 worker 因此**未能寫入 macOS 鏡像**）——該兩檔後由協調者以正本 `cp` 覆製並以 `cmp` 驗證逐位元組相同。

- **施工中抓到之兩處缺陷（皆已修，值得記為教訓）**：
  1. **測試檔之 `deinit` 不得呼叫 MainActor 隔離之 API**：`UserDef.resetAll()` 因兩倉 manifest 之 `defaultIsolation(MainActor.self)` 而繫於 MainActor，而 `deinit` 恆為 `nonisolated` ⇒ 兩倉之新測試檔當場編譯失敗；定案為「`deinit` 只復原 `UserDefaults.pendingUnitTests`，清理一律置於各測試之 `init`」。
