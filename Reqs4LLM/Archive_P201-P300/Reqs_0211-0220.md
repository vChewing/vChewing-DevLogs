### 附記：LibVanguard 之 `percept` 私有輔助不移植之決策

事主就〈落點〉（三）反問「LV 的 `percept` 輔助值得搬嗎，還是完全沒價值」，經逐條查核後**裁定為不移植**。它並非「完全沒價值」，而是在 macOS 這一側其價值被稀釋至零：

1. **零行為**：純轉發，不含斷言、不含預設時間戳、不含 fixture 組裝——只是把一個 tuple 參數拆成具名參數。
2. **省不了字**：`percept(who: pom, key: k, candidate: c, timestamp: t)` 共 74 字元，對照直呼 `pom.memorizePerception((ngramKey: k, candidate: c), timestamp: t)` 為 82 字元，差距在雜訊水準。
3. **反而藏起被測 API 的名字**：macOS 測試端對 `memorizePerception` 有 **93 個直呼點**（9 個 POM 測試檔 ＋ InputHandler 測試）；測試檔內直呼生產符號本身即契約文件。遷入別名會使 LV 側那 21 個注入點自 grep 視野消失。
4. **該輔助是 LV 自身標籤 sprawl 的副產品，且 LV 自己並未統一**：同一個 `Sources/_Modules/LexiconKit/LX_Components/LX_SubLMs/LX_Perceptor.swift` 內，`ngramKey` 見於 `:135`／`:208`／`:216`／`:220`，唯有「注入」重載用冗長的 `contextualizedGramKey`（`:170` 的 `(contextualizedGramKey:candidate:)`；`:197` 另有一個吃 `Homa.PerceptionIntel` 的重載）。而 **macOS 側根本沒有這個 tuple 標籤**：macOS 的 `memorizePerception` 簽名為 `(ngramKey: String, candidate: String), timestamp:, saveCallback: = nil`（`LXPerceptor.swift:663`）；macOS 的 `contextualizedGramKey` 是 `Homa.GramInPath` 的屬性（`Homa/Homa_BasicTypes/Homa_GramInPath.swift:75`），與此無關。故該輔助存在的唯一理由，在 macOS 不存在。
5. **慣例一致性**：macOS 為 93 個直呼點的統一慣例，單檔冒出 21 個別名呼叫會淪為孤兒慣例。

**判準（日後何時這類輔助才值得存在）**：

- 會**斷言**的輔助——注入後立刻 `#expect(pom.mutLRUMap[key] != nil)`，把「靜默空轉的注入」變成紅燈。但這會改動 93 個呼叫點的語意，屬刻意決定而非移植。
- 帶**預設時間戳**的輔助——但 macOS 的 POM 測試刻意逐案給不同時間戳（觀測窗衰減是該族主軸），預設值只會招來複製貼上錯誤。
- **fixture 級**輔助——macOS 已在更高層以 `TestLX(rawData:)` 處理；反向而言，LV 專屬的 `LXTests4TrieHub` 才是真正值得一看的那個。

**附帶結論**：日後若將 LV 的 POM 測試族整體收斂進 macOS（方向仍以 macOS 為正本），搬運時應拆掉 `percept` 包裝、一律直呼 `memorizePerception`。

### 一、`LexiconGramSupplierProtocol`（新檔 `Sources/LexiconAssembly/LexiconGramSupplier.swift`）

三項要求與 LibVanguard 逐一對應：`hasGrams(_:filterType:partiallyMatch:partiallyMatchedKeysHandler:)`、`queryGrams(_:filterType:partiallyMatch:partiallyMatchedKeysPostHandler:)`、`queryAssociatedPhrasesAsGrams(_:anterior:filterType:)`。另含 LibVanguard 的三組預設參數擴充與 `queryAssociatedPhrasesPlain(_:anterior:filterType:)`（僅容器由 `VanguardTrie.TrieGram` 換成 `Homa.Gram`，演算法逐行照搬，含「只能用基於 String 的 Hash」那句註解的成因）。協定保留 `AnyObject` 約束：來源是以**參照**被掛載、而非被複製。另補一個橋接建構子 `Homa.Gram.init(_ trieGram: VanguardTrie.TrieGram)`——LibVanguard 側因 `HomaGram` 與 `TrieGram` 本是同一型別而無此需求，OSNA 側的 `Homa.Gram` 是獨立型別。

### 二、`GramConcatFlags` 與合流 API（新檔 `Sources/LexiconAssembly/LX_GramConcatAPI.swift`）

- `LXAssembly.GramConcatFlags`（`OptionSet, Codable, Hashable, Sendable`）：`.sort`／`.deduplicate`／`.all`。**空集合即「原樣串接」**——依來源掛載順序保留所有結果（含重複），完全不動次序。
- `concatGramAvailabilityCheckResults(@ArrayBuilder<Bool?>:)`：任一來源在庫即在庫；`nil` 視為未表態。
- `concatGramQueryResults(flags:forbiddenKeyValueHashes:grams:)`：`nil` 來源略過 → 可選排序 →（`forbiddenKeyValueHashes` 非空時改以該集合作為唯一過濾依據、**不再另行去重**）否則可選依身分雜湊去重、保留最先出現者；全空回 `nil`。結果建構子用既有的 `SwiftExtension.ArrayBuilder`。
- `sortGrams(_:_:)`：**幅長降冪 → 讀音索引鍵字面升冪 → 權重降冪**（LibVanguard 原政策，刻意與 `Homa.Assembler.sortGram` 的「權重優先」不同；程式碼內已註明此差異，以免日後被當成 bug 修掉）。
- `makeGramIdentityHash(_:)`／`makeGramIdentityHash(keyArray:value:previous:)`：身分＝讀音索引鍵 ＋ 詞值 ＋ 前驗詞值，**刻意不含 `anterior` 與權重**（與 LibVanguard 逐欄一致；權重不屬身分、故同讀音同詞值不同權重者視為同一筆）。

### 三、`LXGramSupplyHub` 與 `LXFactoryGramSupplier`（新檔 `Sources/LexiconAssembly/LXGramSupplyHub.swift`）

- `LXAssembly.LXGramSupplyHub: LexiconGramSupplierProtocol`——多來源元圖供應中樞，對應 LibVanguard `TrieHub` 的角色：`mount(_:)`／`unmountAll()`／`mountedSuppliers`／`concatFlags`，並自帶 `generation` 計數器（掛載異動時遞增，供 `LXFacade` 的查詢快取指紋使用）。`hasGrams` 走「任一來源在庫即在庫」；`queryGrams`／`queryAssociatedPhrasesAsGrams` 走 `concatGramQueryResults`，兩個通道的 `partiallyMatchedKeys` 一律於 `defer` 中回報（聚合後去重，故即使來源各自回報重疊鍵亦不重複）。空掛載時三個入口皆短路。
- `LXAssembly.LXFactoryGramSupplier: LexiconGramSupplierProtocol`——把原廠辭典後端包成可掛載來源，**每次查詢即時向 `LXFacade.factoryTrie` 取值**，故原廠辭典重新連接或卸載後無須重新掛載；供應的是未經後處理的原始元圖（不施假名抑制、不補半形變體、不改權重正負號）。程式碼內以 `<warning>` 明示：若把它掛進 `LXFacade`，同一批原廠資料會與內建原廠查詢路徑重複供應。

### 四、`LXFacade` 的掛載接點（新檔 `Sources/LexiconAssembly/LXFacade_GramSupplierMounting.swift` ＋ `LXFacade.swift` 六處）

- `LXFacade` 新增 `let gramSupplyHub = LXGramSupplyHub()`（internal），對外暴露 `mountedGramSuppliers`／`mountGramSupplier(_:)`／`unmountAllGramSuppliers()`；`LXQuerier`（唯一公開查詢面）同步轉發三者。
- **接進生產管線**：`unigramsFor(keyArray:partiallyMatch:)` 與 `unigramsForWithAlternatives(...)` 各在「原廠辭典那一區塊的最末」追加 `rawAllUnigrams += mountedSupplierGrams(...)`（替代讀音路徑以 `"&"` 連讀鍵詢問，與原廠辭典的 chopped 路徑一致）；`hasUnigramsForFast(keyArray:)` 在同一個 cassette 條件守衛內追加 `mountedSuppliersHasGrams(...)`。**最後一項是必要的、不是錦上添花**：`Homa.Assembler` 以 `hasGrams` 判定讀音是否合法，若輕量版在庫檢查不認得掛載來源，該來源的元圖永遠不會被查詢到。

## 已知的硬約束：SwiftPM 的 `duplication of library code`

2. 要成立，**必須讓 `Vanguard` 完全離開 installer 的 product 圖**（含遞移），而非只換一條宣告。
3. `OSFrameworkImpl`／`IMKUtils` 改指向窄產品後，IME 側的 `vChewing` product 圖內該模組會變成「經中介套件靜態 ＋ 經 `Vanguard` 動態」→ 換那裡觸發同一條禁令。**故「窄產品要裝什麼」是本 phase 的關鍵設計決定。**

### 丁之精確化（動工前唯讀複查所得）

決定性事實：**兩個中介套件對 `Vanguard` 的依賴，純粹只為了 `SwiftExtension` 一個模組。** 實查其 `Sources/`：

- `vChewing_OSFrameworkImpl/Sources/OSFrameworkImpl/OSFrameworkImpl.swift:5` 為 `@_exported import SwiftExtension`；另有 `AppKitImpl/{NSView,NSWindowController,NSWindowPositioner}.swift` 各一行 `import SwiftExtension`。
- `vChewing_IMKUtils/Sources/IMKUtils/IMKHelper.swift:6` 為 `import SwiftExtension`。
- 對 `Vanguard`／`Homa`／`Tekkon`／`Shared`／`LXAssembly`／`TrieKit`／`BrailleSputnik`／`BPMFVS`／`ResourceLocator` 的 `import`：**兩套件皆零命中**（連 `import Vanguard` 本身亦零命中——它們是經由 `.product` 宣告取得該模組的，原始碼從未指名它）。

installer 側同理：自身只 `import SwiftExtension`（3 處），別無他求。

**故丙之落點僅三處**（外加 manifest 之兩倉同步）：

1. `vChewing_OSNeutral_LibVanguard/Package.swift`（**兩倉同步**）新增 `.library(name: "VanguardSwiftExtension", type: .dynamic, targets: ["SwiftExtension"])`。
2. `vChewing_OSFrameworkImpl/Package.swift:29`、`vChewing_IMKUtils/Package.swift:43` 由 `.product(name: "Vanguard", …)` 改 `.product(name: "VanguardSwiftExtension", …)`——**其原始碼一行不動**（它們本來就只 `import SwiftExtension`）。
3. `vChewing_InstallerAssembly4Darwin/Package.swift` 同上改法。

### 為何丁必須是 dynamic（不可為 static）

若 `VanguardSwiftExtension` 為 **static**，則 IME 側 `vChewing` 的 product 圖內，`SwiftExtension` 會同時以「靜態（經中介套件）」與「動態（經 `Vanguard`）」兩態出現——正是〈已知的硬約束〉所載 P210 的 `duplication of library code`，必然被 SwiftPM 拒絕。改為 **dynamic** 則兩者皆動態，該禁令不適用。**事主選丙的直覺在此得到印證：丙不只「可行」，而是「在不拆 target 的前提下唯一可行」的那條。**

### 丁的代價（必須於手術記錄中載明）

- IME 側 `vChewing.app` 自此會**同時載入兩顆動態庫**：`libVanguard.dylib`（整份閉包）與 `libVanguardSwiftExtension.dylib`（僅 `SwiftExtension`）。此為新增之建置產物與執行期映射。
- `SwiftExtension` 於該行程內**存在兩份 image 副本**（一份內嵌於 `libVanguard.dylib`、一份在 `libVanguardSwiftExtension.dylib`）。
- 安全性論據（須於記錄中複述並以實測複驗）：`SwiftExtension` 的對外 API 是**對標準函式庫與 Foundation 型別的擴充、外加少量 static 常數**（installer 端實際使用者即 `String.i18n` 與 `NSApplication.isAppleSilicon`），擴充方法逐 image 靜態派送、無 vtable 或 ABI 之跨邊界問題；且 installer 與 IME 之間從不傳遞 `SwiftExtension` 的自定義型別。**仍須驗證** `SwiftExtension` 是否含自定義公開型別、以及該型別有無跨越 dylib 邊界。
- `Vanguard` 內部（`TrieKit` 等）對 `SwiftExtension` 的依賴不變，故 `libVanguard.dylib` 之內容零變更。
- `VanguardSwiftExtension` 僅裝 `SwiftExtension` 一靶，該靶無資源，故不產生新資源 bundle、亦不觸及 P210 的去 bundle 化設計。

### 丁之精確化（第二輪，動工前唯讀複查）：`SwiftExtension` 必須在每個行程內只有「一份 image」

**決定性發現**：`SwiftExtension` 不只是工具函式，它的**型別出現在 `OSFrameworkImpl` 的公開介面上**——而 `OSFrameworkImpl` 正是 installer 的 AppKit DSL 來源（`AppKit/VwrAppInstaller4Cocoa.swift:10`、`SwiftUI/VwrAppInstaller4SwiftUI.swift:12` 皆 `import OSFrameworkImpl`；DSL 成員如 `buildSection`／`stack`／`makeSimpleConstraint`／`makeNSLabel`／`boxed`／`pinEdges`／`NSFileDragRetrieverButton`／`NSLabelView`／`UILayoutOrientation`）。

| 事實 | 位置 |
|---|---|
| `@ArrayBuilder`（SwiftExtension 的 `@resultBuilder enum`）**出現在 public 簽名** | `Sources/OSFrameworkImpl/AppKitImpl/AppKitImpl_NSView.swift:609`：`public init?(title: String, @ArrayBuilder<NSView?> views: () -> [NSView?])`；另 6 處同款 |
| **retroactive conformance**：對 SwiftExtension 的 `AppProperty` 由 OSFrameworkImpl 這邊宣告 | `Sources/OSFrameworkImpl/SwiftUIImpl.swift:171` `extension AppProperty: @retroactive DynamicProperty {}` |
| `NSMutex<…>` 型別 | `AppKitImpl_NSView.swift:771`、`AppKitImpl_Misc.swift:87/131/510`、`SecureEventInputSputnik.swift:136` |

**推論**：若照〈丁之精確化〉第一版施工（installer 與兩中介套件改吃動態窄產品，而 `Vanguard` 內部仍靜態內嵌自己那份 `SwiftExtension`），則 **IME 行程內會同時存在兩份 `SwiftExtension` 具名型別**。而「同名具名型別多份 image」＋「conformance 宣告在型別所屬模組之外（retroactive）」＋「builder 型別出現於公開簽名」三者疊加，正是 Swift 的 **ABI 危險型態**：屬「單元測試全綠、生產才炸」那一類，不可用「原始碼相同故佈局相同」一句帶過。

**故丙之落實形態（丁，即丙之精確化形態）**：`VanguardSwiftExtension` 為 dynamic 之外，**聚合體內部對 `SwiftExtension` 的取用亦須改走該產品**（同套件之 product 依賴），使 `SwiftExtension` 被靜態連結進**唯一**一顆 dylib（`libVanguardSwiftExtension.dylib`），`libVanguard.dylib` 以動態方式相倚之。結果：

- installer 行程：只有 `libVanguardSwiftExtension.dylib` 一顆；
- IME 行程：兩顆 dylib（`libVanguard.dylib` ＋ `libVanguardSwiftExtension.dylib`），但 **`SwiftExtension` 恰好一份 image**。

**不變式（驗收用之）**：*每個行程內 `SwiftExtension` 的具名型別恰好一份 image。* 任何形態若違反此不變式，即不得採用。

**待實測之關鍵未知**：SwiftPM 是否允許「某 target 依賴**同套件**的 dynamic product」。允許則丁直接成立；不允許則須另尋能維持該不變式的形態。**此為本 phase 最可能翻盤的一點，須最先行之。**

| C | target 僅屬 dynamic product，同套件 exe 以 target 名依賴之 | ❌ exe **未**連結 `libLeafDyn.dylib`（`otool -L` 無此條），且 `leafValue` 在 exe 為**已定義**符號 → 靜態併入 |
| D | 同一 target 同時列入兩個 dynamic product | ❌ `libWide.dylib` 仍**靜態內含** `leafValue`（defined=1）；兩顆 dylib 各一份而 **SwiftPM 不報錯**（靜默重複） |
| E | **＝丁之原定形態**：target 只列入 `LeafDyn`，`Wide` 以 target 名依賴之 | ❌ 同 D：`libWide.dylib` 靜態內含（defined=1）、未連結 `libLeafDyn.dylib` |
| G | **跨套件** dynamic product | ✅ `libWide.dylib` 之 `otool -L` 出現 `@rpath/libLeafDyn.dylib`，`leafValue` 在 libWide 為**未定義**（undefined=1）→ 真動態相倚 |

**判決：丁之原定形態（聚合體內部以同套件 product 形式取 `SwiftExtension`）在 SwiftPM 下無法表達。** 後果不是編譯錯誤，而是**靜默產出兩份 image**——正是〈不變式〉所禁。

**唯一能維持不變式之形態（＝探針 G 已驗證）**：把 `SwiftExtension` 的**來源碼移出聚合體**，放進一個獨立的本機套件（如 `Packages/vChewing_SwiftExtension`），由該套件出貨 **dynamic** product（依事主命名，名為 `VanguardSwiftExtension`）；聚合體之 5 個內部靶與全部外部消費端皆改以該**跨套件** dynamic product 取用之。

**兩份 image 之風險已量化（此為不可採 D／E 之實據）**：聚合體自身（將被併入 `libVanguard.dylib`）使用 `@AppProperty` **115 處**（`Shared/PrefMgr_Core.swift` 即佔 103 項偏好屬性）、`NSMutex` **22 處**、`ArrayBuilder` 4 處；而 `OSFrameworkImpl` 這一側對 `AppProperty` 宣告了 retroactive `DynamicProperty` conformance、並把 `@ArrayBuilder` 用在 public 簽名。即「**SwiftUI 綁定的偏好屬性值住在 dylib、其 conformance 卻宣告在 exe 側**」——兩份 image 之下即是實質風險，非理論顧慮。

**爆炸半徑（已量測）**：需改動之 manifest ＝ 聚合體自身 ＋ **10 個直接 `import SwiftExtension` 的消費套件**（`OSFrameworkImpl`／`IMKUtils`／`InstallerAssembly4Darwin`／`MainAssembly4Darwin`／`CandidateWindow`／`SettingsUI`／`Shared_DarwinImpl`／`UpdateSputnik`／`NotifierUI`／`FolderMonitor`），另可能涉及 `vChewing.xcodeproj/project.pbxproj`（新增本機套件參考）與 CI 清單——**已超出本 phase 宣告之手術範圍**。

**本 phase 狀態：動工暫停、待事主裁定。** 依〈丁之跨平台分流〉末句「若被拒，須回報事主、勿自行降級為兩份 image」辦理：生產碼**一行未動**（本 phase 全部落點僅止於本節之探針與紀錄）。

### 丁之跨平台分流（事主裁定，2026-09-14）

**事主裁定（原文）**：

> macOS 版自帶兩個 dylib 已經是不可避的事實。你可以用條件編譯的方式讓 SwiftExtension 在 macOS 以外的系統下變成 static。

即：**Darwin 走丁**（兩顆 dylib；`SwiftExtension` 一份 image）；**非 Darwin 維持今日形態**（`SwiftExtension` 仍為 static、仍內嵌於唯一那顆 `Vanguard` 動態庫）。**不得因本 phase 而在 Linux／Windows 產生第二顆動態庫、或改變既有產物結構**（LibVanguard 倉的 ubuntu／winnt CI 必須維持原狀）。

**落實機制——P214 的 ArrayBuilder DSL 正是為此而備**：於 `Package.swift` 的 `buildProducts`／`buildStrings`／`buildTargetDependencies` 內以 `#if canImport(Darwin)` 分流（`buildSupportedPlatform` 已有同一寫法的先例）。要點四條：

1. `buildProducts`：**Darwin 專屬**新增
   `Product.library(name: "VanguardSwiftExtension", type: .dynamic, targets: buildStrings { "SwiftExtension" })`；非 Darwin 分支不新增。
2. `Vanguard` 產品的 target 清單（現行第 35 行 `"SwiftExtension"`）：**Darwin 下須移除**——否則它一邊是被列出的成員、一邊經新產品動態取得，即兩份 image，違反〈不變式〉；非 Darwin 保留於清單內（今日形態）。
3. 依賴 `"SwiftExtension"` 的 7 處（產品清單 1 ＋ target 定義 1 ＋ 依賴 5：`ResourceLocator`／`Shared`／`LexiconAssembly`／`LibVanguard` 等生產靶，另加測試靶 `SwiftExtensionTests`）：**Darwin 下改 `.product(name: "VanguardSwiftExtension", package: "LibVanguard")`**，非 Darwin 下維持 `"SwiftExtension"`。**測試靶必須一併處理**——否則測試產品的圖上會出現「靜態（測試靶直取 target）＋動態（經產品）」並存，觸發 `duplication of library code`。
4. 兩倉 `Package.swift` 仍須**逐位元組相同**（`cmp` 複驗）：條件編譯對兩倉一致生效，LibVanguard 倉的 ubuntu／winnt CI 自然走非 Darwin 分支。**附帶查核**：非 Darwin 下 `swift package dump-package` 不應出現 `VanguardSwiftExtension`，且 `Vanguard` 之 target 清單仍含 `SwiftExtension`。

**待實測（丁成立之前提，須最先行之）**：SwiftPM 是否允許「某 target 依賴**同套件**的 product」。若被拒，**須回報事主、勿自行降級為「兩份 image」**——那會命中〈丁之精確化（第二輪）〉所述之 ABI 危險型態。

### 二、實跑探針事故（教訓）

**後果**：事主的輸入法於施工期間失效；`defaults read com.apple.HIToolbox AppleEnabledInputSources` 已不含 vChewing（該輸入源被停用）。

- 腳本內變數緊鄰 CJK／全形字元者**一律寫 `${var}`**（KnowledgeMemo §12.6 已載此坑，本次仍踩）。

## 追加二：子套件改置於聚合體目錄內之 `Deps/`，兩倉 manifest byte-identity 復原（事主裁定）

## 追加三：CI 回報 `supported platforms can't be empty` 之修法（事主部署，兩倉）

**事主回報（原文）**：

> 測試確認 makefile-compiled products 與 xcode-compiled products 都正常。但 Windows & Linux CI 全炸：`supported platforms can't be empty`。

**根因（規劃者之誤）**：子套件 manifest 之平台分流原寫成——

```swift
#if canImport(Darwin)
  let supportedPlatforms: [SupportedPlatform] = [.macOS(.v12)]
#else
  let supportedPlatforms: [SupportedPlatform] = []      // ← 非法
#endif
```

而 `Package(platforms:)` 之參數型別為 **`[SupportedPlatform]?`**：**空陣列不合法**（SwiftPM 報 `supported platforms can't be empty`），非 Darwin 時之正解是 **`nil`**（＝不宣告平台限制）。**本機（Darwin）永遠走不到該分支**，故本 phase 之全部本機驗證（建置、測試、`make debug`、`make release`、installer 實跑、Xcode 兩 scheme）**皆無法暴露此誤——只有 CI 會**。此即〈丁之跨平台分流〉一節「非 Darwin 不產生第二顆動態庫」之落實處，也是本 phase 唯一由 CI 抓出的缺陷。

**事主修法（兩倉同步、逐位元組相同）**：

```swift
#if canImport(Darwin)
  let supportedPlatforms: [SupportedPlatform]? = [.macOS(.v12)]
#else
  let supportedPlatforms: [SupportedPlatform]? = nil
#endif
```

**本機預驗（規劃者補做，2026-09-14）**：以 scratch 套件將 `#if canImport(Darwin)` 反轉為假，強制走非 Darwin 分支（`static` 產品 ＋ `platforms: nil`），實測 `swift package dump-package` 與 `swift build` 皆 **rc=0**、**未再出現該錯誤**（`_MainWorkspace/tmp/p215LinuxSim`；未動任何生產碼）。此後凡跨平台 manifest 之條件分流，皆應以同法預驗。

**狀態**：修法與 `vChewing.xcodeproj/project.pbxproj` 之子套件 wrapper fileRef 已由事主收進 commit（`vChewing-macOS` `98f223a1`、`vChewing-LibVanguard` `d4a834c`，訊息同為 `LibVanguard // Dylibify VanguardSwiftExtension.`）；**GitHub CI 複驗已全綠**（見下）。另事主已實測確認：**makefile 產物與 Xcode 產物皆正常**。

**CI 複驗結果（2026-09-14）**：

| 倉 | `unit-test-…-linux` | `unit-test-…-WinNT` | macOS 端 |
|---|---|---|---|
| `vChewing-LibVanguard` | ✅ success | ✅ success | ✅ success（`debug-macOS-LibVanguard`） |
| `vChewing-macOS` | ✅ success | ✅ success | ✅ success（`debug-macOS-SPMTestsAndPackage`，承載於 `bcd69865`） |
