# 12.6 工作細節附註（六）：雙拼之界面行為、編輯器與偏好槽

> 本檔之條目係**依主題**自原 §12.6 抽出（原檔為時間序），共 14 條；
> 各條之次序仍照原檔。原行號： 711-721, 723, 724 行；另加原檔尾 823 行（其性質同 §12.6）。

- **★ 雙拼之排列值域與偏好槽（2026-10-12，P302；同日覆核重寫）**：三槽分離＝注音 `0...10`／拼音 `100...105`／雙拼 **200…202**（自訂 200 居宣告序首、預設 201；餘二案為微軟、GB/T；原 203–207 已隨五案撤出）。`PrefMgr.keyboardParser` 之 getter 恆回拼音／注音方案；setter 遇 `isDualpin` 之值寫 `keyboardParser4Dualpin` 並開 `pinyinTypingEnabled` 與 `dualpinEnabledForPinyinTyping`。**判準一律用 `isPinyin`／`isZhuyin`，不可寫 `>= 100`**（`fixOddPreferencesCore()` 之糾錯亦按家族）；自訂方案原文存於 `kDualpinSchemaJSON`（String、預設空），匯入時**明寫三鍵、不經 setter**。
- **★ E9 之自身豁免（2026-10-12，P302）**：`DualpinParser.validate(conflictingRawIDs:)` 之相衝條件為 `!DualpinParser.builtinParsers.contains(self), conflictingRawIDs.contains(rawID) || DualpinParser.builtinRawIDs.contains(rawID)` ⇒ **內建方案之原文（值相等者）得通過校驗**、冒名者則否；`builtin(fromJSON:named:)` 只解碼、不改值。
- **★ 雙拼下拉之段落分隔線有**兩處**就地複製（2026-10-12，P303）**：`UserDefRenderableImpl.swift:332`（SwiftUI：`if [7, 100, 200].contains(item.rawValue) { Divider() }`）與 `UserDefRenderableCocoa.swift`（Cocoa：`intOptions` 之組裝處）各一份，且**三槽之過濾一律走 `parser.isZhuyin`／`.isPinyin`／`.isDualpin`**（拼音下拉只列 100–105、雙拼下拉列 200…202）⇒ 新增／移動 `KeyboardParser` 成員時**兩處皆須改**（值集仍為 `[7, 100, 200]`——族首仍為 200，與拼音族首 100 同例）；選單標題即引擎之 `KeyboardParser.localizedMenuName`——自訂案之「綴方案標題」增補（`localizedMenuNameConsideringDualpinImport`）已於 2026-10-13 依事主裁撤（該選單無法即時生效），自訂項改示定值「自訂雙拼方案」（`i18n:KeyboardLayout.DualpinCustom`）。
- **★ 雙拼方案匯入之語義（2026-10-12，P303）**：`DualpinSchemaStore`（`Shared_DarwinImpl`）**只轉述** `Arimitsu` 之公開面（`JSONDecoder` 解碼、`validate(conflictingRawIDs:)`、`title(forLocaleTag:)`），不含檢證邏輯；1 MiB 上限、單筆整份取代、security-scoped 存取於 store 邊界 start／stop 且**不存 bookmark**。成功之四件事＝寫 `kDualpinSchemaJSON` → 寫 `keyboardParser4Dualpin = ofDualpinCustom` → 開 `pinyinTypingEnabled` 與 `dualpinEnabledForPinyinTyping`（**明寫、不經 `keyboardParser` setter**，因 getter 恆回拼音槽）→ `reconcileAfterExternalPrefsImport()`；失敗分 unreadable／tooLarge／malformed／invalid 四型（後者携 E 碼與 detail）；`statusText(after:schemaJSON:)` 於 outcome 為 `nil` 時改依偏好現值推斷（供重繪）。
- **★ 雙拼之狂打不另立開關，隨拼音側之狂打開關（2026-10-12，P302 事主實機回報後修正）**：`isFuriousTypingModeEffective` 之 `.DualPin` 臂改讀 `prefs.furiousTypingEnabled4Pinyin`（與 `LXFacade.furiousSideEnabled` 同口徑；雙拼屬拼音家族）；故關掉拼音狂打後，雙拼不再持有 copilot 候選窗、簡拼 cells 與重切分諸義。
- **★ 雙拼之刪除鍵撤銷待配之首鍵（2026-10-12，P302 事主實機回報後修正）**：刪除鍵之 `input.text` 係可列印字元，故原先行入打字機、被當非碼鍵而只清 pending 且不消費本鍵，其後落常規刪除流程時組字器已空 ⇒ 誤發 `9D69908D` 且不切狀態；現於打字機之碼鍵判定前先接住刪除鍵，撤銷 pending 並收為 `.ofAbortion()` 或刷新組字區。
- **★ 雙拼之固化時機隨狂打開關而異（2026-10-12，P302 事主交辦 m00294）**：`DualpinTypewriter` 之 `.translate` 於狂打側只把詞幹寫入組音區（讀音須留給自動套用、重切分與 copilot 候選窗），於**非狂打側**則於**次鍵當下即固化入組字器**——兩鍵既已拼出一個完整音節，該讀音節點即是合理之桶，不待下一鍵或空白鍵；固化入口仍為 `solidifyPendingSyllable`，迴歸測試用例 `IH-Dualpin-010`。
- **★ 雙拼之待配首鍵作廢後必刷新組字區（2026-10-12，P302 事主 m00498 回報後修正）**：首鍵係以組字區讀音欄呈現，故三處退位（非碼鍵、`dualpinIngest` 回 nil、`.passthrough`）不得只呼 `dualpinFlushPending()`——退位對象未消化本鍵時幽靈讀音續留顯示，其後之刪除鍵遂落進 `handleBackSpace` 空轉早退，只示警 `9D69908D` 且不切狀態。新助手 `DualpinTypewriter.delegateToBPMF(_:session:)` 於退位對象回 nil 且確有 pending 時，依 `isConsideredEmptyForNow` 收為 `.ofAbortion()` 或刷新組字區；測試用例 `IH-Dualpin-011`。
- **★ 雙拼之無效碼＝Beep＋Drop＋一過性 tooltip（2026-10-12，P302 事主 m00179 交辦、m00587 覆核）**：`DualpinTypewriter` 之 `.invalid` 分支除 `errorCallback`（OS 中立層＝日誌，session 接至系統鈴聲）與丟棄兩鍵外，另呼 `session.showTooltip("i18n:ErrorMessage.InvalidDualpinCode".i18n, colorState: .redAlert, duration: 1.2)`；**不得把 tooltip 掛在狀態上**——不成碼時組字區已空、狀態必為 `.ofAbortion`，而 `switchState` 會把它換成全新 `.ofEmpty()` 連 tooltip 一併丟棄（連續打字時遂不可見），故改為切狀態後直接呼叫。文案鍵落 macOS 側四語 `Localizable.strings`；測試用例 `IH-Dualpin-002`／`012`。
- **★ 雙拼 schema 之 `aliases` 係既有欄位，內建七案皆不宣告（收官後兩案亦然）（2026-10-12，P302；事主 m00035 之裁定使 m00989 之補齊撤回）**：別名（碼→詞幹）只進 `aliasCodeToStems`，而 `report.codeToStems` 依設計僅含主碼 ⇒ `DualpinTranslator.init(report:alphabet:)` 須併攏兩索引（逐碼去重），否則宣告者雖過校驗卻不吃鍵。惟**不得以別名替方案造出它不可能產生之讀音**：微軟雙拼之零聲母前綴鍵為 `o`（啊＝`oa`）、無任何碼起於 `a` ⇒ `aa` 於該方案恆屬無效兩鍵序（GB/T 34947-2017 之零聲母鍵為 `a`，同鍵序於彼反倒是主碼）；內建原文一律不設 `aliases`，機制改由測試內自備之 schema 驗證。
- **★ 雙拼之授權界線：小鶴雙拼（含小鶴音形）無免費授權（2026-10-12，事主轉述小鶴音形作者之親自裁示）**：內建七案之鍵位皆取自 Wikipedia `{{Shuangpin}}` 模板（收官後內建只餘兩案，亦然）（鍵位映射之概念本身不受條款約束，受約束者是官方碼表檔案本身）；**小鶴雙拼永不內建**——其作者已明確裁示不予免費授權，故該方案只能由使用者**自備 JSON schema** 經 P303 之匯入管線自行配置（引擎與內建七案一律不隨附其碼表；收官後內建只餘兩案，五案之鍵位改隨官網倉 JSON 供給）。P301 研究期之「事主去信作者迄未得覆、先不討論」自此改記為「作者已覆：不予免費授權」。
- **★ 字面節點之後的數字連打：聲調覆寫不得吞鍵（2026-10-13，P302 Amendment；事主 m05250 第①點）**：拼音側之數字向為聲調鍵（`composer.inputValidityCheck(charStr:)` 放行數字），而 `BPMFFullMatchTypewriter.consumeReadingInputIfNeeded` 前置之 `performRearIntonationOverrideIfNeeded` 只驗「`composer.isEmpty` ＋ 非空白鍵 ＋ 係聲調鍵」即取後節點之快照；後節點若係**字面標點節**（如 `_punctuation_1`），`getPreviousRearSyllableSnapshot()` 仍自 `assembler.actualKeys[cursor-1]` 逐 scalar 重建注拼槽，得一個「非讀音」之快照 ⇒ `makeOverrideRequest(newIntonation:)` 回 nil ⇒ 報 `E2FAD61C`（覆寫聲調時無法生成讀音快照）並 `return true` **吞掉本鍵**（連打「1」「2」「3」時第二位起全滅；「1」因 `composer.isEmpty` 而先落標點鏈，故倖存）。修：快照重建之後加 `guard playbackComposer.phonabetKeyForQuery(pronounceableOnly: true) != nil else { return nil }`，令非真讀音之節點放行至 triage 之標點鏈（`InputHandler_TriageInput` 之 `handlePunctuation`）。**純拼音狂打（`typingMode == .pinyinFuriousTyping`）同病同治**——病灶住兩家族共用之打字機鏈路，雙拼非專屬；迴歸用例 `IH-Dualpin-013`、`IH-FuriousPinyin-016`。診斷法：把 `errorCallback` 暫時轉印至 stdout，吞鍵之真因即現形（LM 是否收 `_punctuation_N` 可先以此排除辭典之嫌）。
- **★ 雙拼之退格粒度＝「碼所譯出之整個音節」；狂打之 copilot 窗於首鍵即出（2026-10-13／2026-10-14，P302 Amendment；事主 m05250 第②③點、m07306，判準見 m05682）**：①雙拼以「碼」為打字單位，而刪除鍵原循常規流程逐字母刪組音區之拼音，留下不合任何碼之半截讀音（既不成碼、亦難查詞）⇒ `DualpinTypewriter` 於「待配首鍵」分支之後另接一臂：`if input.isBackSpace, !handler.composer.isEmpty { composer.clear() ; dualpinDiscardTranslatedReading() ; switchState(...) ; return true }`；新助手 `InputHandler_DualpinConfig.dualpinDiscardTranslatedReading()` 須呼 `DualpinTranslator.resetAll()`（兼清 `pendingFirstKey` **與** `siblingStems`）——重碼詞幹係「併走即消耗」之材料，音節既撤即須同去，否則錯配於下一音節。②copilot 窗（狂打側）原只由組音區之拼音反推讀音桶，而首鍵未成碼時組音區尚空 ⇒ 窗不成立；今新增 `DualpinTranslator.stemsStarting(with:)`（以該鍵為首之諸碼所譯諸詞幹）與 `dualpinPendingPrefixReadingKeys()`（展為無調注音、去重），令 `InputHandler_HandleStates.furiousFrontContext` 於組音區空時改取此前綴桶。③**首鍵即「未完成之讀音」**（2026-10-14 事主 m07651 裁定：雙拼之音節恆為兩鍵，半截之碼即待確認之讀音）——`furiousFrontUnfinishedReading` 之 `.DualPin` 臂於組音區空時改回 `dualpinPendingDisplayText`（素材住翻譯狀態機），`hasFuriousFrontPending` 與 `isFuriousCopilotCandidateWindowVisible` 於該拍即真、窗頂 pane 由 `dualpinPendingFirstKeyPaneText` 供給（＝「首鍵 → 該鍵於**首鍵之位**之意義」，依事主 m08259、m08553 之裁定；`DualpinParser.meanings(ofKey:)` 取聲母、零聲母鍵示 `∅`；前綴窮舉與次鍵之韻母皆撤，詞幹仍歸桶用），`InputSession.unfinishedReading`（連同測試之 `MockSession` 鏡像）遂復歸單一來源；Shift＋選字鍵亦可提前選字——判準抽為 `handleFuriousShiftCandidateSelectionIfNeeded` 供 `BPMFFullMatchTypewriter` 與 `DualpinTypewriter` 共用（雙拼之鍵逕交後者，前者之同名前置判斷於該路徑不復見，否則 Shift+1 落為「！」）。**惟該拍之固化一律讓位**：`solidifyFuriousFrontReading()` 於 `.DualPin` 且組音區空時回 `false`（半截之碼不成音節，其桶含該鍵所能開啟之全部詞幹之全部讀音、數百鍵，逕插將令同一音節重複入庫），`BPMFFullMatchTypewriter` 之 Enter 分支於固化不成時不再吞鍵；選字成功時 `confirmFuriousFrontCandidate()` 以 `dualpinFlushPending()` 消費待配首鍵。迴歸用例 `IH-Dualpin-014`／`015`（pane 與判準）、`016`（首鍵之 Shift 選字與首鍵之消耗）。
