- **腳本內的全形字元陷阱（2026-09-13 實錄）**：本工作區的 shell 常以 `LC_ALL=C` 執行，此時 bash 會把緊接在全形字元（如 `（`）之前的高位元組**一併視為變數名的一部分**——`log "…：$scheme（Debug）…"` 會以 `scheme\xef…: 未綁定的變數` 失敗（在 `set -u` 下直接中止腳本，且若已把 stderr 重導就完全看不出原因）。**凡變數緊鄰 CJK／全形字元者，一律寫成 `${var}`。** 同源的坑：Python `re` 的 `\b` 視中日韓字元為 word character，故 `\bTypewriter\b` 不會命中 `Typewriter的`（見 `DevReqsHistory.md` Phase 201 的〈方法學教訓〉）；腳本化取代 CJK 文本時請改用 `(?<![A-Za-z0-9_])`／`(?![A-Za-z0-9_])` 這類斷言。
- **跨平台 manifest 的 `platforms:` 陷阱（2026-09-14 實錄）**：`Package(platforms:)` 之參數型別是 **`[SupportedPlatform]?`**，故 **`platforms: []` 會讓 SwiftPM 報 `supported platforms can't be empty`**（Linux／Windows CI 當場炸），正解是 **`platforms: nil`**（＝不宣告平台限制）。要條件編譯分流者，須把變數宣告為 **optional**：`#if canImport(Darwin) let p: [SupportedPlatform]? = [.macOS(.v12)] #else let p: [SupportedPlatform]? = nil #endif`。**此誤在本機（Darwin）永遠測不出來**——務必以「把 `canImport(Darwin)` 反轉為假」的 scratch 套件預驗（見 `_MainWorkspace/tmp/p215LinuxSim` 之做法），或直接等 CI。
- 如果事主丟給您 Xcode Instruments Profile 檔案的話，可能會是二進位檔案，請先嘗試用 `xctrace export` 解讀成 XML 再分析。
- **★ 回歸測試用例之輸入域必須自資料導出，不得由測試自建（2026-09-26，P261 實錄；CI 追補三輪之根因）**：測試自建之鍵域一旦含「非按鍵」（如反引號、空格——素材檔內它們只作「本排列無此鍵」之標記），即等於**把無定義之行為當成規格來測**——此為「**測試綠而 CI 紅**」之典型：缺陷在**測什麼**，不在**測得對不對**。**配套兩則**：**(a)** 語料類測試用例須能分辨「**沒讀到**」與「**讀到了但濾掉幾列**」——只寫下界魔數會使兩者同形，應同時曝露原始列數與過濾後列數；**(b)** 大型靜態初始值之複雜推導會撞編譯器（`compactMap` 閉包配切片令 swift-frontend 6.4 於 `TypeCheckPrimaryFileRequest` 崩潰），宜預先拆解為帶型別標註之樸素迴圈。
- **★ 變異測試是判準類測試用例之驗收手段（2026-09-26，P257 實錄）**：凡改動「偏好 → 旗標 → 查詢」之推導，**先以舊實作跑一次新測試用例並確認其轉紅**——否則測試用例可能只打到下游（直接驅動 config 之測試用例驗不到推導式）。實錄：P257 之兩支新測試用例在舊實作下轉紅 4 處與 2 處，而兩支直接驅動 config 之既有測試用例照舊通過。
- **★ 測偏好之測試用例須自備隔離容器，且不可只清輸入鍵（2026-09-26，P253／P257 實錄）**：以 `UserDefaults.unitTests = .init(suiteName:)` ＋ `pendingUnitTests = true` ＋ `UserDef.resetAll()` 起手，事後還原並 `removeSuite`；`@AppProperty` 之 get／set **逐次**讀寫 `UserDefaults.current`（容器一切換即生效、無快取）。**★ 清鍵時連輸出鍵一併清**——P253 之初稿未清 `candidateStateJKHLBehavior` 等輸出鍵，遭跨 suite 汙染而使整段被**靜默略過**（單獨跑綠、全倉跑紅）。**兩顆 `swift test` 不得並行**（同源：同一行程內之跨 suite 偏好汙染）。**（P266 補）** 並行之害不限於同倉：兩倉同時各跑一套全倉測試時，`test_IH400` 曾出現 2 處假紅（單跑與其後之乾淨複跑皆綠）⇒ 交差前之最終驗證須獨占機器。**（P314 起之現行形）** 本條所載之 `UserDefaults.unitTests`／`pendingUnitTests`／`removeSuite` 三件已不存在，改以 `OSUtils.defaultsStore = InMemoryDefaultsStore()` ＋ `OSUtils.isRunningUnitTests = true` 起手（見本卷末條）；「不可只清輸入鍵」之教訓不變——`InMemoryDefaultsStore` 係**空容器**，故連輸出鍵亦無從殘留。
- **★ 兩倉同源之子套件：byte-sync 成立即無須重複確認 CI（2026-09-28，事主明示；同日補條件）**：`vChewing-macOS` 之 `Packages/vChewing_OSNeutral_LibVanguard` 與 `vChewing-LibVanguard` 逐位元組同源（`Sources`／`Tests` 逐檔 SHA-256 全同）⇒ 其 CI 只需在 `LibVanguard` 側成立、macOS 側以 byte-sync 為憑；**惟 macOS 倉之改動若超出該子套件及其 internal deps，仍須於 macOS 側確認 CI**。
- **★ 有副作用之輔助函式不得寫進 `#expect` 之運算式（2026-09-28，P263 實錄）**：Swift Testing 於失敗診斷時會**二次求值**該運算式——IH171 首遍得窗、次遍得空窗（打字與切環境被執行兩遍），遂誤報失敗。凡打鍵／切環境／寫入狀態者，一律先取值再斷言。

- **★ iconv 之鏈接處置因平台而異（2026-10-06，P289 追記）**：Apple 平台之 `libiconv` 是**獨立 dylib** ⇒ manifest 須明列 `.linkedLibrary("iconv", …)`；glibc／musl 則把 `iconv_open`／`iconv`／`iconv_close` **收在 libc 內**（glibc 之轉換表另以 gconv 模組隨 libc6 供貨）⇒ **Linux 無須任何鏈接設定**；Windows 無 iconv，`CodePointDecoder` 走 `MultiByteToWideChar`（碼頁 54936／936／950）。`IH-InputMode-001`（餵 GB18030 之 `C8D0` 與 Big5 之 `A462`、皆期得「刃」）即 Linux CI 上實際走 iconv 之路徑。**musl（靜態 Linux SDK）之字集覆蓋較窄、若干東亞編碼缺失**，該側之 GB／Big5 解碼可能落回 `nil`（CI 為 glibc、未涵蓋此路）。
- **★ 共用層（`Sources/Shared`）之改動須兩倉同源、逐位元組相同（2026-10-11，P299 補記）**：`UserDef`／`PrefMgrProtocol`／`PrefMgr_Core` 三檔同時存在於正本 `vChewing-LibVanguard` 與消費側 `vChewing-macOS/Packages/vChewing_OSNeutral_LibVanguard`（「各自獨立、同源」之兩份副本）——任改一側後須 `diff -q` 逐檔複核、並於另一倉補一筆同源 commit（P299：`b8bdbf2b` ↔ `e9759a8a`）。**漏改一側不會有任何建置或測試徵兆**（macOS 側照樣全綠），唯賴顯式比對。
- **★ PKG 安裝路徑與 App 安裝器同罪；換檔後之保證刀須以 console user 為界（2026-10-11，P300）**：Homebrew 係以 `pkg` 安裝唯音（`vChewing-Homebrew/Casks/vchewing.rb`），故 PKG 之 `postinstall` 以 **root** 執行；而 payload 抽取發生於 `preinstall` 與 `postinstall` 之間 ⇒ 保證刀須落 `pkgPostInstall.sh` 之 chown 段之後、`TextInputMenuAgent` 之終止與 `…/MacOS/vChewing install` 註冊之前，並以 `ps -o user= -p` 過濾至 `${login_user}`（`/usr/bin/stat -f%Su /dev/console`），否則會動到同一機器上其他已登入使用者之實例。捕捉＝`pgrep -x <名>`（與 `killall` 同認 comm，故自 `*.appTrashed` 舊 bundle 啟動之實例亦在內）∪ `pgrep -f "Contents/MacOS/<名>"`（補 comm 被截斷或改過者）；日誌 `Terminate: reason=postSwap captured=[…] escalated=… result=… surviving=[…]` 與 P298 之 Swift 側逐字同型（shell 側無 `launchFailed` 一詞）。**附帶訂正**：P298 所記「`pgrep -x` 只認 `MAXCOMLEN`（16 位元組）以內之程序名」在本機 macOS 27 **不成立**——19 字元名之 stub 以 `pgrep -x <全名>` 命中；反之 `exec -a` 改過之 comm 於 `ps -o comm=` 顯示為截斷之 15 字元，該情形由 `-f` 路徑補位。
- **★ 單元測試不得並行跑兩支 `swift test` 行程（2026-10-14，P302 實錄）**：兩倉之測試共用同一份 `UserDefaults`／語彙／POM 落盤狀態 ⇒ 並行執行（即使分屬不同倉）會互相踩踏，症狀是「先前全綠之雙拼用例成批失敗」（`dualpinPendingDisplayText` 忽為 nil、`composer.romajiBuffer` 不符）；逐一序列執行即復綠。驗證改動時，跨倉之測試一律排隊。
