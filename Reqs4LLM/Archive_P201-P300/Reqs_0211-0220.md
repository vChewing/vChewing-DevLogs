### 附記：LibVanguard 之 `percept` 私有輔助不移植之決策

事主就〈落點〉（三）反問「LV 的 `percept` 輔助值得搬嗎，還是完全沒價值」，經逐條查核後**裁定為不移植**。它並非「完全沒價值」，而是在 macOS 這一側其價值被稀釋至零：

1. **零行為**：純轉發，不含斷言、不含預設時間戳、不含 fixture 組裝——只是把一個 tuple 參數拆成具名參數。
2. **省不了字**：`percept(who: pom, key: k, candidate: c, timestamp: t)` 共 74 字元，對照直呼 `pom.memorizePerception((ngramKey: k, candidate: c), timestamp: t)` 為 82 字元，差距在雜訊水準。
3. **反而藏起被測 API 的名字**：macOS 測試端對 `memorizePerception` 有 **93 個直呼點**（9 個 POM 測試檔 ＋ InputHandler 測試）；測試檔內直呼生產符號本身即契約文件。遷入別名會使 LV 側那 21 個注入點自 grep 視野消失。
4. **該輔助是 LV 自身標籤 sprawl 的副產品，且 LV 自己並未統一**：同一個 `Sources/_Modules/LexiconKit/LX_Components/LX_SubLMs/LX_Perceptor.swift` 內，`ngramKey` 見於 `:135`／`:208`／`:216`／`:220`，唯有「注入」重載用冗長的 `contextualizedGramKey`（`:170` 的 `(contextualizedGramKey:candidate:)`；`:197` 另有一個吃 `Homa.PerceptionIntel` 的重載）。而 **macOS 側根本沒有這個 tuple 標籤**：macOS 的 `memorizePerception` 簽名為 `(ngramKey: String, candidate: String), timestamp:, saveCallback: = nil`（`LXPerceptor.swift:663`）；macOS 的 `contextualizedGramKey` 是 `Homa.GramInPath` 的屬性（`Homa/Homa_BasicTypes/Homa_GramInPath.swift:75`），與此無關。故該輔助存在的唯一理由，在 macOS 不存在。
5. **慣例一致性**：macOS 為 93 個直呼點的統一慣例，單檔冒出 21 個別名呼叫會淪為孤兒慣例。

**判準（日後何時這類輔助才值得存在）**：

- 會**斷言**的輔助——注入後立刻 `#expect(pom.mutLRUMap[key] != nil)`，把「靜默空轉的注入」變成紅燈。但這會改動 93 個呼叫點的語意，屬刻意決定而非移植。
- 帶**預設時間戳**的輔助——但 macOS 的 POM 測試刻意逐案給不同時間戳（觀測窗衰減是該族主軸），預設值只會招來複製貼上錯誤。
- **fixture 級**輔助——macOS 已在更高層以 `TestLX(rawData:)` 處理；反向而言，LV 專屬的 `LXTests4TrieHub` 才是真正值得一看的那個。

**附帶結論**：日後若將 LV 的 POM 測試族整體收斂進 macOS（方向仍以 macOS 為正本），搬運時應拆掉 `percept` 包裝、一律直呼 `memorizePerception`。

### 一、`LexiconGramSupplierProtocol`（新檔 `Sources/LexiconAssembly/LexiconGramSupplier.swift`）

三項要求與 LibVanguard 逐一對應：`hasGrams(_:filterType:partiallyMatch:partiallyMatchedKeysHandler:)`、`queryGrams(_:filterType:partiallyMatch:partiallyMatchedKeysPostHandler:)`、`queryAssociatedPhrasesAsGrams(_:anterior:filterType:)`。另含 LibVanguard 的三組預設參數擴充與 `queryAssociatedPhrasesPlain(_:anterior:filterType:)`（僅容器由 `VanguardTrie.TrieGram` 換成 `Homa.Gram`，演算法逐行照搬，含「只能用基於 String 的 Hash」那句註解的成因）。協定保留 `AnyObject` 約束：來源是以**參照**被掛載、而非被複製。另補一個橋接建構子 `Homa.Gram.init(_ trieGram: VanguardTrie.TrieGram)`——LibVanguard 側因 `HomaGram` 與 `TrieGram` 本是同一型別而無此需求，OSNA 側的 `Homa.Gram` 是獨立型別。

### 二、`GramConcatFlags` 與合流 API（新檔 `Sources/LexiconAssembly/LX_GramConcatAPI.swift`）

- `LXAssembly.GramConcatFlags`（`OptionSet, Codable, Hashable, Sendable`）：`.sort`／`.deduplicate`／`.all`。**空集合即「原樣串接」**——依來源掛載順序保留所有結果（含重複），完全不動次序。
- `concatGramAvailabilityCheckResults(@ArrayBuilder<Bool?>:)`：任一來源在庫即在庫；`nil` 視為未表態。
- `concatGramQueryResults(flags:forbiddenKeyValueHashes:grams:)`：`nil` 來源略過 → 可選排序 →（`forbiddenKeyValueHashes` 非空時改以該集合作為唯一過濾依據、**不再另行去重**）否則可選依身分雜湊去重、保留最先出現者；全空回 `nil`。結果建構子用既有的 `SwiftExtension.ArrayBuilder`。
- `sortGrams(_:_:)`：**幅長降冪 → 讀音索引鍵字面升冪 → 權重降冪**（LibVanguard 原政策，刻意與 `Homa.Assembler.sortGram` 的「權重優先」不同；程式碼內已註明此差異，以免日後被當成 bug 修掉）。
- `makeGramIdentityHash(_:)`／`makeGramIdentityHash(keyArray:value:previous:)`：身分＝讀音索引鍵 ＋ 詞值 ＋ 前驗詞值，**刻意不含 `anterior` 與權重**（與 LibVanguard 逐欄一致；權重不屬身分、故同讀音同詞值不同權重者視為同一筆）。

### 三、`LXGramSupplyHub` 與 `LXFactoryGramSupplier`（新檔 `Sources/LexiconAssembly/LXGramSupplyHub.swift`）

- `LXAssembly.LXGramSupplyHub: LexiconGramSupplierProtocol`——多來源元圖供應中樞，對應 LibVanguard `TrieHub` 的角色：`mount(_:)`／`unmountAll()`／`mountedSuppliers`／`concatFlags`，並自帶 `generation` 計數器（掛載異動時遞增，供 `LXFacade` 的查詢快取指紋使用）。`hasGrams` 走「任一來源在庫即在庫」；`queryGrams`／`queryAssociatedPhrasesAsGrams` 走 `concatGramQueryResults`，兩個通道的 `partiallyMatchedKeys` 一律於 `defer` 中回報（聚合後去重，故即使來源各自回報重疊鍵亦不重複）。空掛載時三個入口皆短路。
- `LXAssembly.LXFactoryGramSupplier: LexiconGramSupplierProtocol`——把原廠辭典後端包成可掛載來源，**每次查詢即時向 `LXFacade.factoryTrie` 取值**，故原廠辭典重新連接或卸載後無須重新掛載；供應的是未經後處理的原始元圖（不施假名抑制、不補半形變體、不改權重正負號）。程式碼內以 `<warning>` 明示：若把它掛進 `LXFacade`，同一批原廠資料會與內建原廠查詢路徑重複供應。

### 四、`LXFacade` 的掛載接點（新檔 `Sources/LexiconAssembly/LXFacade_GramSupplierMounting.swift` ＋ `LXFacade.swift` 六處）

- `LXFacade` 新增 `let gramSupplyHub = LXGramSupplyHub()`（internal），對外暴露 `mountedGramSuppliers`／`mountGramSupplier(_:)`／`unmountAllGramSuppliers()`；`LXQuerier`（唯一公開查詢面）同步轉發三者。
- **接進生產管線**：`unigramsFor(keyArray:partiallyMatch:)` 與 `unigramsForWithAlternatives(...)` 各在「原廠辭典那一區塊的最末」追加 `rawAllUnigrams += mountedSupplierGrams(...)`（替代讀音路徑以 `"&"` 連讀鍵詢問，與原廠辭典的 chopped 路徑一致）；`hasUnigramsForFast(keyArray:)` 在同一個 cassette 條件守衛內追加 `mountedSuppliersHasGrams(...)`。**最後一項是必要的、不是錦上添花**：`Homa.Assembler` 以 `hasGrams` 判定讀音是否合法，若輕量版在庫檢查不認得掛載來源，該來源的元圖永遠不會被查詢到。
- **快取指紋**：兩條 `unigramsFor` 路徑的 `Hasher` 皆追加 `hasher.combine(gramSupplyHub.generation)`。這使掛載／卸載自動令 LRU 快取失效，也讓「空掛載」時該分量恆為常數——即**預設零行為變更**。

## 附註

- **與 LibVanguard 的刻意差異（四條）**：① 落點在 `LXAssembly` 命名空間內（LibVanguard 為 `Lexicon` 頂層）；② 元圖型別為 `Homa.Gram`（欄位 `current`／`probability`）而非 `Lexicon.HomaGram`；③ `makeGramIdentityHash` 於 OSNA 為 `public`（使用 `forbiddenKeyValueHashes` 的宿主必須能算出同一雜湊），LibVanguard 為 `private`；④ 另加 `Homa.Gram.init(_ trieGram:)` 橋接。
- **未讓 `LXFacade` 自身 conform**：本可如此（它是 OSNA 側 `TrieHub` 的對位物），但其查詢是「已過濾除表／語彙置換／POM／排序」的後處理結果，且 `filterType` 對它無意義、關聯詞語只有詞值無讀音鍵——硬套會做出一個語義不精確的 conformance。故 `LXFacade` 只當**掛載端**，來源則由 hub 與宿主自訂型別擔任。
- **未讓子語言模組 conform**：`LXCoreEX`／`LXCassette`／`LXAssociates` 在 OSNA 皆為**值型別**（struct），以參照掛載會整份複製且語義會走樣（LibVanguard 側的 `LXPlainBPMF` 等為 `final class`）。它們的內容仍由 `LXFacade` 就地供給。
- **待裁**：`concatGramQueryResults` 的排序政策目前是 LibVanguard 政策（幅長→字面→權重），與 `Homa.Assembler` 的權重優先政策並存；若日後要把 OSNA 既有的多來源區塊（`unigramsFor` 內十餘處 `+=`、`abbreviatedWordCandidates` 的雙來源合流）也收斂進這個 API，須先裁定採用哪一套排序政策——這兩處現行的「分區優先 ＋ 依詞值去重」語義與本 API 的「依身分去重」不同，直接套用會改變候選次序，故本 phase 未動。
- **兩倉關係**：macOS 版是正本，legacy 版是減去模組 import 與 `nonisolated` 的同構副本；改動 macOS 側之後須照〈五〉的機械規則同步（反之不成立）。legacy 依慣例不承擔單元測試，故本 phase 的 20 項測試只在 macOS 側。
- 全 phase 落點皆未動 `Homa`、`TrieKit` 與 `vChewing-LibVanguard`。
