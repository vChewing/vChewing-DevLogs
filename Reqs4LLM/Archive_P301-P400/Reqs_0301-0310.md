## 落點與理由

- **模組**：`Arimitsu` 係 `LibVanguard` 之直屬 SubTarget（`Sources/LibVanguard/Arimitsu/`；父 target `exclude: ["Arimitsu"]`、兩份 manifest 皆增列）⇒ `mapHanyuPinyin` 等 internal 不可直讀，Tekkon 曝露純值公開 API `allHanyuPinyinStems`（426 條、升冪）供取，`mapZhuyinPinyin!.keys` 作交叉核對；Arimitsu 反向依賴 Tekkon、Tekkon **不**逆依賴；測試另立 `Tests/LibVanguardTests/Arimitsu/`，`DefaultIsolation` 暫定 `MainActor`（目的：Tekkon 改動量最小化）。`DualpinParser` 為 **struct**（載入／檢證／編解碼）。
- **身分與持久化**：`rawID` ＝ **DNS 名**（內建 `dualPin.Microsoft`／`dualPin.GBT17`；空／非 DNS 形／相衝 ⇒ E9）；`UserDefaults` **僅承載一筆**（自備存 JSON、原廠僅存 `rawID`）。**標題自持**：`rawTitle` ＋ `localizedTitle`（五級 fallback＝精確 → 去區域 → 語言主標籤 → `en` → `rawTitle`），以 `title(forLocaleTag:)` 作字串比對、不引 `Locale`。
- **校驗五條**：①每條詞幹皆可得碼（`eh` 等 **DIPE**〔漢拼有、雙拼無〕靜默忽略，不列 E／W）；②碼長**恆 2**，碼長宣告或 `overrides` 非二鍵 ⇒ **E8 拒收整份**；③**重碼不得列為 ERROR**（實測 GB/T 5 組、微軟 3 組；裁定權在 `Homa` 之 DP 與語言模型）；④`autochopPolicy` 非 `.disabled` ⇒ **W7**、不拒收、以 `.disabled` 運行並明示不支援，**不得靜默降級**；⑤身分見上。
- **內建兩案**：微軟雙拼（Rime `double_pinyin_mspy.schema.yaml`；27 鍵含 `;`、零聲母 `o`，11 條 `ing` 系音節用 `;`）與 GB/T 34947-2017（以 zh.wikipedia「雙拼」條目與 `macroxue/shuangpin` 之 `evaluator.js` 兩獨立來源覆核）。微軟之規則係對**拼音拼寫**作尾綴改寫，**不得**作音位正規化（j/q/x 後之 `u` 保持 u 鍵）。**考場一致性**：中國內地電腦化公共考試只准微軟雙拼、禁改設置（考場預裝 2007 版谷歌拼音）⇒ 內建微軟表須與該方案逐條等同、行為亦等同（不 autochop、不打聲調），P302 須含考場側樣本交叉驗證。
- **autochop 明文不做**：三家切、微軟與谷歌不切 ⇒ 係選配而非共通義務；考場不切，唯音自作聰明反致肌肉記憶失配 ⇒ 預設 `.disabled`（不回溯、不猜；未成碼之鍵序不進組音區，免複現 `q → ㄑ`），本版只實作該 case。
- **保留鍵之攔截**升格為 schema 欄位 `keyInterception`（`.none`／`.explicit`／`.schemeAlphabet`）：按鍵碼經 Apple SDK 覆核——`;` 係 41、符號選單鍵係**波浪符號鍵**（非 `;`）⇒ `;` 必抵 `handleComposition`（`TriageInput.swift:95` 無其 case）⇒ 內建路線於 triage 層**零改動**；唯 schema 用波浪符號鍵等保留鍵時，才須於 `:144` 前諮詢 Arimitsu。
- **接入點**＝打字機側之**前控式套接**：`DualpinTypewriter` 只認雙拼（認鍵、維持 pending、碼完成時 `replacePinyinBuffer`），餘鍵逕回 `BPMFFullMatchTypewriter`（先例 `Typewriter_MixedAlphanumerical.swift:24-28`）⇒ 雙拼狂打因組音區交回拼音路徑而**自動承襲拼音狂打之諸義**；切割由翻譯器給出（碼長 2 ⇒ O(1)、不需 trie，**不倚賴** `pinyinAutoChopResult`）。因 `MandarinParser` 恆為 `.ofHanyuPinyin`，分派於 `handleComposition` 之 `switch typingMode` 增 **`.DualPin`** case＋生效閘（schema 可用 ∧ 非磁帶 ∧ 非 SCPC）；**無效兩鍵序 ⇒ Beep ＋ Drop**（兩鍵皆丟、不進組字區、不落字面；響鈴由打字機側 `SessionHost.shared.soundBuzz()`，Arimitsu 本身不發聲）。
- **否決**：亂序雙拼（係漢拼之二次編碼，鍵入順序仍按聲介韻調；Rime 作者佛振語，算術旁證見驗證表）；趙元任國語羅馬字（聲調入拼寫，不容）；令 Tekkon 反向依賴 Arimitsu。
- **P302 之施工序**：手術範圍限 `vChewing-LibVanguard`；Tekkon 之改動（`allHanyuPinyinStems`）須**獨立先行一筆** commit（`Tekkon // <Member>: <What>.`），其後才是其餘。小鶴雙拼自此不在未裁定之列（事主明示「先不討論」）。

## 要解決的問題

- 雙拼鍵位是**鍵盤字母**而非音位，而 `Tekkon.Composer` 只認完整漢拼 ⇒ 須一座翻譯官把兩鍵序譯成詞幹、再經 `replacePinyinBuffer(with:)` 進場。
- 426 條詞幹之可得性須可稽核，而 `mapHanyuPinyin` 係 internal；兩條公開繞道皆為陷阱（`ofHanyuPinyin.mapZhuyinPinyin!` 之鍵值方向與名相反、`SyllableIndex.allReadings` 係**注音**）。
- 拼音側（含雙拼）無中英混打回退 ⇒ 無效鍵序不得洩為原文 ASCII，只能 Beep＋Drop。

## 落點與理由

- **A 先行、獨立一筆**（P301 之施工序）：Tekkon 只增一件投影式存取器（`mapHanyuPinyin.keys.sorted()`）、不動表本身；Arimitsu 反向依賴 Tekkon、Tekkon 不逆依賴。
- **架構**：`Arimitsu`（其名係漢語拼音發明人周有光之「有光」日文漢字音讀）係 `LibVanguard` 之直屬 SubTarget（`path: "Sources/LibVanguard/Arimitsu"`、deps 僅 `Tekkon`），父 target 以 `exclude: ["Arimitsu"]` 排除、產品 `Vanguard` 收之；OS 中立、永不發聲——無效之鍵序由型別器經 `errorCallback` 上報。
- **`.DualPin` 之分派與狀態機**：首鍵**只顯示**、不入組字區（pending 首鍵計為組字材料，session 故不再中止並清空）；次鍵把詞幹寫入 Composer，**其固化時機隨狂打開關而異**——狂打側續留組音區（供自動套用、重切分與 copilot 取用），非狂打側於次鍵當下逕行固化；不成序則丟棄＋Beep；待配首鍵遇刪除鍵則就地撤銷、不落常規刪除路徑。同碼兄弟讀音隨譯碼器同行，於音節定型之兩處併入讀音鍵查詢。組字區語義仍係**漢語拼音**，`;` 仍為結束鍵（triage 零改動）。

- 病灶：`replayJournal` 把已驗證之日誌記錄累積進 `[String: KeyPerceptionPair]`，其中 `removeKey` 寫作 `tempMap[key] = nil`。字典無從區分「未提及此鍵」與「此鍵已移除」，故 `replayApplicator`（走訪該映射）對移除一無所見——快照裡已載入的鍵，於任何想刪它的日誌記錄之下皆倖存。`clear` 同理只清得掉「本批累積」、清不掉快照內容。後果：bleach 掉或逐出掉的鍵，於下次啟動復活。
- 附帶病灶（由本 phase 新加之測試揪出）：`markKeyForRemoval` 沿用 `markKeyForUpsert` 的 2 秒 per-key 節流，且在窗內**直接丟棄該移除**。節流一個 upsert 不失資料（其值於落盤時自現行映射讀取）；節流一個移除則讓該鍵留在快照或已寫入之日誌記錄裡——即上述症狀本身。
- 根因（一行）：移除與清空皆無從表達於「鍵值映射」此一載體，且標記層又會靜默丟棄移除。

## 落點與理由

- **新增巢狀 `enum JournalChange { case clear; case upsert(KeyPerceptionPair); case remove(key: String) }`**，`replayApplicator` 改收 `([JournalChange]) -> ()`：以**有序陣列**承載變化，序即日誌序（跨批次時，同一鍵之 upsert 與 remove 唯在序中才有意義）；`remove` 為獨立選項，方能區分「未提及」與「已移除」。
- **刪去 `inout Bool mutated` 出參**：原碼寫之而無人讀取；非空陣列即等義。
- **`clear` 之處置**：清空使其前之變化全數失效，故逕行 `changes.removeAll()`；但清空本身必須交付，否則清不掉快照既有內容（此即舊碼之失）。
- **`LXPerceptor.loadData(fromURL:)`**：於同一把自有鎖內逐筆套用（`.clear` → `mutLRUMap.removeAll()`；`.upsert` → 賦值；`.remove` → `removeValue(forKey:)`），其後照舊 `resetLRUList()` ＋ `enforceCapacity()`——P305 所立之容量不變量仍由該兩處維持。持鎖紀律不變：套用仍在鎖內，持久化層之葉鎖仍於回呼前放掉（`POMLockDisciplineTests` 之斷言照舊全綠）。
- **`markKeyForRemoval` 不再受節流**：僅當該鍵之 upsert 尚未落盤（`pendingUpsertKeys.remove(key) != nil`）時相消而不記錄；其餘一律入列。`markKeyForUpsert` 之節流不動。
- **被否決**：改動 WAL／快照之檔格式（格式無恙，問題在記憶體側之語義）；把移除集合另以 `Set<String>` 出參（保留日誌序方為正解）；連 `markKeyForUpsert` 之節流一併移除（會使日誌量隨每次選字增長、徒增快照重寫頻率，且非本症所必需）。

## 已知界線

- 節流之殘餘界線（**非本 phase 引入**）：若某鍵之移除已落盤，而該鍵在 2 秒內又被重新記起，`markKeyForUpsert` 之節流會略過該次 upsert，該鍵於重啟後即依已落盤之移除而消失（原碼因移除根本不生效而無此現象）。實際觸發需「使用者刻意 bleach 一鍵後 2 秒內重打同一 n-gram 上下文並選同一候選」，或「逐出後 2 秒內重記同一鍵」——後者之鍵早非 LRU 尾端，故不另設機制；日後若要收，須為每鍵另記「最後落盤之操作種類」。
- `loadData` 之重播若因容量收斂而逐出鍵，其逐出標記會被 `replayJournal` 尾端之 pending 清理一併清掉，故快照仍可能留有已逐出之鍵。此不影響記憶體有界（載入後即再被逐出），僅令快照較實際需要者略大；要收須把「重播後之逐出」與「重播之 pending 清理」分開。

## 落點與理由

- **三處直接賦值者各補兩事**：`inputHandler?.clear()`（棄素材：組音器、組字器、狂拼 trail、雙拼待配首鍵；不碰閂滯旗標，與 `switchState` 同徑）與 `clearInlineDisplay()`（清客體組字區）；模式提示之賦值前加 `guard !state.hasComposition, … else { return }`（提示於啟用後 0.05 秒方行，其間可能已開始打字）。
- **捨「遞交」而取「丟棄」**：`performServerDeactivation()` 之語義係「離開客體，故遞交」，但快速路徑之重新啟用係同一客體之再一次「開始」；此刻遞交等於把未見之殘留（無讀音可解之數字）塞進客體，故逕棄。
- **被否決**：① `updateCompositionBufferDisplay()` 代 `clearInlineDisplay()`——連帶收起浮動組字窗，壞「模式提示避讓已顯之窗」（`SS-Lifecycle-010` 之 `shownPoint?.y == 124` 轉紅）。② `switchState(.ofEmpty())`——該臂對既有組字會**遞交**，即把殘留數字塞進客體。③ **雙拼層拒收待配首鍵期間之數字鍵**——曾實作後撤除：以 `9`（非聲調鍵）否證聲調鍵之說，且僅及數字、未及同族路徑，屬捨本逐末；此類數字仍循 P302 既有語義（首鍵逕捨、數字落為字面節、不示警），以 `IH-Dualpin-017` 釘住。
