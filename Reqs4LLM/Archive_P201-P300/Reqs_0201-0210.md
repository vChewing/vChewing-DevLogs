## 待定事項

**B｜`Typewriter` 的型別要不要一併改？** 依定案，`Typewriter` 只改 package／target 名，型別名不動。但該模組內仍有約 8 個含 "Typewriter" 的型別（`TypewriterProtocol`、`BPMFFullMatchTypewriter`、`MixedAlphanumericalTypewriter`、`CassetteTypewriter`、`RomanNumeralTypewriter`、`HaninSymbolTypewriter`、`CodePointTypewriter` 等）與函式 `handleTypewriterSCPCTasks`。結果會是「`OSNeutralAssembly` 模組內滿是 Typewriter」。若定案為「一併改」，本 phase 須連同這些型別、其檔名與測試一併處理；若定案為「接受現狀」，本 phase 到此為止。

### 〈待定 B〉定案（2026-09-13）

**接受現狀：`Typewriter` 系型別名一律不動。** 理由有三：

1. 事主的更名對照表已明文將 `Typewriter` 限定為「Swift Package 名稱與 Target 名稱，**不是** Struct / Class / Protocol Type 名稱」——此即定案本身，本 phase 只是確認而已。
2. 該型別群與 `handleTypewriterSCPCTasks` 的新名無任何既定方案；強行發明會引入未經裁定的命名（尤其 `TypewriterProtocol` 究竟該叫 `OSNeutralSessionProtocol` 還是別的，屬語意決策而非機械改名）。
3. 模組層與型別層的命名得以分離：`Sources/OSNeutralAssembly/Typewriter/` 子目錄與其檔名（`Typewriter_*.swift`、`TypewriterProtocol.swift`）一併保留，使「Typewriter」收斂為**該子系統的領域術語**（打字態械族）而非模組名。

故第 4 項驗收之「零殘留」以**排除該群**為條件成立。

## 要解決的問題與大概需求方向

## 背景（溯源結論）

安裝程式「偵測 App Translocation、等到舊 bundle 被系統釋放才安裝」這一條線，其來源是 OpenVanilla：`Source/Mac/Installer/AppDelegate.m`（Lukhnos Liu，2016-12-30，commit `db8548a6` "Handle Gatekeeper app translocation when upgrading"），後於 installer 的 Swift 化過程中被抽出為 `Source/Mac/Installer/BundleTranslocate.{h,m}`。唯音經上游 fork 承襲至今，落點為 `RelocationDetector.swift` 的 `Reloc.isAppBundleTranslocated`、`InstallerVMProtocol.swift` 的輪詢流程，以及 `kTranslocationRemoval*` / `shouldWaitForTranslocationRemoval` / `translocationTimer` 等識別子與常數值。**不保留出處聲明為本 phase 的目的之一**。

## 手術內容（定案：換策略，連偵測都不必）

### 一、安裝流程

現行：

```
killall → 掃描＋改名／trash 舊 bundle → 必要時 osascript 提權改名
        → if Reloc.isAppBundleTranslocated(舊 bundle) {
            亮面板，每 1 秒輪詢「是否已釋放」，最多 60 秒 → 才安裝
          } else { 立即 cp -R }
```

改為：

```
killall → 掃描＋改名／trash 舊 bundle → 必要時 osascript 提權改名
        → 立即嘗試安裝；失敗則亮面板並每 0.5 秒重試，直到成功或 60 秒逾時
```

「單次安裝嘗試」＝把原本的 `cp -R`（外部 `Process`）換成 Foundation：`FileManager.copyItem` 至**同目錄**的隱藏暫名 `.vChewingInstallStaging-<UUID>.app`，再 `moveItem` 就位。任一步拋錯即視為失敗。

之所以要暫名＋同卷宗搬移：

- 轉置映像為唯讀，寫入必然失敗，故「複製失敗」本身即為可靠的等待訊號——不需要知道「是否被轉置」。
- 同卷宗 `moveItem` 是原子搬移，且失敗時清掉暫存物即可，不會在重試之間留下半殘 bundle。
- 暫名以 `.` 起頭（隱藏），故不會被 `findAppBundlesWithSameConnectionName`（該函式帶 `skipsHiddenFiles`）誤認為已安裝的 bundle。

### 二、新流程

現行（改前）：

```
killall ×2 → 掃描＋改名／進垃圾桶 → 必要時 osascript 提權改名
          → if Reloc.isAppBundleTranslocated(舊 bundle) {
              亮面板，每 1 秒問一次「釋放了沒」，最多 60 秒 → 才安裝
            } else { 立即 cp -R }
```

改後：

```
killall ×2 → 掃描＋改名／進垃圾桶 → 必要時 osascript 提權改名
          → 立即嘗試安裝；失敗才亮面板並每 0.5 秒重試，直到成功或 60 秒逾時
```

「單次安裝嘗試」＝ `FileManager.copyItem` 至目標目錄內的隱藏暫名 `.vChewingInstallStaging-<UUID>.app`，再 `moveItem` 同卷宗原子就位；任一步拋錯即清掉暫存物並排定下一次。外部 `Process`（`/bin/cp`）與 `print(kDestinationPartial)` 一併移除。

之所以「複製失敗」即為可靠的等待訊號：Gatekeeper 的轉置映像是**唯讀**的磁碟映像，寫入該路徑必然失敗；不必先知道「是否被轉置」。附帶好處有三——(1) 涵蓋其他會鎖住目標路徑的暫時性原因（Spotlight 索引、防毒、殘留 agent）；(2) 多數使用者的常見路徑由「乾等最多 60 秒」變成近乎即時，只有真的卡住才亮面板；(3) 暫名以 `.` 起頭，故不會被 `findAppBundlesWithSameConnectionName`（帶 `skipsHiddenFiles`）誤認為已安裝的 bundle。

### 二、資源查找的去 bundle 化

新增 `SwiftExtension` 套件的 `ResourceLocator` target（`Sources/ResourceLocator/ResourceLocator.swift`）：以「不假設編譯產物必定身處於某個 bundle 內」為前提，**依序**嘗試候選位置，全部落空則回傳 `nil`、絕不 `fatalError`。

查找順序：手動指定（`specifyResourceBundleURL(_:forBundleNamed:)`／`resourceRootURL`）→ `Bundle.main.resourceURL` → `Bundle(for: anchor).resourceURL` → `Bundle.main.bundleURL` → 錨定型別所屬 bundle 之同層目錄 → **編譯產物所在目錄**（`dladdr(#dsohandle)` 取得當前 image 路徑，再取其上層與其 `Contents/Resources/`）。最後一項是本 phase 的關鍵：它讓「動態庫與資源 bundle 同層」這種不可能從宿主推得的佈局得以命中。

三處改動：

| 落點 | 改前 | 改後 |
|------|------|------|
| `BPMFVS.getBPMFVSDataURL()` | `Bundle.module.url(forResource:withExtension:)`（查找失敗即 `fatalError`） | `dataURLOverride ?? ResourceLocator.url(…)`，回傳 `URL?` |
| `Bundle.currentSPM`（`MainAssembly4Darwin`） | `static let … : Bundle`，找不到即 `fatalError` | `static var … : Bundle?`；**查找成功才快取**，失敗不快取，令宿主事後的手動指定仍然有效 |
| `Bundle.main.preferredLocalizations[0]` | 無保護 subscript | `.first ?? "en"` |

`BPMFVS` 另新增 `isDataTableLoaded`（查找結果是否已成功載入）與 `dataURLOverride`／`specifyDataURL(_:)`；`cachedLookupTable` 由 `let` 改為 `var` ＋ `loadLookupTable()`，故指定／清除指定後會即時重載，載入失敗時所有 `convert` 一律原樣回傳輸入值。

`Bundle.module` 自此於兩倉**生產碼零殘留**。惟仍有兩處刻意不動：`LexiconAssembly/Sources/LXAssemblyMaterials4Tests/TestData.swift`（測試材料靶、不在執行期閉包內）與 legacy `DictionaryData/`（pinned 的 VanguardLexicon submodule、建置期工具）。

### 三、OSNeutralAssembly 層級的資源指定介面

新增 `Sources/OSNeutralAssembly/ResourceProvision.swift`（`public enum ResourceProvision`），把各依賴自身的資源指定 API 統一轉曝露，宿主只需認識本套件：

| API | 作用 |
|-----|------|
| `specifyResourceRoot(_:)` | 全域資源根目錄，所有資源 bundle 優先在此尋找 |
| `specifyResourceBundle(_:forBundleNamed:)` | 為具名資源 bundle 手動指定位置（bundle 本身或其所在目錄皆可） |
| `specifyBPMFVSTable(_:)` | 轉發 `BPMFVS.specifyDataURL(_:)` |

### 追加檢證之二（同日）：Xcode 產物與 make 產物共用 `Build/Products` 的互刪問題（已修）

**症狀**：`make debug`／`make release` 會把 Xcode 放在 `Build/Products/<Config>/` 的產物整批刪掉。

**實測（修前）**：`Build/Products/Debug` 內先有 Xcode 的 72 個 `.o`／`.swiftmodule` 與 2 個 `.app.dSYM`；跑一次 `make debug` 之後全部歸零，只剩插件自己的兩個 `.app`。

**根因（不在倉庫內）**：`Plugins/BundleApps/plugin.swift` 開頭以 `try? fm.removeItem(at: outputDir)` 清空整個 `Build/Products/<Config>`；而本機 Xcode 的**全域**偏好把 Xcode 的 `SYMROOT`／`OBJROOT` 指到同一棵樹：

```
IDEBuildLocationStyle           = Custom
IDECustomBuildLocationType      = RelativeToWorkspace
IDECustomBuildProductsPath      = "Build/Products"
IDECustomBuildIntermediatesPath = "Build/Intermediates.noindex"
```

倉庫內無任何一處設定此二者（`grep` ＋ `plutil` 皆證）；`xcodebuild -showBuildSettings` 在**不帶** `-derivedDataPath` 時亦回報 `SYMROOT = <repo>/Build/Products`，即該全域偏好對本專案生效。

**試過但無效／不可行的兩條路（留給後人省時間）**：

1. `vChewing.xcodeproj/project.xcworkspace/xcshareddata/WorkspaceSettings.xcsettings`（`BuildLocationStyle` 取 `UseCustomLocation` 或 `Custom`、`CustomBuildProductsPath = Build/Xcode/Products`、`CustomBuildIntermediatesPath = Build/Xcode/Intermediates.noindex`）：**`xcodebuild` 完全不採納**——`-showBuildSettings` 的 `SYMROOT` 兩種寫法下都一動不動。該檔已刪除（不留一個「宣稱了卻沒生效」的設定檔）。
2. 專案層級 build setting `SYMROOT`／`OBJROOT`：**會讓 Xcode 退回 legacy 佈局、使 SPM 整組失效**——實測 `xcodebuild -showBuildSettings` 直接報 `Packages are not supported when using legacy build locations, but the current project has them enabled.`，所有本地套件解析為 `(null)`。已撤回（`git diff` 為空）。

**修法（只動插件、最小面）**：不再清空整個目錄，改為只刪自己擁有的兩個產物：

```swift

let vChewingApp = outputDir.appending(path: "vChewing.app")
let installerApp = outputDir.appending(path: "vChewingInstaller.app")

```

**驗證（修後，實測）**：

|---|---|---|---|

插件自有產物仍正常刷新（`vChewing.app` 的 mtime 由 1789304232 → 1789304237），`make release` 亦照常產出 `Build/Products/Release/{vChewing,vChewingInstaller}.app`（該處 dylib 數仍為 0）。`make lintFormatUncommitted` rc=0，format 後重跑 `swift build` 與 `make release` 皆過。
