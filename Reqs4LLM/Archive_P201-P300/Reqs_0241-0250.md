## 一、Swift 側：`dump-userdef-metadata`（兩倉；正本 ＋ 逐位元組鏡像）

### 1.1 動詞介面

```sh
swift run vChewingSharedCLI dump-userdef-metadata \
    [<locale>=<path-to-.strings>]... \
    [--extra-label-prefix=<prefix>]... \
    [--strict]
```

- **stdout 只承載純 JSON**（`> file.json` 直接可用）；一切警告與缺鍵報告走 stderr——此點與該 CLI 其餘動詞「進度印 stdout」之慣例刻意不同（照 P239 §5.4.1）。
- 不給任何 `locale=path` 時仍輸出完整之程式面後設資料（標籤為空）——故本動詞在沒有 `.strings` 的環境下依然可用、且便於測試。
- `--extra-label-prefix`（**本 phase 之設計補充**，見 §四）：收錄「非 `UserDef` 命名空間、但助手也需要」之既有 i18n 鍵。唯音之注音／拼音排列選單名稱係由 `KeyboardParser.localizedMenuName` 供出（`i18n:KeyboardLayout.*`／`i18n:TypingMethod.*`），不經 `UserDef.metaData`；若無此機制，助手只能手抄這 17 條標籤（必然漂移），或令 CLI 相依 `Tekkon`（＝動 manifest，與 P239 §5.4.3 第 2 條「新增動詞無須改任何 manifest」之益處相衝）。
- 退出碼：`0` 成功；`1` 引數不合法／`.strings` 讀不到；`--strict` 下，任一語系缺任一鍵、**或任一 case 確有未遷移之標籤**，即回 `1`。

### 1.2 輸出 schema（`schemaVersion: 1`）

```json
{
  "schemaVersion": 1,
  "generator": "vChewingSharedCLI dump-userdef-metadata",
  "locales": ["zh-Hant", "zh-Hans", "en", "ja"],
  "count": 118,
  "entries": [ {
      "key": "kCandidateListTextSize", "rawValue": "CandidateListTextSize",
      "type": "integer", "defaultsType": "integer", "default": 24,
      "range": [12, 196], "minimumOS": 10.9,
      "exchangeBlacklisted": false, "metadataPending": false,
      "metadataPendingReason": "numericOptionLabels",
      "options": null, "optionsKind": "numeric",
      "labels": { "zh-Hant": { "shortTitle": "選字窗字號", "description": "…" }, "…": {} }
  } ],
  "missingI18nKeys": [], "pendingMetadataKeys": [],
  "extraLabelPrefixes": ["i18n:KeyboardLayout.", "i18n:TypingMethod."],
  "extraLabels": { "zh-Hant": { "i18n:KeyboardLayout.IBM": "IBM 排列" } }
}
```

相對於 P239 §5.4.2 之草案，施工時另立四項（皆為**加項**、不破壞原欄位）：

1. `defaultsType`：`defaults write` 用之型別名（`defaultsCommandTypeName`），與語意型別 `type` 分列。
2. `optionsKind`：`"numeric"`（標籤即其值之十進位數字，如字級 12…196——此類選項**不承載語意**，故不收錄、而由消費端依 `range` 出數值輸入；此舉同時令輸出由 261 KB 降至 223 KB）／`"labels"`（一般單選題）／`null`。
3. `metadataPendingReason`：`none`／`numericOptionLabels`／`foreignI18nOptionLabels`／`unmigratedLabels`／`unmigratedOptionLabels`。
4. 根層之 `pendingMetadataKeys`（真欠譯；`--strict` 即以此為據）。**初版另有一欄 `benignPendingMetadataKeys`（已知之偽陽性）——該欄已於缺陷 ② 根治後移除**（見 §九）。

### 1.3 `--strict` 之判準（初版：施工者之設計補充；其後已根治，見 §九）

P239 §5.4.3 第 7 條稱「`isMetadataPendingManualUpdate` 目前對所有 case 皆 false ⇒ 嚴格模式今日不會誤報」。**實測反例**：該 helper 對三條鍵回 `true`，而三者皆**非**欠譯——

| 鍵 | helper 為何誤報 | 實情 |
|---|---|---|
| `kCandidateListTextSize` | `options` 之標籤為 `"12"`…`"196"`，不等於 helper 假定之 `i18n:UserDef.<case>.option.<idx>` | 選項係以值域逐值生成、標籤即該值本身 |
| `kPopupCompositionBufferTextSize` | 同上（`"18"`…`"40"`） | 同上 |
| `kKanjiConversionPreferences` | `options` 之標籤為 `i18n:KanjiConversionMode.{ModernTrad,KangXi,JIS}` | 已遷移，只是用既有之 `KanjiConversionMode` 命名空間 |

初版之決定是**不改動**既有 helper（其亦為 `list-pending-userdef` 與 `generate-missing-strings` 所用），而於動詞內另立判準：非選項之標籤欄位凡出現非 `i18n:` 形式者 ⇒ `unmigratedLabels`（真欠譯）；選項逐項分類（`i18n:UserDef.<case>.option.<idx>` 為已遷移、標籤即其值之數字者為數值標籤、其餘 `i18n:` 鍵者為外來命名空間）⇒ 前者皆不算欠譯。該判準下之實測結果為 **`pendingMetadataKeys: []`**、偽陽性恰為上述三條鍵，故 `--strict` rc=0。**其後事主指示「四個缺陷都修了吧」，遂改為根治該 helper 本身**（見 §九第 2 項）：判準改為「凡以 `i18n:` 起頭者即為已遷移」＋「值即標籤之數字不算欠譯」，`benignPendingMetadataKeys` 一欄隨之移除。

### 2.2 為何零相依（實測根據）

本機之 TypeScript 為 **7.0.2（Go 原生版）**，其**已移除** `target: es5` 與 `module: none`：

```
tsconfig.json(3,15): error TS5108: Option 'target=ES5' has been removed.
tsconfig.json(4,15): error TS6046: Argument for '--module' option must be: 'commonjs', 'es6', …
```

即「降級至 ES5」與「以無模組系統之全域 script 編譯」兩條路同時被封。既定路線有二：安裝舊版 TypeScript（引入相依），或改以「ES5 寫法 ＋ ES2015 編譯 ＋ 產物守衛」為紀律。本 phase 採後者：

- 原始碼一律 `var` ＋ `function` ＋ 字串相加；不用箭頭函式／樣板字串／`let`／`const`／解構／展開／`class`／物件簡寫／`for...of`／預設參數。
- `tsconfig.json`：`target: es2015`、`module: commonjs`、**`lib: ["ES5", "DOM"]`**、`strict`、`rootDir: src`（TS 7 未顯式指定 `rootDir` 會報 `TS5011` 並改以 `dist/src/…` 佈局輸出——此即 P239 已記之坑）。`lib` 取 ES5 是刻意的：凡誤用 ES6+ 標準庫 API，**編譯期即報錯**。
- 產物以 `tools/build.mjs` 依**宣告序**串接為單一 script（模組以 TypeScript 之 `namespace VCA` 合併；`tools/build.mjs` 內之載入序與 `src/` 之檔案集不一致即建置失敗）。
- **`tools/es5guard.mjs`**：先以自寫之掃描器剃除字串／樣板／註解／正則字面量，再逐行比對 13 條 ES6+ 語法規則（箭頭函式、`let`／`const`、樣板字串、`class`、展開／其餘、`for...of`、`async`／`await`、產生器、預設參數、物件簡寫）、13 條 ES6+ 標準庫 API 規則（`Array.from`、`.includes`、`Object.assign`、`Promise`、`Map`／`Set`……）與 4 條模組系統殘留規則（`require`／`exports`／`import`／`export`）。有一項即建置失敗。
- 打包器（`esbuild`）因此完全不必要——這也正好回應事主「npm 依賴越少越好」之要求；`node_modules/` 自始不存在，P239 §5.3 所憂之「Xcode 同步群組列舉數萬檔拖慢索引」亦隨之消失。

### 2.3 題庫（分支問卷）

十二頁：**歡迎** →（分支樞紐）**您原本用哪一款輸入法** →（分支樞紐）**打字方式** → **打字節奏與聲調** → **按鍵行為** → **選字窗** → **中英混打** → **標點、數字與符號** → **辭典與智慧功能** → **通知與系統整合** → **進階選項**（標示「可整頁跳過」）→ **摘要與產生**。題庫共觸及 **105** 條 `UserDef` 鍵（`allQuestionKeys()` 之實測值；餘 13 條為黑名單、字典型別、無標籤或實驗性者）、**107 道題目**（「還不確定」之超集下）。

各頁之題目**由後設資料生成**（標題取 `shortTitle`、說明取 `description`、選項取 `options`），本 phase 只定義「分頁、排序、分支、推薦值」：

- **分支**：`kKeyboardParser4Zhuyin`（注音排列 0…10）與 SCPC 三題只在「注音組句／逐字選字」下出題；`kKeyboardParser4Pinyin`（100…105）只在「漢語拼音」下出題；磁帶四題只在「CIN 字根」下出題；「還不確定」一律出題（超集）。分支切換時，已不可見之題目的答案會被**即時剔除**（免得把使用者看不到的鍵寫進配置包）。
- **系統版本**：`minimumOS` 高於當前系統者不出題，並於該頁顯示「已依您的系統版本（%1）略過 %2 個需要較新系統的選項」。版本碼為 **`major × 100 + minor`**（見 §四第 3 條）。
- **不可退讓之約束**：每個單選題之預設選項一律為「維持不變（推薦）」；「以推薦值（或出廠預設值）補齊本頁未答之項目」是**逐頁、明示**之核取項（未勾之頁面一個鍵都不輸出——已由冒煙測試固化）。
- **推薦值刻意從嚴**：只收《新手上路》明載之兩條處方（逐字選字派：`kUseSCPCTypingMode`／`kAssociatedPhrasesEnabled`／`kCandidateKeys = "123456789"`／`kUseHorizontalCandidateList = false`／`kCandidateWindowShowOnlyOneLine`／`kEnforceSingleLineCandidateWindowLayout4SCPC`／`kAlsoConfirmAssociatedCandidatesByEnter`；微軟新注音：`kUseRearCursorMode = true`）與同篇分支所暗示之三條（拼音派開拼音、CIN 派開磁帶、漢音開符號表熱鍵）。其餘一律不推薦——**助手不替他人生產沒有依據的立場**；P239 附錄 D 之 ★ 項待事主核定題庫時再行擴充。

## 七、附註（施工實錄，供後續 phase 參考）

1. **本 phase 由單一協調者施工**（未分派 worker）。全程以「先寫 Swift 側、後寫助手」之序：後設資料之真實內容是題庫設計之前提——若先寫助手，題庫之鍵名與值域必憑空臆測（實測即抓到 `kHalfWidthPunctuationEnabled` 之 rawValue 實為 `HalfWidthPunctuationEnable`、`kNumPadCharInputBehavior` 之值域與選項不一致兩事）。

3. **`node --test` 之目錄引數**：Node 22 之下 `node --test tests/`（目錄）會以「找不到模組」失敗；須寫成 `node --test tests/*.test.js`（由 shell 展開）或改用 glob。Makefile 之 `test` 目標已據此定案。
4. **`vm.runInThisContext` 與 `delete globalThis.VCA`**：`var VCA`（`namespace` 之產物）在 script 頂層會建立**不可配置**之全域屬性，故 `delete globalThis.VCA` 會拋 `TypeError`；測試欲「重新初始化」時，重跑產物即可（狀態存於 namespace IIFE 之閉包內，重跑即得全新閉包）。
5. **Node 之 `globalThis.navigator` 是唯讀 getter**：DOM 替身須以 `Object.defineProperty` 覆寫之，不能直接賦值。
6. **`.strings` 之讀取**：`NSDictionary(contentsOfFile:)` 直接吃 old-style plist（四檔之 `plutil -lint` 皆 `OK`），**不必自寫 `.strings` 解析器**——P239 §5.4.3 第 8 條之判斷正確。
7. **`make lintFormatUncommitted` 之涵蓋範圍**：其檔案清單取自 `git diff --name-only HEAD`，故**新建（untracked）之檔案不在內**。凡新增 Swift 檔者，須另行顯式跑 swiftlint／swiftformat，並於其後複跑建置與測試。

## 病灶定位（探針實證）

### 一、實測再現（以出貨辭典為靶）

以 `vChewing-macOS/Build/Products/Release/…/MainAssembly4Darwin_MainAssembly4Darwin.bundle/Contents/Resources/VanguardFactoryDict4Typing.txtMap`（13,877,520 bytes，2026-09-22 建置）為靶，經 `LXAssembly.LXFacade.connectFactoryDictionary(textMapPath:)` 載入（**須先令 `asyncLoadingUserData = false`**，否則載入為非同步、旋即查詢會落空——此為探針首跑之所以只見倚天墊底資料之原因），再以 `Homa.Assembler(gramQuerier:)` 餵入讀音：

| 讀音 | 出貨辭典之組句結果 | 該鍵之辭典內容（權重） |
|---|---|---|
| `ㄉㄜ˙` | 的 | 的 −4.976／地 −5.072／得 −5.072／**底 −9.465**／CNS 群 −11 |
| `ㄉㄡ-ㄉㄜ˙` | **兜底** ← 病灶 | **兜底 −8.718（詞頻 1）**／兜的 −9.32（詞頻 0） |
| `ㄒㄧㄠˇ-ㄉㄜ˙` | 小的 | 小的 −8.019／小底 −9.32（詞頻 0） |
| `ㄏㄠˇ-ㄉㄜ˙` | 好的 | 好的 −9.32 |
| `ㄨㄛˇ-ㄉㄡ-ㄉㄜ˙` | 我｜**兜底** | （跨詞段亦然） |

### 二、病灶真因：一條詞頻 1 的又音詞條贏了組句 DP

`ㄉㄡ-ㄉㄜ˙` 之三條路徑比較：**兜底（單一雙字詞）−8.718** ＞ 兜的（雙字詞）−9.32 ＞ 分解為單字 都(−5.038) ＋ 的(−4.976) ＝ −10.014。DP 取最大者，故得「兜底」。尤須注意者：−9.32 恰為**詞頻 0 之墊底權重**（好的／我的／大的／新的／老的／兜的／小底 皆為此值），而詞頻 1 即抬到 −8.718——**一條罕用詞條即足以奪權一個常用搭配**。此為資料問題、非引擎問題：引擎係照其模型給出的最優解行事，病灶是辭典裡存在一條「兩岸已無人如此唸」的又音詞條且其詞頻非零。

### 三、全庫範圍掃描（窮舉）

為確認「還有多少條這種地雷」，對出貨辭典做了窮舉掃描——凡以 `ㄉㄜ˙` 結尾、且其值以「底」結尾的讀音鍵：

```
key=ㄉㄜ˙            → 底（typeID 5／6 各 −9.465；typeID 7＝CNS 為 −11）
key=ㄉㄡ-ㄉㄜ˙       → 兜底（−8.718）
key=ㄒㄧㄠˇ-ㄉㄜ˙    → 小底（−9.32）
總計 3 個讀音鍵
```

三者之中**唯 `ㄉㄡ-ㄉㄜ˙` 會實際奪權**：`ㄉㄜ˙` 之「底」(−9.465) 遠低於「的」(−4.976)；`ㄒㄧㄠˇ-ㄉㄜ˙` 之「小底」(−9.32) 低於「小的」(−8.019)。故 ACYL 所述「只要輸入到 OO底（ㄉㄜ˙）就會變成底」**在系譜上只有一個來源**：其輸入之末兩音節必為 ㄉㄡㄉㄜ˙（即欲敲「都的」）。此推論同時解釋了「我檢查過我的自訂詞彙裡面並沒有 OO底 這樣的字彙」——該詞條在**原廠**辭典內，不在其自訂語彙內。

## 病灶定位（探針實證）

### 一、實測再現（`spaceKeyBehaviorAgainstICB` 三值結果全同 = 該偏好確實未被讀取）

以本靶 `InputHandlerTests` 之 `prepareMixedModeHandler()` 為靶，注入足以令 auto-split 命中單鍵尾綴之讀音（測試辭典僅收少量讀音），逐詞打完後壓送一枚空白鍵：

| 詞 | 值 0（插入空格） | 值 1（呼出選字窗，預設） | 值 2（輪替候選字） |
|---|---|---|---|
| `apple` | `appl` ＋ ㄍ | `appl` ＋ ㄍ | `appl` ＋ ㄍ |
| `school` | `schoo` ＋ ㄠ | `schoo` ＋ ㄠ | `schoo` ＋ ㄠ |
| `schema` | `schem` ＋ ㄇ | `schem` ＋ ㄇ | `schem` ＋ ㄇ |
| `personal` | `person` ＋ ㄌ | `person` ＋ ㄌ | `person` ＋ ㄌ |
| `hello` | `hell` ＋ ㄟ | `hell` ＋ ㄟ | `hell` ＋ ㄟ |
| `ls` / `tod` / `film` | `ls ` / `tod ` / `film ` | 同左 | 同左 |

**三值逐格全同** ⇒ 該偏好於混打路徑中**毫無作用**（純中文組字之路徑則有讀，見 `InputHandler_TriageInput` 之 `.kSpace` 分支：值 2 走輪替、值 0 走「遞交組字內容 ＋ 半形空格」）。此即工單樓主之第一則留言所指。**`ls`／`tod`／`film` 之所以正常**，係因其緩衝長度未達 5 字元、未觸發次節之逃生門。

### 二、`>= 5` 字元之 auto-split 逃生門（值 1／2 亦同病之真因）

`Typewriter_MixedAlphanumerical.swift` 之 Space 分支：

```swift
      if !shouldPreferASCIIWordOnSpace || twoCharPrefixIsPhonetic
        || handler.mixedAlphanumericalBuffer.count >= 5
        || bufferHasMultipleUppercaseAndLowercase {
        if tryAutoSplitASCIIAndPhoneticSuffix(fullInput: handler.mixedAlphanumericalBuffer + " ", …) { return true }
        …
      }
```

該 `count >= 5` 一條係 2026-05-04（`743d7817`，`Typewriter // MixedAlnum: Fix issues exposed by Izanami tests.`）所加，其註解自陳目的為「支援 hello你好 等長 ASCII prefix 的混輸情境」。**實查其適用面**：`shouldPreferASCIIWordPath(_:)` 之第一道閘即 `^[A-Za-z]+$`，故「含數字或符號」之混輸緩衝（如 `hellosu3`）本即令 `shouldPreferASCIIWordOnSpace` 為假、無須該逃生門；該條實際只作用於**純字母**之緩衝——亦即正是它會誤傷的英文詞。`apple`（`shouldPreferASCIIWordPath` ＝ **真**：大千 `a`＝ㄇ 被 `p`＝ㄆ 覆寫，靜態排列之條件五不容「以另一鍵改寫既有槽值」）本應走 ASCII 路徑，卻被該逃生門改判為 auto-split，遂遞交 `appl` 並把 `e`（＝ㄍ）送進注拼槽。

### 三、空白鍵何以會進到 `handle(_:)`

`InputHandler_TriageInput.swift` 之 `.kSpace` 混打分支前提為「緩衝非空或已閂滯」；惟 `handleComposition(input:)`（`InputHandler_HandleComposition.swift:31-32`）對**每一顆** `charCode.isPrintableUniChar` 之按鍵皆會呼叫 `MixedAlphanumericalTypewriter.handle(_:)`——空白鍵（U+0020）自不例外。故空白鍵之第一站即該 `handle`，而該處之 Space 分支從未讀 `spaceKeyBehaviorAgainstICB`。

## 何以只修「插入空格」這一層（值 1／2 不修之理由）

工單樓主之第二則留言要求把範圍擴及預設值 1。**經逐案比對，此層不可安全收緊**，理由如下（可驗、非權宜）：

`apple` ＋ 空白 與 `ello` ＋ `g` ＋ 空白（大千 `g`＝ㄕ，一個獨立的無聲調音節）在引擎眼中**同構**：

| | `apple` | `ellog` |
|---|---|---|
| 緩衝內容 | 純 ASCII 字母，5 字元 | 純 ASCII 字母，5 字元 |
| `shouldPreferASCIIWordPath` | **真**（`a`→`p` 覆寫觸犯靜態排列條件五） | **真**（`e`→`l` 覆寫同罪） |
| auto-split 候選 | 尾綴 `e`＝ㄍ（詞庫有命中） | 尾綴 `g`＝ㄕ（詞庫有命中） |
| 使用者意圖 | 英文詞 | ASCII 前綴 ＋ 注音 |

**兩者在輸入面上別無二致**；唯一的差別只存在於使用者心裡。故：

- **刪除或收緊該逃生門**（例如要求尾綴 ≥ 2 鍵）⇒ `test_IH400`（Izanami：以 `ello` 等前綴跑遍整張注音表，逐讀音斷言「commissions 須含前綴、組字器須留該讀音」）於「純字母鍵序」之讀音（如 ㄍㄨㄟ＝`ejo`）與單鍵讀音（如 ㄕ＝`g`、ㄖ＝`b`、ㄙ＝`n`）上**當場轉紅**——該測試所釘住的是一條真需求（所有可發音讀音於混打模式下皆須可輸入），不得為本 phase 而改。
- **改以「尾綴是否為完整音節」判別**（如要求有韻母）⇒ 救得回 `apple`（ㄍ 為純聲母）卻救不回 `school`（ㄠ 為純韻母、且是完整音節），而工單樓主明列 `school`；且此舉等於在 Typewriter 內**新立一份注音音節結構表**，正是工單樓主自陳「不新增 Tekkon 靜態音節表」所拒者。
- 事主早於 2026-09-10 對原提報者之說明（「沒有英文 Lexicon 支撐，所以『判定英文』比較難搞」）已指出此為**需求層之固有平手**，非引擎缺陷。

**故本 phase 之定案**：使用者若明示「空白鍵＝插入空格」（值 0），即以其明示為準（本 phase 所修）；值 1／2 則維持現狀（工單樓主第一則之驗收條件亦明言「同一組詞在預設空格行為下維持現狀」），值 1／2 之使用者仍以 **Shift+Space** 整段送出（此為事主原建議、且現行行為已支援，`test_IH514` 固化之）。**此為刻意之範圍界線、非未竟事項**；若事主認為值 1／2 亦須改判，請裁定其取捨（該取捨必得在「Izanami 之可輸入性」與「英文詞尾鍵不吃」之間二選一）。
