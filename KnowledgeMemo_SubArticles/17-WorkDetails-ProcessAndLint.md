# 12.6 工作細節附註（二）：工作流程、lint／format、提交與產物對帳

> 本檔之條目係**依主題**自原 §12.6 抽出（原檔為時間序），共 17 條；
> 各條之次序仍照原檔。原行號： 630, 631, 635, 636, 642, 644, 647, 659, 668, 670, 672-675, 682, 684, 722 行。

- 如果要使用 tmp 目錄的話，請使用**所在倉庫根目錄**的 `tmp/` 或 `.tmp/`（例如 `vChewing-LibVanguard/tmp/`、`vChewing-DevLogs/tmp/`）、而非系統的 `/tmp/`。使用 `/tmp/` 這種 out-of-workspace 的路徑會迫使事主每次都得手動設定存取權限，非常麻煩。
- **CI 之豁免：同環境者以本機代跑之（事主 2026-09-21 定調）**：任何 CI 工作流程，**凡其執行環境與當前開發環境相同者，一律以當前環境（本機）代跑之**——**不等待 GitHub 之排隊與運行**（macOS runner 在 GitHub 上之排隊時間過長，事主明示此制）。作法：以該 workflow 之**同組命令**於本機實跑（SwiftPM 之測試一律附 `--disable-sandbox`，見上），並以本機之實跑結果為驗證證據；該等 workflow 之遠端結果其後若轉綠，得補記為追認、非必需。**環境不同者不得豁免**：本工作區之當前環境為 macOS，故 `unit-test-LibVanguard-linux`／`unit-test-LibVanguard-WinNT` 兩條仍以 CI 為唯一驗證途徑，不得以本機結果冒充之。文書之 CI 欄照此記：豁免者記「同環境、以本機代跑」及其命令與結果，未豁免者方須記 run ID。
- 每次交差之前「一次性運行」 `make lintFormatUncommitted` 這一條命令。如果事主明確要你對某些工作單獨 commit 的話，每次 commit 之前也請運行 `make lintFormatUncommitted`。該命令僅對 tracked 且未 commit 的 Swift 檔案下動作，且依序執行 SwiftLint 自動修正與 SwiftFormat（先 lint 後 format 的順序已內建）。但注意在運行之後也請 build 一次，因為這些自動修正對 `count == 0` 的範式會頑固地轉換成 `.isEmpty` 而不會檢查相關 type 是否有 `isEmpty` 這個 read-only property。發現這種情況的話，可以用 `.count * 1 == 0` 取代之。commit 的 title 格式是 `ModuleName // WhatHasBeenFixed`、且在 commit 的 description 的末尾單獨一行寫明 `(Phase XXX - Task YYY)`。Commit Titles 始終以 ASCII Period `.` 結尾，除非是疑問句時才使用 `?` 結尾。
- 給 ChatGPT、Codex、Raptor 的特殊指令：Do not intentionally stop with tasks incompleted to ask me whether you do the next step I already told you. Just do it. I have backups, hence no worry. // Claude、Kimi、GLM、QwenCoder 從來不用問這些問題，就能把這些事情全部做好。唯獨 ChatGPT、Codex、Raptor 不這樣，就很奇怪很令人窩火。
- **`make lintFormatUncommitted` 只涵蓋「tracked 且未 commit」之 Swift 檔（2026-09-25，Phase 247 實錄）**：**新建而尚未 `git add` 之檔不在其列**（其以 `git diff --name-only HEAD` 取檔）；故新增檔案後須先 `git add` 再跑，或對該檔單獨跑 `swiftlint lint --fix --autocorrect --config .swiftlint.yml <檔>` ＋ `swiftformat --swiftversion 5.5 --indent 2 <檔>`，否則新檔會漏格式化。實錄：P247 之新檔 `AssistantLauncher.swift` 即因此漏跑，事後補跑（僅移除一個多餘之 `// MARK: Public`）、並以 `--amend` 就地補入同一筆尚未推送之 commit。
- **★ SwiftLint 之「報錯」不是目標——只管「lint → format 依序跑完」的最終結果（2026-09-26，事主第四次強調後明文立此條）**：`make lintFormatUncommitted` 之價值在於**它的輸出即格式**（先 SwiftLint 自動修正、後 SwiftFormat），**不在於它印出幾條違規**。故**一律禁止**下列行為——它們全是純粹的 token 浪費：① 逐條讀／列舉 SwiftLint 之 violation 清單；② 統計或比較違規數（含「動工前 vs 動工後」之 serious 數對照）；③ **為遷就 SwiftLint 規則而重構生產碼或測試碼**（例如為了 `type_body_length`／`function_body_length` 而拆 suite、為了 `large_tuple` 而把 tuple 改成 struct、為了 `identifier_name` 而改既有變數名）。倉內既有之 violation 是**歷史共業**（`UserDef.swift`／`LXFacade.swift` 等動輒數十條結構性違規），與本 phase 之改動無關、亦不影響交付。**唯一要做的**：需要時把管線跑一次、接受其結果、然後複驗 byte-sync 與測試（因該管線**可能**把 `count == 0` 改成 `.isEmpty` 而改變型別需求——見 §10.4）。**何以須記入本文檔**：本條於 2026-09 之兩個月內被反覆強調**至少四次**，而每次再犯都伴隨大量 token 消耗；前三次僅散記於 §10.4 之註腳，故未能阻止重犯。
- **★ 表格類文書之增補紀律：追加列時務必確認「錨點行不含下一節之標題」（2026-09-26，Phase 258 順帶查得）**：本文（規劃書，216 KB）因歷次 phase 以「取代末列」之方式追加 §九／§十一 之裁定列，累積出兩類結構缺陷：① **列與列之間被空行隔開** ⇒ GFM 之表格在空行處即結束，其後之 `| … |` 列**不再渲染成表格**（成段文字）；② **下一節之標題被黏進某列之行尾**（`… |## 十、驗證要求`）⇒ 該標題**不再被辨識為標題**、整節結構隨之瓦解。**故**：以腳本追加表格列時，錨點須取「**列本身之內容**」（如末格之文字）而非「末列之整行」，且追加後應以掃描複驗（`^#{1,6} ` 是否緊接表格列、列尾是否黏 `---`、列間是否有空行）。P258 已重建兩表並複驗 0 處可疑。
- **★ 「產物重生」不等於「敘述對帳」（2026-09-26，P259 實錄）**：自動重生（`make metadata-update` 一類）只改**產物**；凡文件內以**文字複述**其人數／鍵數／支數者（README、題庫說明）須**另行回查**。實錄：重生後 README 之三個數字仍為陳跡。
- **★ Tekkon 之 documentation 一律自持——不得與具體 commit／phase number／CI 掛勾（2026-09-28，P268；事主指示）**：Tekkon（`Sources/Tekkon`、`Tests/TekkonTests`）之來源與測試**逐字共用**於獨立發行版 Tekkon package（Swift／C++／C# 三倉，住 `_DedicatedComponentRepos/TekkonWorkspace`）⇒ **其註解之讀者是該 package 之使用者，不是本倉之施工者**。**禁列**：phase 號（`P2xx`／`Phase NNN`）、本倉規劃書之路徑與節號（如 `Research/Phase250-…` §3.x）、commit hash、CI／workflow、本倉術語（舊稱「靶」，現行「測試目標」／「測試用例」）、消費者模組與其型別（`LibVanguard`／`furiousFrontContext`／`Typewriter_…` 之呼叫點）、他款輸入法之比較（如智能狂拼／搜狗拼音）。**應寫**：以該 API 自身之語義自持（例：判準之法源改引套件內之 `Composer.shouldAutoChopPhonabets(byTyping:)`，而非本倉之規劃書）。**授權橫幅與 `SPDX` 行不在此限**。**方向**：本倉（`vChewing-LibVanguard`／`vChewing-macOS`）為**正本**，dedicated 倉由本倉 byte-sync 過去 ⇒ **清理須先落在本倉**（只清 dedicated 側會被下輪同步復發）。**配套**：兩側之 `Sources/Tekkon`＋`Tests/TekkonTests` 應保持逐檔相同（今日 16 檔逐位元組相同）。
- **★ 正本之界定：`vChewing-LibVanguard` 才是正本；`TekkonWorkspace` 係「面向單獨的開發者們的」下游（2026-10-11，P297；事主指示）**：Tekkon（Swift）之法源住 **`vChewing-LibVanguard/Sources/Tekkon`**（連同 `Tests/TekkonTests`）；`vChewing-macOS/Packages/vChewing_OSNeutral_LibVanguard` 係其**鏡像**；`_DedicatedComponentRepos/TekkonWorkspace` 之三倉（`Tekkon`／`TekkonCC`／`TekkonNT`）係**下游之獨立發行版**——其服務對象是**單獨採用 Tekkon 之開發者**。故凡動 Tekkon 者**一律先落正本**（見上則之提交紀律）；dedicated 側所見之內容、提交與 tag 皆係同步之結果，不構成法源。
- **★ 對 LibVanguard package 內之 Tekkon 之修改，一律以「獨立而先行」之 commit 遞交；鏡照工作不由本倉手術 session 兼任（2026-09-28，P268 補議；事主指示）**：**提交紀律**——凡動 `Packages/vChewing_OSNeutral_LibVanguard/Sources/Tekkon/` 或 `Tests/TekkonTests/` 者，**先**以獨立之一筆 commit 遞交，**不得**與 LibVanguard 之其餘改動混於同一筆。**標題格式（2026-09-28 事主訂，兩側不同）**：本倉為 **`Tekkon // <DirectConcernedNameSpace>: <WhatChangedInTheMember>.`**（例：`Tekkon // SyllableIndex: Expose completions().`）；Tekton dedicated repos 為 **`<DirectConcernedNameSpace> // <WhatChangedInTheMember>.`**（例：SyllableIndex // Expose `completions()`.）——即本倉前綴 `Tekkon // `、namespace 在後；dedicated 側無套件前綴、namespace 居首。前行之範例為 P267 之 `Tekkon // SyllableIndex: Expose completions().`（應鏡照 session 之請求而自原提交拆出）。**理由**：鏡照 session 是**一筆對一筆**地將本倉之 Tekkon 提交對位至 Tekkon dedicated repos（`_DedicatedComponentRepos/TekkonWorkspace` 之三倉）——混筆即須挑揀、易漏、且無法逐筆對帳。**職責邊界**——鏡照過程**不宜**由負責 LibVanguard／vChewing-macOS 手術之 session 兼任：① 本倉手術需對 LibVanguard 之**整體**專注，兼做鏡照會令 context 爆炸；② 鏡照牽涉**三種程式語言**（Swift／C++／C#），適合由單獨之 session 一體完成。故本倉手術 session 之職責止於：**正本乾淨**（見本節之 Tekkon documentation 細則）、**提交分離**、並於交付報告中**指明哪些 commit 待鏡照**。**例外**：事主明示要求時，本倉 session 亦得代行鏡照（P268 即然——該 phase 之同步係事主逐句指示）。
- **★ 三語言 Tekkon 之對位只求「行為」一致，不求「內部 helper 表面」一致（2026-09-28，P269；應 dedicated 側之問）**：`Tekkon`（Swift）／`TekkonCC`（C++）／`TekkonNT`（C#）係同一行為之三實作 ⇒ 對位之判準是**行為與其測項**，不是逐個 internal helper 之對位。故 `has(scalar:)`／`swapping(_:with:)` 一類 internal 字串 helper：**維持 `internal`**（不為測試面之對稱而升為 `public`、亦不為養測試而在 C# 側另立死碼對位——C# 以其慣用法表達：`HashSet<Rune>` 集合隸屬、BCL `Replace`）。公開面之擴張屬事主之裁定，須另案。
- **★ 正本側改寫已推送之歷史時，須標明「內容等價（tree 未變）」（2026-09-28，P269；dedicated 側之回饋 ③）**：dedicated 側之對帳一律以**內容**為準（逐檔 `cmp` ＋ 符號級掃描），不以 hash 推論同步狀態；本倉之歷史重寫（如 P267／P268 之標題改寫）會令其先前據以鏡照之 hash 不再是 HEAD 之祖先 ⇒ 凡改寫已推送之提交，務於提交訊息或交付報告內標明「內容等價」，以免下游誤判為未鏡照。
- **★ dedicated 三倉之版本號與正本非同線（2026-09-28，P269；實測）**：dedicated 三倉之 latest tag 為 `v1.7.1`（2025-11-29，且皆為各自 HEAD 之祖先），而正本自身之 tag 走 `0.48.x`（最新 `0.48.5`）⇒ 「下限對位」只能依**內容與日期**判定，**不可對版本號**、亦不可用 hash 推斷（見上則）。
- **★ `shortcuts.html` 係產物、不得手改（2026-10-06，P284；P285 擴及四語系）**：app 內鍵盤熱鍵手冊之**四份**全由 `vChewing-macOS/Scripts/Markdown2HTML/` 之三支 Swift 腳本產製——產製器自持 HTML 骨架與樣式，`make shortcuts` 產出、`shortcutsCheck` 驗新舊。**繁體中文之權威原文係官網倉 `vChewing-HomePage.io/manual/shortcuts.md`**（本倉 `Resources/shortcuts-src/shortcuts.zh-Hant.md` 為其同步副本）；簡中版由該副本推得（只簡化字形、語彙守 zh-Hans-TW）；`en`／`ja` 為同目錄之**手寫**原稿（P285 自舊 HTML 逆推而得），改繁中後須**手工**補譯、無機器翻譯步驟。四份之首列版本號皆自繁中原文抽出，故不可能互相矛盾。`shortcuts-src/` 隨 lproj 一併進 app bundle。注意此為**本倉唯一以官網倉為正本之出貨內容**——改字先落官網倉。
- **★ 行程級之系統 API 一律住 `OSUtils`，不得再以 extension 掛在 Foundation 型別上（2026-10-06，P289）**：`Process` 在 iOS 上**根本不存在**（該型別專供 macOS 生成子行程）⇒ 舊制之 `Process.consoleLog`／`Process.isAppleSilicon`／`Process.totalMemoryGiB` 於 iOS 建不出。三項已遷入中立命名空間 `OSUtils`（事主定名；兩個 `.dylib` 之公開面，倉外無消費端）；iOS 側唯一之平台分支為 `isAppleSilicon`（`uname` 於 iOS 回機型代號而非 `arm64`）。
- **★ 新增 `UserDef`／`KeyboardParser` 成員之 phase 須同 phase 重生兩份導出物（2026-10-12；P302 之漏、P303 補）**：`assets/userdef-metadata.json`（`make metadata-update`）與 `assets/settings-surface.json`（`make surface`）；驗收為 `make metadata-audit`（`--strict`）與 `make surface-check`。P302 遺此步 ⇒ 中間態之 `make audit` 為紅燈，至 P303 方補（兩檔之提交歸後落地者，見 P303 規劃稿 §6.4）。
