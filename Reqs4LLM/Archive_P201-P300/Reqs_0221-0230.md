## 要解決的問題

事主原文：「mixedAlnum 模式下需要用 tooltipUI 的第二行顯示游標最前方組出來的注音讀音 preview。」

混輸模式原本恆久顯示一枚 Tooltip，內容**僅**為使用者敲下的 ASCII 原文——因為組字區顯示的是注拼槽轉寫出來的讀音，ASCII 原文反而無處可見。缺口在於：使用者無從得知該 ASCII 字串被注音排列解析成什麼讀音。組字區固然在同一位置插入了讀音，但那段讀音會被組字區既有內容擠壓、且在安全強化組字區等客體下根本不顯示。

## 落點

### 一、Tooltip 改為兩行（`InputHandler_HandleStates.swift`）

`generateStateOfInputting()` 內的混輸 Tooltip 區塊改為：首行 ASCII 原文、次行讀音；**讀音為空時不附加第二行**（否則 TooltipUI 之行高量測會多算一行空白、視窗多出一段下緣留白）。

```swift
if prefs.mixedAlphanumericalEnabled, !mixedAlphanumericalBuffer.isEmpty {
  let readingPreview = inlineReadingPreview
  result.tooltip = readingPreview.isEmpty
    ? mixedAlphanumericalBuffer
    : mixedAlphanumericalBuffer + "\n" + readingPreview
  result.tooltipDuration = 0 // 設為 0 使 Tooltip 恆久顯示，直到混打模式結束。
}
```

TooltipUI 本身無須改動：`TooltipContentView` 本以 `.usesLineFragmentOrigin` ＋ `.usesFontLeading` 繪製與量測，`\n` 之多行形制自標記狀態（`.ofMarking`）的既有兩行 Tooltip 起即在用。

### 二、讀音之取用與呈現（`InputHandler_CoreProtocol.swift` ＋ `IMEStateParsed.swift`）

`readingForDisplay`（組字區用）與 Tooltip 第二行的需求不同，故拆為三支：

```swift
var readingForDisplay: String { // 組字區：原行為不變
  let currentReading = inlineReadingForCompositionBuffer
  guard !prefs.cassetteEnabled else { return currentReading }
  return currentReading.isEmpty ? mixedAlphanumericalBuffer : currentReading
}

var inlineReadingPreview: String { // Tooltip 第二行
  guard !prefs.cassetteEnabled, !composer.isPinyinMode else {
    return inlineReadingForCompositionBuffer
  }
  return IMEStateParsed.convertReadingForTooltip(composer.getComposition(isHanyuPinyin: false))
}

private var inlineReadingForCompositionBuffer: String { …原 getInlineCompositionForDisplay 分支… }
```

本值是 Tooltip 的一部分，故**呈現規則沿用 Tooltip 自家既有的那一套**。倉內 `showHanyuPinyinInCompositionBuffer` 有兩套呈現、不可混用：

| 呈現位置 | 實作 | 拼音形態 |
|---|---|---|
| 組字區 | `composer.getInlineCompositionForDisplay(isHanyuPinyin: 偏好)` | 數字標調式（`mo3`） |
| Tooltip | `IMEStateParsed.readingThreadForDisplay`（標記狀態既有） | 注音**教科書式**（輕聲前置）；偏好啟用**且該 Tooltip 為橫排**時，改漢語拼音**教科書式標調**（`mǒ`） |

後者之「橫排」判準（`alwaysShowTooltipTextsHorizontally || !InputSession.isVerticalTyping`）與 `showTooltip(...)` 決定 Tooltip 排版方向的判準同源。故把該規則自 `readingThreadForDisplay` 抽成共用成員 `IMEStateParsed.convertReadingForTooltip(_:)`（逐字等義之重構），第二行呼叫同一支——偏好與直排兩個閘門一次到位，日後 Tooltip 讀音規則若有更動，兩處也不會各走各的。

**一項必須踩準的細節**：該轉換函式的輸入**恆為注音原字串**，故第二行的取值來源固定為 `getComposition(isHanyuPinyin: false)`。若圖省事餵入組字區那套「隨偏好變動」的取值（偏好開啟時已是 `mo3`），`restoreToneOneInPhona` 會替它補出 `mo31`，終得 `mǒ1`——`test218` 即為釘死此點而設。

### 三、設定介面與 i18n

| 概念 | en（既有鍵） | ja | zh-Hant | zh-Hans |
|---|---|---|---|---|

## 落點

### 一、`.xcarchive` 之形制（照現代側逐項對位）

```
vChewingInstallerLegacy-YYYY-M-D-HHMMhrs.xcarchive/
  Info.plist
  Products/Applications/vChewingInstallerLegacy.app/
  dSYMs/
    vChewing.app.dSYM/
    vChewingInstallerLegacy.app.dSYM/
```

- **`Info.plist`**：`ArchiveVersion 2`／`CreationDate`／`Name`／`SchemeName`／`ApplicationProperties`（`ApplicationPath`／`Architectures`／`CFBundleIdentifier`／`CFBundleShortVersionString`／`CFBundleVersion`／`SigningIdentity`／`Team`）。`SigningIdentity` 與 `Team` 依現代側之例留空：archive 內之 app 是 ad-hoc 簽章，Developer ID 身分屬於匯出端那台機器。
- **`Products/Applications/` 放的是安裝程式**，不是 IME——IME 以 `Contents/Resources/vChewing.app` 棲身其內。這不是取捨而是對位：現代側之 archive 同樣只放 `vChewingInstaller.app`（實查 `Build/Products/Debug/vChewingInstaller.app/Contents/Resources/` 亦為此形），且 legacy 的那支 Xcode 專案 archive 的本來就是這個 scheme（`xcodebuild archive -scheme vChewingInstallerLegacy`）。
- **`dSYMs/`** 對兩支執行檔各出一份（`xcrun dsymutil`，非 AppleScript 式之猜測）；release 產物仍帶 debug map，故 dSYM 為實物（實測 35 MB ＋ 7.2 MB）。
- **刻意不含 `SwiftSupport/`**：那一區是 App Store 上傳用的（供審查端重簽內嵌之 Swift 執行期），本 archive 之用途是 Developer ID 簽名與公證——與現代側一致。
- 檔名沿用現代側 `…-YYYY-M-D-HHMMhrs.xcarchive` 之節奏，legacy 側冠以 `vChewingInstallerLegacy-`。

### 二、開關與分工

- **plugin 端**新增 `--archive`（與現代側同名）。`assembleAppBundles` 之回傳值自 `URL` 改為 `(appsDir: URL, version: (marketing: String, build: String))`，讓 archive 直接沿用剛剛組 bundle 時讀到的 `Release-Version.plist` 版本對，不必再讀一次。
- **archive 只寫在套件目錄內**（`Build/Products/`）：command plugin 之寫入權止於 `--allow-writing-to-package-directory`，故搬進 `~/Library/Developer/Xcode/Archives/<date>/` 是 `make` 的事——與現代側 `archive` 目標以 glob 搬走同一手法，連「搬而非複製、`Build/Products/` 下不留 `.xcarchive`」之行為也一致。
- **`Makefile` 端**：`archiveLegacy: LEGACY_CONFIG := release` 且前置為 `releaseLegacy`——archive 是發行產物，單架構 debug 的 archive 既未最佳化又只有 x86_64。`LEGACY_CONFIG` 之 target-specific 值亦令 `$(LEGACY_PRODUCTS_DIR)` 指向 release 產物目錄（否則會落到 debug 那一份，這正是 `bundleLegacy` 之預設 config 踩過的坑）。
- `Architectures` 由 `lipo -archs` 現讀而非寫死：legacy 之 universal 是兩次 `swift build`（`x86_64-apple-macosx10.9` 與 `arm64-apple-macosx11.0`）各自出 slice 後再 `lipo` 併起來的，與一次建置出 universal 的現代側不同路。

## 落點

### 一、`PerceptionPersistor` 之鎖改為嚴格葉鎖（單邊消滅倒置）

- **`saveData` 不再於持鎖狀態下呼叫任何回呼**：新增 `private func pendingKeys() -> PendingKeys` 與 `private struct PendingKeys { upserts, removals, needsFullSnapshot }`——鎖內只做「排序鍵集 ＋ `needsFullSnapshot`」的**狀態快照**，出鎖後才跑 `mapProvider`／`keyValidator` 組 records，最後回鎖清 pending。`preparePendingJournalRecords` 改收該快照；其內原有的 `if needsFullSnapshot { return [] }` 早退改由呼叫端之 `guard !pending.needsFullSnapshot` 承接（同一時間點、同一語意，行為不變；該 guard 與其後 `records.isEmpty` 之 guard 共用同一句日誌）。
- **`shouldCompactJournal(for:)` 之鎖歸屬反轉**：舊版是呼叫端持鎖呼叫它（函式內含 `attributesOfItem` 之檔案 I/O）；改為函式自行在需要讀 `journalEntriesSinceLastCompaction` 時取鎖，呼叫端不再持鎖。此處非死鎖來源，改的是「持鎖期間不做 I/O」這條同族的紀律。
- **類別 doc 新增〈取鎖紀律〉**：明寫本類別的鎖恆為葉鎖、取用期間不得呼叫 `dataProvider`／`mapProvider`／`keyValidator`／`loadCallback`／`replayApplicator`，並寫出失敗模式（與 `LXPerceptor` 之持鎖路徑互為倒置即成永久死鎖）。
- **新增 `isLockHeld`（internal，標註僅供測試）**：實作為 `NSLock.try()`——同一執行緒在持鎖狀態下重入取鎖時亦回 `false`，故可把上述紀律釘成可斷言的性質。此探針置於類別本體之 `// MARK: Internal` 段（不另開 extension：該檔已有一個以上同型 extension，另開會多出一筆 `no_grouping_extension`）。

**`LXPerceptor` 側刻意一行不動**：該側「持鎖時呼叫 persistor 之 pending-key 標記」是既有契約（見上引 `MARK` 標題），且那些呼叫是**葉操作**（只取一把鎖、不呼叫任何回呼）。倒置的成因在 persistor 側那一處嵌套，故單邊消滅即足；動 `LXPerceptor` 只會平白改動與 macOS 倉逐位元組同步的檔案。

### 二、回歸測試（新檔，3 支，皆單執行緒可確定判定）

死鎖本身是時序性的、且 6.4 建置下此二型別為 main-actor-isolated（寫不出真正的兩執行緒競態測試，硬寫也只能靠 `assumeIsolated` 之類的不安全手段）。故改以**探針斷言不變式**：回呼被呼叫的那一刻，鎖不得被持有。

- `testSaveDataJournalCallbacksRunOutsidePersistorLock`：快照檔先存在（否則 `saveData` 會走完整快照分支而提前返回）＋ 標記一筆待 upsert 鍵，走「追加日誌」分支；斷言 `mapProvider`／`keyValidator` 執行時鎖未被持有。末以「日誌檔確實落地」佐證該二回呼真的被走過，避免斷言空轉為真。
- `testSaveDataSnapshotCallbackRunsOutsidePersistorLock`：快照檔不存在 → 走完整快照分支，斷言 `dataProvider` 亦然。
- `testLoadDataCallbacksRunOutsidePersistorLock`：造一份快照 ＋ 一行合法日誌記錄，斷言 `loadCallback`／`keyValidator`／`replayApplicator` 三者亦然。
