# 12.6 工作細節附註（四）：輸入引擎、查詢語義、IMK 診斷與狀態護欄

> 本檔之條目係**依主題**自原 §12.6 抽出（原檔為時間序），共 29 條；
> 各條之次序仍照原檔。原行號： 645, 646, 651, 652, 656, 660, 661, 663, 664, 666, 676-681, 688-694, 700, 702 行；另加原檔尾 826, 827, 828, 830 行（其性質同 §12.6）。

- **★ 判「某模式是否生效」時，凡有第二處就地複製其判定者，即為新增維度時之盲區（2026-09-26，Phase 258 實錄）**：`InputHandler_TypingMode.typingMode` 是狂打模式之「單一出口」（型別分派、各閘門、行內提示皆由其推導），但 `LexiconAssembly/LXFacade.syncPrefs()` 內之注音文抑制旗標 `shouldSuppressFactoryZhuyinwenData` 出於**模組邊界**（`LXFacade` 拿不到 `composer`）而**就地複製**了同一判定。P258 為「中英混合輸入回退否決注音狂打」新增一維時，若只改前者，即出現「模式已非狂打、抑制卻仍開」之第五態（違反 P257 之四態裁定）；反之只改後者則出現反向割裂。**故此類「就地複製」之處必須與真源逐字同步，且以測試雙向守住**（此案：64 組真值表 ＋ IH168）。**一般化**：在本專案宣告「某屬性即單一出口」時，須先確認無第二份複製品——否則該宣告只在原模組內成立。
- **★ 一個功能「失效」時，先分清「相爭落敗」與「從未執行」（2026-09-26，Phase 258 實錄）**：事主所報「注音狂打開啟後、中英混合輸入回退失效」，初看像兩套機制搶按鍵而其中一方落敗；實查卻是**回退那條分支根本沒有被建構**——`handleComposition` 之 `switch typingMode` 是唯一分派口，而 `typingMode` 當時只問狂打開關。**判別之法：先查分派口之判準讀了哪些旗標**；若某旗標不在判準之視野內，則「兩者並存」之情境下它連被諮詢的機會都沒有。**旁證之價值**：本案中空格鍵仍走回退（`TriageInput` 之 `kSpace` 分診只讀 `mixedAlphanumericalEnabled`、不經 `typingMode`）——「一半的鍵走 A、一半的鍵走 B」之割裂，即「分派口漏讀旗標」之典型指紋。
- **★ 紅線之判讀：先讀其自陳之理由，再讀其禁令（2026-09-26，P254 ＋ P261 實錄）**：凡見「某旗子不得放寬」一類紀律，**須先確認「不動」是否真的等價**——若新增之值會讓它變真，就要**收緊**而非「保持原樣」。實錄：`isPinyinFamilyTypingMode` 原為 `isComposerUsingPinyin || isFuriousTypingModeEffective`，P254 令後項亦可於注音側成立 ⇒ 只「不動」即令佈局翻譯被跳過、注音完全打不出字；正解為收緊成單一條件（等價變換）。**另一半**：禁令之文字常比其**自陳之理由**寬——P261 之「Tekkon 不得新增任何知曉『狂打』概念之 API」，其理由為「Tekkon 是無狀態偏好、無會話概念之音節組裝器」⇒ 該禁令之**實質**是「不得在 `receiveKey` 內做任何自動提交」，指**行為**而非**命名**。**凡遇禁令與需求相牴觸，先讀理由；讀完仍有疑義才問事主。**
- **★ 「閘門變真」不等於「視窗出現」——先查該 UI 的資料由誰供給（2026-09-26，P256 實錄）**：`isFuriousCopilotCandidateWindowVisible` 含 `state.isCandidateContainer`，而 `State.ofInputting` 起手之 `candidates` **為空**（其候選只有兩個寫入者）⇒ 只改「未完成讀音」之判準，注音側之窗**永遠不會開**。**凡「某 UI 的閘門一改即通」之推論，必須回頭查資料供給端。**
- **★ 歸位之判準＝「它讀誰的狀態、誰持有它」（2026-09-26，P260／P261 實錄）**：**判準（純函式）住其唯一呼叫者之目錄；狀態型別住其持有者之處**（`InputHandlerProtocol` 持有之 Config ⇒ 住 `InputHandler/`；`Tekkon.Composer` 之純函式 ⇒ 住 `Tekkon/`）。**成對之既有慣例必須成對處理**（`FuriousTypingConfig` 與 `MixedAlnumConfig` 係同一寄居慣例，只動一邊即製造新的不一致）。**判「該不該搬」時先問「它讀誰的狀態」**：同一檔內之兩個擴充，讀純 `Tekkon` API 者可搬、讀 `InputHandlerProtocol` 者**結構上不可搬**。
- **★ 以 `rawValue` 查表者，鍵一律不得帶 `k` 前綴（2026-09-26，P259 實錄）**：`UserDef` 之「名」與「rawValue」並存，初稿之否決表以 `"kFuriousTypingEnabled4Pinyin"` 為鍵而查表用 `entry.rawValue`（**無** `k` 前綴）⇒ **否決靜默失效**。**凡「查表無命中卻不報錯」之設計，一律先驗一次命中。**
- **★ 功能缺口之歸因須先實測，勿依症狀推論因果（2026-09-26，P258 實錄）**：事主原擬之歸因（「單注音插入阻礙簡拼」）經實測**不成立**，事主亦自陳歸因有誤並裁定撤回該方案。與本文檔既有之〈相爭落敗 vs 從未執行〉一條同源：**兩者皆屬「先實測、後歸因」**。
- **★ `partialMatchEnabled` 係全域查詢閘，不得為「只豐富候選窗」而開（2026-09-28，P265 實錄）**：其消費者含組字器之 `gramQuerier`（`unigramsFor(keyArray:partiallyMatch:)`）、`hasGrams`（自動切音節之辭典閘）與掛載來源 ⇒ 一開即令 DP 採納「keyArray ≠ 所敲鍵」之元圖、未確認即改寫鍵鏈（實測：鍵入 ㄍㄋㄋ 顯示成「狗男女年」）。**partial 語義若只欲施用於候選清單，須於窗層自取**（`Typewriter_Cassette` 早有同型警告）。
- **★ 查詢之回傳序即名次序；陳列之分層留給窗（2026-09-28，P263／P264 實錄）**：`abbreviatedWordCandidates` 一度以分區陳列（原廠區塊先、使用者片語後）⇒ 清單位置≠分數名次，兩處名次型消費者遂誤判（自動套用之次級、α 固化之首筆）。P264 令回傳序即分數序，窗層只保留段數／語境分層。**凡以清單位置取名次者，先確認該清單之序即名次。**
- **★ 一查詢若由兩分區（原廠／使用者辭典）合成，其匹配語義與呈現順序須逐項對齊（2026-09-28，P262 實錄）**：`abbreviatedWordCandidates` 之兩側不一致——原廠側恆等段（trie 內定 `longerSegment: false`），使用者片語側之通用前綴掃描則忽略多出的段 ⇒ 兩格之簡拼撈回三音節之使用者造詞。**修在查詢端、不動通用前綴 API**，收斂取**上界**（短者另由需整詞完全匹配之消費端把守）；**呈現順序亦然**——同一功能在兩模式各據一條路徑時，其窗內順序須同源（IH170）。
- **★ 「當次推導」之結果不得寫進持久狀態：語境加分只准移動選取、不准記成覆寫種類（2026-09-29，P272 實錄）**：`Homa.Node.getScore` 命中 bigram／trigram 時原以 `selectOverrideGram(..., type: .withTopGramScore)` 記下——而該臂逕以 unigram 基線計分 ⇒ 加分**只生效一拍**：下一次組句不重算加分，該節點隨即退回無語境之選取（實測：按 ㄕˋ 得「這個檔案是」、再按 ㄗ 即還原「這個檔案室怎」；`assemble()` 因而對同一組鍵不冪等）。正解為新增 `adoptGramForContext(keyArray:value:previous:anterior:)`：**只移動 `currentGramIndex`**、不動覆寫狀態；`.withTopGramScore` 之「弱釘選」語義**只屬顯式套用者**（POM 之自動套用端 P181 仍倚賴之）。配套：`unigramScore` 須擋住「帶語境之元圖在無前述內容處充當基線」。
- **★ 上下文鞏固保全「值」時亦須保全「詞界」（2026-09-29，P272 實錄）**：`consolidateCandidateCursorContext` 原以**逐鍵覆寫**保全節點其餘各鍵之值 ⇒ 三鍵節點「檔案室」被拆成「檔」「案」「室」、**詞界消失**；而覆寫後之各下游（POM 之語境觀察、後續組句）皆依節點判讀詞界，故選「是」所記下之語境成了「檔 案」、該記憶對「檔案 是」永不生效。改以「覆寫範圍以外之連續鍵**先併為單一節點**（由長至短）、辭典無此詞才退回逐鍵」：值之保全一字不動、詞界得存（實測記憶鍵由 `(ㄉㄤˇ,檔)&(ㄢˋ,案)&(ㄕˋ,是)` 變為 `(ㄍㄜˋ,個)&(ㄉㄤˇ-ㄢˋ,檔案)&(ㄕˋ,是)`）。**一般化**：凡「拆節點」之處置，皆須問「誰在下游讀這個分段」。
- **★ 「拼音並擊」之讀音轉換分兩式，不得互換（2026-09-29，P277）**：`convertReadingForTooltip(_:)` 供**完整**讀音（補陰平、轉教材式標調、問方向）；`convertReadingForHanyuPinyinDisplay(_:isHanyuPinyin:)` 供**未完成**讀音（窗頂 pane、混打 Tooltip 之讀音行）——**逐字同組字區讀音欄**（數字標調附尾、`ü` 作 `v`、不補陰平）、不問方向。混打 Tooltip 之 ASCII 原文不得回填（其住讀音欄）。
- **★ 混打之讀音量測不拘狂打開關；顯示路徑不得只讀注拼槽（2026-09-29，P278）**：`mixedAlnumBufferPendingReading` 為核心量測，`mixedAlnumPendingReading` ＝其加掛併存閘（狂打素材用）。注拼槽僅為緩衝之投影、於「整段未被詞庫採納」時即被打字機清空 ⇒ 混打 Tooltip 之讀音預覽必須取緩衝側之量測（`su;`⇒`niang`），否則整窗無讀音可示。
- **★ 並存態之空白鍵歸屬須有單一正本；Shift+Space 為 ASCII 逃生口（2026-09-30，P280）**：混打＋注音狂打並存時一律取 `MixedAlnumSpaceDuty`（分診早段之固化塊與打字機共用之）——待調讀音者＝陰平確認、帶 Shift 者＝放棄注音、遞交整段 ASCII ＋ 半形空格；新修飾鍵維度不得再於兩處各寫一份運算式。逃生口之遞交須**先取出原文再清空緩衝**，否則 `committableDisplayText` 會把 copilot 對該讀音之投機預覽一併遞交（`su`＋Shift+Space 得 `你su `）。
- **★ 「顯示什麼」與「遞交什麼」須由同一取值鏈導出（2026-10-06，P287）**：組字區顯示（`generateStateOfInputting`）與遞交取文（`committableDisplayText`）各推一次「未完成讀音」⇒ 並存態下顯示取混打緩衝原文、遞交取 copilot 之投機預覽（`su` 得 `你你泥su`），且緩衝原文被插入兩次（`abcabc`）。P280 只在一個站點補救，其餘四個同型站點遂照病。**凡「該顯示什麼」與「該遞交什麼」分屬兩函式者，須令後者取前者之來源**（或令兩者共用同一私有取值鏈），並以測試守住；同理，凡「某物之原文由呼叫端追加」之約定，插入端即不得再插入之。
- **★ IMK 回呼路徑上「查無 session」之分支不得靜默（2026-10-09，P291 客訴 #618 之實證）**：`SessionControllerSputnik` 之 `activateServer`／`deactivateServer`／`recognizedEvents`／`handleEvent` 四處，原在 `session(forAddr:)` 回 nil 時逕回中性值（0／false／nothing）⇒ 日誌上與「事件根本未投遞」同形，無從定案。凡此類降級分支一律走 `logUnresolvableController(_:at:)`，印 addr／`isAddressAlive`／gen／`trackedControllerCount`。
- **★ 診斷日誌只寫在失敗分支上不足；成功路徑亦須記身分（2026-10-10，P296 客訴 #618）**：事件型別層級之失蹤（同一時段 keyDown 有、flagsChanged 全無）無法由「查無 session」之降級日誌看出。回呼進入點一律印 controller 位址、`isAddressAlive`、generation、解析所得 session 之已指派位址與 client bundle id——三者一比即可分「未進入」「位址已除名」「被路由到別枚 controller」。
- **★ `IMKInputSessionController` 之兩條現行行為（2026-10-09，P291 實查）**：`-deactivateServer:` 後 3.0 秒，`-IMKSwift_delayedDealloc` 即對該 controller 無條件呼叫 `terminateForClientXPCConn:`（客體在 3 秒內回到前景，方由 `-activateServer:` 取消）；`+IMKSwift_pruneStaleControllersOnServer:excludingSelf:` 自 `8a734b4d` 起**無 count 門檻**，每次新 controller 初始化即剔除一個最舊且非 `_currentController`、非自身者。
- **★ 拼音對照表之方向：key＝拼音、value＝注音——勿信屬性名（2026-10-11，P297 實證）**：`mapHanyuPinyin` 等六表皆然（起首如 `"chuang": "ㄔㄨㄤ"`）；`MandarinParser.mapZhuyinPinyin` 之名讀不出方向、其內容即「拼音→注音」。`PinyinTrie.init` 之註釋曾反寫此方向（自 C++ 側謄抄時兩詞互易，`f4cfcbc3` 引入，P297 訂正）。
- **★ 換裝輸入法時「殺舊行程」須在換檔之後、且須驗證（2026-10-11，P298 實證）**：IMK 隨選啟動、永遠自磁碟上已註冊之 bundle 拉起 ⇒ 換檔**前**殺只會讓系統把舊碼重新拉起（新 PID、舊碼），恰好躲過其後一切檢查（實測：舊 legacy 行程在新碼就位後仍服務近 30 秒）。postcondition 不可寫「沒有行程」（必被重拉），須為「**那批捕捉到的 PID 皆已消失**」；`killall` 之結束碼從前未經檢查，不構成保證。
- **★ IMK 之 Legacy／Modern 分身由 `+subclass` 挑選、與建置 SDK 無關（2026-10-11，P298 副產物）**：`[IMKServer subclass]` → `_IMKServerLegacy`、`[IMKClient subclass]` → `IMKClient_Modern`；唯音以 `IMKServer(name:bundleIdentifier:)` 建 server，故 server 端走 Legacy。實測 legacy（sdk 13.3）與 modern（sdk 27.0）兩建置之事件堆疊皆「每事件 2 幀 `_IMKServerLegacy`、裝飾層 0 次」⇒ 建置 SDK 不影響 IMK 傳輸路徑。
- **★ 私面干涉之診斷開關須「決策當下求值」、不得快取（2026-10-11，P299）**：`IMKSwift` 對 `IMKServer` 之四項干涉皆有對應鍵（`_IMKSwift_disableServerControllerPruning`／`_disableEvictedClientInvalidation`／`_disableClientWrapperTermination`／`_disableControllerDelayedDeallocation`；`UserDef` 之 `rawValue` 以單底線開頭合法，雙底線保留給偏好交換之中介鍵），由 Swift 端安裝回傳 `BOOL` 之 block、ObjC 端每次決策都回呼 ⇒ 使用者可在失靈當下翻開關做因果判定，無須換版重裝；未安裝之 block 一律視為「未停用」＝出貨行為。四鍵之巢狀：`…ControllerDelayedDeallocation` ⊃ `…ClientWrapperTermination`（後者屬前者之一步）；`…ServerControllerPruning` 開則 `…EvictedClientInvalidation` 無效（無剔除則無連線可保）。四鍵之 2⁴＝16 種組態因上述兩條巢狀關係實際只有 **9 種可分辨行為**（S1 ⇒ S2 失效；S4 ⇒ S3 失效——後者之守衛落於前者所守之 body 內、程式碼級不可達）；現場判別走四步決策樹即可（`Research/Phase299_Research_DevZoneIMKSwiftSwitches.md` §6），不必窮舉。
- **★ 打字機（Typewriter）可套接：同一 `handler` 上多型別接力（2026-10-12，P301 研究實查）**：`TypewriterProtocol.handle(_:) -> Bool?` 之回值即「本鍵是否已被輸入法攔截處理」（`nil` 為未處理）；`Sources/LibVanguard/Typewriter/Typewriter_MixedAlphanumerical.swift:24-28`（亦 `:195-212`、`:249-263`）即於自身 `handle` 內具現 `BPMFFullMatchTypewriter(handler)`、設定其可注入面後 `return typewriter.handle(input)`。可注入面（皆 `public var`；`Typewriter_BPMFFullMatch.swift:23-29`）＝`onLexiconMatchFailure`／`isToneOverrideEnabled`／`isLeadingIntonationAccepted`。⇒ 欲加「按鍵語義不同之新輸入法層」時，宜採**前控式套接**（新層只認自己的鍵，其餘轉呼 BPMF），不必在 BPMF 內再插條件；組音槽／組字器（`assembler`）／`session` 皆在 `handler` 上，套接不須搬運狀態。
- **★ 中英混輸層僅為注音服務、拼音側不得借道（2026-10-12，P301 事主訂正）**：`isMixedAlphanumericalLayerInEffect`（`Sources/LibVanguard/InputHandler/InputHandler_MixedAlnumConfig.swift:99-102`）＝`currentTypingMethod == .vChewingFactory && typingMode != .cassette && !composer.isPinyinMode && prefs.mixedAlphanumericalEnabled`；且 `MixedAlphanumericalTypewriter` 對拼音模式逕轉 `BPMFFullMatchTypewriter`（`InputHandler_HandleComposition.swift:32-33`）。⇒ 拼音側（含雙拼）之一切「回退為原文 ASCII」需求皆須自持實作。
