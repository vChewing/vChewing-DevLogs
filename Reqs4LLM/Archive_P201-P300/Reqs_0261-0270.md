### 一、兩個擴充，只有一個是候選

事主之例外條件（「唯 `ZhuyinAutoChopPredicateTests` 有沾到 Tekkon 以外的 components」）於此**從寬成立**——該檔之依賴面實查如下。

#### 五項查得

| # | 查得 | 實據 |
| --- | --- | --- |
| ① | 該檔之**兩個**擴充只有一個是候選 | `isZhuyinFuriousTypingModeEffective` 讀 LibVanguard 之 `isFuriousTypingModeEffective` ⇒ **結構上不可能搬**（除非 Tekkon 反向依賴 `InputHandlerProtocol`） |
| ② | 判準之依賴面**全在 Tekkon 之既有 `public` API** | 逐一實查 12 項：`isEmpty`／`receiveKey(fromScalar:)`／`receiveKey(fromString:)`／`getComposition`／`parser`／`consonant`／`semivowel`／`vowel`／`intonation`／`Composer.init(arrange:)`／`SyllableIndex.shared(parser:)`／`isPrefix` |
| ③ | 測試靶**不沾 Tekkon 以外之組件** | import 僅 `Foundation`／`Tekkon`／`Testing`；`@testable import LibVanguard` **實為空載**（逐符號掃 `*Handler`／`*Session`／`*Pref*`／`*Config`／`*State`／`*Candidate`／`*Assembler`／`*Querier`／`*Facade` 命中 **0**）；語料本就住 `Tests/TekkonTests/TestAssets_Tekkon/` |
| ④ | §3.3 之紅線**按其原文不禁止此事** | 紅線之實質為「**不得在 `receiveKey` 內做任何自動提交**」；而 `pinyinAutoChopResult`（`:276`）**已在 Tekkon 內回傳自動 chop 之判準與建議切分**、`allowsExtendedRomajiBuffer`（`:89`）之註解直書「狂拼」⇒「知曉概念」那半句依其自陳之理由係指**行為**而非**命名** |
| ⑤ | 意義**在「決策」層統一、在「乘載」層刻意不統一** | 兩側皆為「問 → 辭典閘 → 提交 → 刷新 → 追蹤」五步同構，且**提交物同為無調注音詞幹**（`PinyinTrie` 之 value 即 zhuyin 讀音 ⇒ `committedReadings` 之文件自陳「前段注音讀音鍵」）；惟拼音側**必須回傳**兩半（`committedReadings` ＋ `remainingRomaji`），注音側**只需回布林**——因注音之讀音**本就在注拼槽內**（呼叫點以 `phonabetKeyForQuery` 自取），拼音之切分則必須被建構 |

#### ★ 兩軸命名規則（事主裁定；規則本體已登錄於 `KnowledgeMemo4LLM.md`）

**名字指「模式／鍵盤家族」者用 `Zhuyin`／`Pinyin`；名字指「切分機制與其提交物」者用 `Phonabet`。** 推導自 ⑤：機制是**族中立**的，族只決定哪一臂跑。

| 現名 | 處置 |
| --- | --- |
| `shouldAutoChopZhuyin(byTyping:)`、`zhuyinAutoChopSlots()`、`zhuyinAutoChopHighestFilledSlot(_:)`、`performZhuyinAutoChopIfNeeded`、`ZhuyinAutoChopPredicateTests` 及其兩支測試函式名 | → `phonabet…` |
| `performPinyinAutoChopIfNeeded`、`InputHandlerTests_ZhuyinFurious.swift`、`isZhuyinFuriousTypingModeEffective` | **不動**（前二者之族名有實義：運送 romaji／驗的是模式） |

**候選名之取捨**：`Phonabet`（採）＞ `Phoneme`（會引入第二個術語；本倉已有 `Tekkon.Phonabet`／`allowedPhonabets`）。

#### 檔名之取捨

事主原提案 `Tekkon_Composer_PhonabetAutoChop.swift`，經評估後改為 **`Tekkon_PhonabetAutoChop.swift`**：Tekkon 六檔一律 `Tekkon_<名詞>`（`Constants`／`Phonabets`／`PinyinTrie`／`SyllableComposer`／`SyllableIndex`／`Utilities`），**無 scope 前綴、無雙底線**；且 `Composer` 一詞在 Tekkon 內已由 `SyllableComposer` 佔用。另一條正面理由：`SyllableIndex`／`PinyinTrie` 皆為**獨立型別放在 Composer 之外**，而本判準實質上是「Composer 狀態 ＋ 本鍵 → 裁決」之純函式，與 `SyllableIndex` 同類。

#### 紅線之判讀

§3.3 之禁令按其**自陳之理由**（Tekkon 是無狀態偏好、無會話概念之音節組裝器）係禁**行為**而非**命名**；兩項反例（見〈五項查得〉④）已存在於生產碼。故 §3.3 就地補〈範圍釐清（v26）〉。**通則本體見 `KnowledgeMemo4LLM.md`〈紅線之判讀〉一條。**

**兩顆助手首次成為真 `private`**：在舊址，Swift 之訪問級別規則迫使它們至少與呼叫它們的 `public` 函式同級（實為 `internal`，只是以 `private` 書寫故不生效）；遷入 Tekkon 後該擴充與助手同檔，遂名副其實。

**閘門之歸屬理由**：它**消費 `typingMode`**，是 Handler 側「當前處於哪個模式」之真值，不是打字機之物；且其定義**呼叫** `isFuriousTypingModeEffective`——與其兩族同址，較另立新檔更不易漂移。**另一方案（另立 `InputHandler_FuriousTypingGates.swift`）不採之理由**：同族三旗本住同一個 `extension InputHandlerProtocol`，只搬其一即拆散；該檔內另有 6 處使用通用閘。

#### Tekkon 檔案頭新增之必要註（遷移之唯一實質代價）

權威規格（逐條理由、四則對照實例、三條已知界線）住 `Research/Phase250-ResearchAndNextSurgeryPlan.md` §3.2（v7），而**該檔不在 Tekkon 套件內**——Tekkon 係對外發布之套件。故新檔以**摘要自持**，並明寫**雙向綁定**：不得只動此處之實作而不動該正本，亦不得只動正本而不動此處。**凡把「有外部權威文件」之程式碼遷入獨立套件者，此為必付之帳**；顯式承擔勝於留下無出處之規格。

#### 遷移之無損性

**逐行文字指紋**：搬遷前後兩檔之全部行 vs 兩檔餘部 ＋ 三新檔之全部行，逐行多重集相減——**LOST 僅 1 行**（一條陳舊之 doc comment：`InputHandlerProtocol.shouldAutoChopZhuyin` → `Tekkon.Composer.shouldAutoChopPhonabets`，該接收者自 P255 起即為真）、**GAINED 僅檔頭與 `import`／`MARK`／`- Note:` 共 20 行**。此形比「測試全綠」更強，因它同時證明**沒有任何一行被靜默丟棄**。
