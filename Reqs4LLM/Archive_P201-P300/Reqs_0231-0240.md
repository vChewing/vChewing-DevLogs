事主原文：

## 病灶定位（探針實證）

`CandidatePool4AppKit` 有兩個**行程級**的靜態範本 cell（`static var shitCell`／`static var blankCell`，用於量測最小 cell 尺寸與填充行）；`CandidateCellData4AppKit.init` 會依當下的 `unifiedSize`（＝偏好 `candidateListTextSize`）把 `textDimension` 算好**存進 struct**，此後 `updateMetrics` 只寫 `visualDimension`、不回寫 `textDimension`。於是範本 cell 一旦在字級 A 之下被初次存取，其 `textDimension` 便在該行程內定影於 A。

`lineStep`（「單行高度（horizontal matrix）」）原本寫成 `cellTextHeight + 2 * padding`，而 `cellTextHeight` 是 `let cellTextHeight = CandidatePool4AppKit.shitCell.textDimension.height`——**建池時的快照**。`lineStep` 只被橫向排版的捲動模型消費：

- `pageCandidateSize` 之橫向分支 → `lineStep × maxLinesPerPage`（＝捲動視口高度，即使用者所見的視窗最大高度）
- `maxScrollOffset` 之橫向分支 → `candidateOnlySize.height − lineStep × maxLinesPerPage`
- `scrollerThumbRatio`、`scrollByLines`、`snapScrollOffset`、`scrollToMakeLineVisible`

**橫向排版為何以快照式算式表達視口高度**（此即故障只落在此處之結構性原因）：

- TDK（非捲動）分支之視窗高度取自 `metrics.fittingSize`——由 `layoutCells` 逐一量測排出的 cell 高度相加，故必然跟隨字級。
- 縱向排版之捲動視口量的是 `candidateLines[page]` 各列**實測**寬度與高度，故亦必然跟隨字級。
- 唯獨橫向排版的捲動視口以 `lineStep` 這個**合成值**表達（設計意圖正確：視口恆為 `maxLinesPerPage` 行高，末頁不足行數時視窗不縮水），而該合成值取自定影快照 ⇒ 字級一變即與真實版面脫節。

**探針實證（35 個候選、`lines: 4`、`isExpanded: true`、`layout: .horizontal`；先在字級 16 之下定影範本 cell，再改字級）**：

- 字級 16：`unifiedTextHeight` 19.0、`lineStep` 23.0、`pageCandidateSize.height` 92.0、實測 cell 高 23.0、第二行原點 y 25.0 ✓ 一致。
- 字級 40（術前）：`unifiedTextHeight` 48.0（**已即時更新**）、`lineStep` **23.0（未動）**、`pageCandidateSize.height` **92.0（未動）**，而實測 cell 高 **42.0**、第二行原點 y **44.0**、`candidateOnlySize.height` **312.0** ⇒ 視口高度只有內容真實高度的三分之一弱，且 `maxScrollOffset` 反被算成 220.0（應為 104.0）——捲動範圍連帶失真。
- 字級 40（術後）：`lineStep` 52.0、`pageCandidateSize.height` 208.0、`maxScrollOffset` 104.0 ✓ 與實測行距 52.0 逐位吻合。

**GSI 視圖層之同一量測（`VwrCandidateGSI4AppKit.fittingSize`，`rendersInScrollMode = true`）**：字級 16 ⇒ `(350.0, 115.0)`；字級 40 術前 ⇒ `(746.0, 137.0)`（高度只多 22 行點——那 22 點是底部欄位隨字級長出來的部分，視口本身紋絲未動）；字級 40 術後 ⇒ `(746.0, **253.0**)`。此即事主所述「最大高度並沒有隨著 candidate font size 而遞增」之直接再現。

## 落點

`CandidatePool4AppKit.swift`：把 `cellTextHeight` 由 stored 快照改為計算屬性，即時讀取全域通用的字級換算（與 `CandidateCellData4AppKit.updateMetrics` 內 `cellDimension.height = unifiedTextHeight + 2 * padding` 同源），並在原地註明「不得自範本 cell 取值」之理由。

```swift
    /// 候選字 cell 的文字高度（跟隨偏好中的候選字字級即時浮動）。
    /// 不得自範本 cell（`shitCell`）取值：範本 cell 的 `textDimension` 只在該靜態成員初次
    /// 初始化時定影一次，行程存活期間更動字級不會更新它，一旦快照化即會讓行步進（連帶
    /// 捲動模式的視口高度）停在舊字級。
    var cellTextHeight: CGFloat { CandidateCellData4AppKit.unifiedTextHeight }
```

`lineStep`（`cellTextHeight + 2 * padding`）與其餘五個消費端一行未動——修在單一真源上，五處同步受惠。刻意**不**改 `pageCandidateSize` 之算式：`lineStep × maxLinesPerPage` 表達「視口恆為整頁高」這一設計意圖（末頁不足行數時不縮水）本身正確，病灶只在取值來源。

## 要解決的問題

事主原文：

> 1. GSI 捲動模式不繪製頂部 pane（unfinished reading）：溢成捲動模式時該 pane 靜默消失。
> 2. 候選字的 candidate key label 的顯示區域得設法保持成一個正方形的面積。不然的話，Candidate Font Size 越大，這 Candidate Key Label 越是顯得窄得誇張。

## 病灶

### 一、GSI 捲動模式之頂部 pane

非捲動模式（TDK 與 GSI 之普通模式）之 pane 走 `CandidatePool4AppKit.updateMetrics()`：該函式量出 pane 尺寸 `dimensionUnfinishedReading`、算出 `topPaneShift = 該高 + padding`、把**全體 cell 之 visualOrigin.y 下移**並把 `fittingSize.height` 加高，`metrics.unfinishedReading` 則記下 pane 之矩形。**三件事在捲動模式全都不成立**：

1. `VwrCandidateGSI4AppKit.drawScrollMode(...)` 從未繪製 `attributedDescriptionUnfinishedReading`（該函式只畫候選格、scroller 與底部欄位）。
2. 捲動模式之視窗高度走 `fittingSize` 之另一分支（`pad + page.height + extraHeight + bottom.height`），未含 pane。
3. 捲動模式之候選區幾何——`clipOrigin`、`drawOffsetX/Y`、`scrollerTrackRect`、`drawBottomFields(topY:)`、`findCell` 之命中點與視埠矩形——全以 `originDelta` 為基準，未計 pane。

且捲動模式之 cell 幾何來自 `computeCandidateOnlySize()`（自 `(0,0)` 起排、不經 `updateMetrics` 之 `topPaneShift`），故**連「cell 被下移」這個副作用都不會發生**：pane 就這樣無聲無息地消失。

### 二、選字鍵標籤之顯示區域

標籤以 `selectionKeyFont()`（monospaced 系統字、字級 `fontSizeKey = max(ceil(0.6 × 候選字字級), 11)`）繪製，其**呈現盒**＝字寬 × 行高（數字之 advance 約 0.6 em、行高約 1.17 em）——即盒之兩邊比約 **1 : 1.95**（窄高）。而顯示區域之橫向留白原為 `phraseDrawXOffset = ceil(size * 0.6)`（＝標籤字級、亦即其字寬），故**顯示區域恰好只夠容納「字寬」，比標籤自身之行高窄上一倍**：字級越大，這個「窄得誇張」的比例越顯眼。

實測（本機，非高亮格）：字級 12 ⇒ 盒 8.0 寬 × 13.0 高；24 ⇒ 15.0 × 17.7；40 ⇒ 24.0 × 28.3；96 ⇒ 58.0 × 68.3；196 ⇒ 118 × 139。

**耦帶發現（本 phase 一併收緊）**：既有之 cell 寬度算式（`textDimension.width + 4 × padding`）在**極大字級**下本就容不下「標籤 ＋ 候選字詞」——以字級 196 為例，候選字詞之起點（`2 × padding + 118`）＋字詞寬（測得 184.9）＝ 306.9 > 該格寬 297，即術前即已超格約 10 點（該算式之「餘裕」約 14 點，係按 1 字型紋理而非實測 advance 估的）。

## 落點

### 一、GSI 捲動模式之頂部 pane（`VwrCandidateGSI4AppKit.swift`）

新增兩個成員，把 pane 之幾何收攏成單一真源：

```swift
  private var topPaneDimension: CGSize {   // 空字串 ⇒ .zero（pane 隱藏）
    let strPane = thePool.attributedDescriptionUnfinishedReading
    guard rendersInScrollMode, !strPane.string.isEmpty else { return .zero }
    let rawDim = strPane.getBoundingDimension(forceFallback: true)
    return CGSize(width: ceil(rawDim.width), height: ceil(rawDim.height))
  }

  private var topPaneShift: CGFloat {      // pane 高 + padding；0 ⇒ 無 pane
    let dimension = topPaneDimension
    guard dimension.height > 0 else { return 0 }
    return dimension.height + thePool.padding
  }
```

六處幾何一併以 `topPaneShift` 下移：`fittingSize`（高＋shift；寬納入 pane 寬）、`drawScrollMode` 之 `clipOrigin` 與 `drawOffsetY`、`scrollerTrackRect` 之 y、`drawBottomFields(topY:)`、`findCell` 之命中點（`clickPoint.y -= topPaneShift`）與其視埠矩形（連同 cell 之 view 座標推算）。**軌道高度須與 pane 無關**（＝候選區高 − 上緣圓角留白）：軌道之頂端隨 pane 下移、底端仍貼齊候選區下緣——首版誤將高度亦減去 shift，令軌道短掉一個 paneShift（直立軌道；見〈驗證〉之複核記錄）。pane 本身繪於 `(originDelta, originDelta)`（與 `updateMetrics` 之 `rectUnfinishedReading` 同座標）——**不隨捲動移動**。另：clip path 之快取鍵補上 `lastClipOrigin`（pane 之出現／消失會平移裁切矩形，只比對尺寸會取到過期路徑）。

### 二、選字鍵標籤之正方形顯示區域（`CandidateCellData4AppKit.swift` ＋ 兩視圖）

```swift
    /// 選字鍵標籤之顯示區域：正方形，邊長取其自身之行高。
    var keyLabelBoxSide: CGFloat {
      let keyFont = selectionKeyFont()
      return ceil(keyFont.ascender + abs(keyFont.descender) + keyFont.leading)
    }
```

`updateMetrics` 內：`phraseDrawXOffset = keyLabelBoxSide`（候選字詞自正方形右緣起排）、`headerDrawXOffset = ceil((keyLabelBoxSide - 標籤字寬) / 2)`（標籤水平居中於其盒內）；並新增「標籤盒 ＋ 候選字詞」之硬約束：

```swift
      let keyAndPhraseWidth = keyLabelBoxSide
        + makeAttributedStringPhrase(isMatrix: false).size().width
      cellDimension.width = max(cellDimension.width, keyAndPhraseWidth + 2 * padding)
```

四處繪製點（TDK 1 處、GSI 3 處：捲動模式兩分支與普通模式）改用 `visualOrigin.x + 2 * padding + cell.headerDrawXOffset`；TDK 之候選字詞偏移由行內算式 `ceil(size * 0.6)` 改讀 `cell.phraseDrawXOffset`（與 GSI 一致）。

### 補記（2026-09-19）：標籤之墨跡光學居中（事主複驗回報之追加修正）

事主回報原文：

> 空間倒是騰出來了，但這個 candidate key text glyph 的位置看上去卻是在這個空間的 center-trailing 位置對齊的。換言之，center-leading 過大、center-trailing 過小。我在懷疑是不是需要從 NSAttributedString 組裝的角度干涉這個：candidate key text 左側的 space 的 fontsize 變小一些、candidate key text 右側的 space 的 fontsize 變大一些。

**量測（先確認現象，再動手）**：以離屏渲染掃描非高亮格之標籤墨跡，量其於正方形區域內之左右留白：

| 字級 | 區域邊長 | 左留白 | 右留白 | 差（正＝偏右） |
|---|---|---|---|---|
| 24 | 18.0 | 5.5 | 4.5 | **+1.0** |
| 40 | 29.0 | 9.5 | 7.5 | **+2.0** |
| 96 | 69.0 | 20.5 | 20.0 | +0.5 |

### 程式碼變更

### 病灶與手法

**病灶一：動態注音排列在混打下失效。** 原碼以「**鍵數 == 佔用槽數**」作「整段為單一音節」之代理量（`hasNoDestructiveOverwrite` 與 `bufferIsSingleSyllablePhonetic` 之末行），該等式**預設一鍵一槽**；動態排列之合法編碼本即跨鍵改寫槽值（大千26 之 `qquu`＝ㄅㄚ 為 **4 鍵 2 槽**），故該式對動態排列恆不成立。原碼對此之因應是**兩處區域豁免**——`case .ofDachen26: 6 // 這是酷音大千26鍵的顯著缺點`（`maxSingleSyllableKeyCount`，僅放寬上限）與兩道 `guard handler.composer.parser != .ofDachen26 else { return false }`（直接把檢查整條停用）。豁免本身即是病灶之證：停用之後，大千26 使用者打純注音（`qquu`）不但沒被吸收、反而**整串滯留為 ASCII 並於 Space 時被當英文遞交**。**手法**：改以 `handler.composer.isSequentiallyTypedRawKeyOrder(fullInput)` 為動態排列之判準——該 API 之條件五對動態排列本不生效、條件三又只以「最終值首見鍵序」為準（正為動態排列之合法多寫編碼而設；Phase 233 曾以五個動態排列、7337 筆語料於 `suffixOnly: true` 下逐筆檢證零誤殺）。兩道豁免一併移除。

**病灶二：短英文 token 之亂序判定缺位。** `shouldPreferASCIIWordPath` 原以「非前進式槽消耗」之**計數**為英文證據，並內建 `count >= 3` 護欄，故**兩字母之純英文字母緩衝永遠不會走 ASCII 偏好路徑**；於是 `ls` 這類「槽序上不可能這樣打」的 token 被 `bufferIsSingleSyllablePhonetic` 收為單一音節（`l`＝ㄠ 佔韻母槽、`s`＝ㄋ 佔聲母槽；引擎層因 CSVT 未強制而容忍，`isPronounceable` 又只看「三槽有無內容」）。**手法**：於該函式新增**第二項證據**——`isNotSequentiallyTypedReading(_:)`（`!isSequentiallyTypedRawKeyOrder(text)`，僅對「全為 ASCII 英文字母且長度 ≥ 2」者有定義）。兩項證據以 OR 結合，任一成立即偏好 ASCII。

**證據二之適用範圍一併收窄至靜態排列**：動態排列之合法編碼本即跨鍵改寫槽值，計數無意義（`qquu` 之計數為 2，若不放行則會反過來阻斷病灶一之修正）。故該計數僅於 `!parser.isDynamic && !isPinyinMode` 時計算。

### 術中發現：「冗餘鍵」在混打語境下不可放行（關鍵，且與 Phase 233 PostReport 之建議相左）

PostReport §8 曾建議「**替換**（第一階）／收斂（第二階）」條件五 ↔ 長度代理量，並在 §3.1 指出現行七處近似之收斂價值。實作後**測項 `test_IH400_MixedAlnumKanjiInputTest_Izanami`（前綴 `ai`）當場紅 4 筆**（ㄛˊ 之 `aii6`、ㄨˇ／ㄨˊ／ㄨˋ 之 `aij3`／`aij6`／`aij4`），症狀為「`ai` 前綴未被遞交、整段 `ㄇㄛˊ` 被當成單一讀音「模」」。

**根因**：`aii6` 之鍵序為 `a`(ㄇ) `i`(ㄛ) `i`(ㄛ，**同值重寫**) `6`(ˊ)——其**冗餘鍵**（第 3 鍵未佔新槽）在 P233 之條件五下**不構成違規**（「同值之重寫不留下可觀測之變化、亦不影響判定」，此為該 API 之明定界線、且為動態排列所必需），故 P233 判其為合格讀音；然在**混打語境**下，該冗餘鍵恰恰是「ASCII 前綴 ＋ 注音後綴」之分界證據（此即使用者打出 `ai`＋`i6` 而非 `ai6` 的原因），放行即令切分消失。

**處置**：**靜態注音排列維持「鍵數 == 佔用槽數」**（該式即「無冗餘鍵」，比引擎層判準略嚴——另含同鍵之重寫），僅**動態排列**改委由引擎層判準。此一分工同時滿足三項約束：動態排列之合法多寫編碼得放行、靜態排列之冗餘鍵分界得以保留、兩者共用同一份權威（`isSequentiallyTypedRawKeyOrder` 之條件三／五及其 `isDynamic` 分流）。**教訓**：`isSequentiallyTypedRawKeyOrder` 回答的是「這是否為一個打得出來的讀音」；混打所要問的是「這是否為**這一整段**讀音（nothing else）」——兩者對「同值重寫」之寬容度不同，不可直接互換。
