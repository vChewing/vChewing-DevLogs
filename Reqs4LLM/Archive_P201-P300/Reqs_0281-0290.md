## 要解決的問題

- **組字期間之客體熱鍵全滅**：實測（合成事件壓送真 `InputSession`）——空狀態時 `Cmd+Ctrl+W`／`Cmd+Ctrl+C`／`Cmd+W`／`Ctrl+W` **皆已放行**；而組字區非空時（`su3` 後之 `.ofInputting`）前四者**一律 `handled == true`**，連本不屬任何輸入法功能之 `Cmd+W` 亦然。客體（Chrome）之 `Cmd+Ctrl+C`／`Cmd+Ctrl+W` 因而無從送達。
- **病灶＝終末處理之盲區**：`InputHandler_TriageInput` 之終末處理（`vCLog("Blocked data: …")` ＋ `errorCallback?("A9BFF20E")`）是「誰都沒認領」之終點，原樣吃掉一切落網者；全倉唯一之 Command 放行口 `isSingleCommandBasedLetterHotKey`（`InputSession_HandleEvent`）**只及空狀態**、且要求旗標全集**恰為** `[.command]` 或 `[.shift, .command]`，`Cmd+Ctrl+` 連形狀都不符。選字窗／符號表分支另有一處同型攔截（`handleCandidate` 未認領者一律回 `true`），其泛用蜂鳴碼為 `172A0F81`。
- **第二層病灶（事主實機驗收指出）**：**只交還仍不足**——客體在輸入法持有內文組字區（marked text）期間不執行自己的 Command 系熱鍵，故 Chrome 依舊吃不到 `Cmd+Ctrl+C`／`Cmd+Ctrl+W`。須**先遞交既有組字內容、再交還該事件**。
- **mozc 之對照（事主指定研究）**：`~/Repos/_LABS/mozc-latest/src/mac/mozc_imk_input_controller.mm` 之 `handleEvent:client:` **只在引擎確有消費時才回 `YES`**——鍵碼映射失敗、`DIRECT` 模式下非直通指令、`SendKeyWithContext` 失敗，皆逕回 `NO` 交客體（尾端 `return output.consumed();` 即此紀律）。

## 落點與理由

- **於既有之三處終末攔截各自讓位，不新增關卡**：終末處理在定義上即「輸入法自身無任何處理」之所在，於彼交還**不可能奪走唯音自己的任何功能**；而帶 Command 之組合鍵不會產生文字資料，故交還亦無「組字區與客體文件失去同步」之顧慮（後者正是該段攔截存在的理由）。① `InputHandler_TriageInput` 之終末處理；② 選字窗／符號表分支（`.ofAssociates` 仍照舊轉空態重分診）；③ `InputHandler_HandleCandidate` 尾端之泛用碼 `172A0F81` 之前**靜默回報未認領**，俾分診端接手。**`Ctrl+Cmd+[`／`]` 之候選輪替位於候選處理之更前處**，該輸入法功能不受影響。
- **交還之前必先遞交**（`releaseUnclaimedCommandChord()`）：其內走 `session.resetInputHandler()`——**即 IMK 之 `commitComposition:` 所用的同一條路**（遞交 `committableDisplayText` 與混打緩衝、並收斂至空狀態），故未完成讀音之去留一律照既有偏好 `trimUnfinishedReadingsOnCommit` 決定，**不另立判準**；無未遞交內容時該函式不動作（空狀態行為與手術前一致）。
- **判準只認 Command**（`isCommandShortcutChord` ＝ `isHoldingAny([.command])`）：不帶 Command 之 `Ctrl`／`Option` 組合鍵仍可能是文字資料（控制字元），吃掉才是正確的——故 `Ctrl+W` 於組字期間照舊攔截並發 `A9BFF20E`（`test522` 固化此界線）。
- **駁回之選項**：① **只交還而不遞交**——實機不足（事主回報），故本 phase 第二筆提交改為先遞交。② 改在 `isSingleCommandBasedLetterHotKey` 上放寬旗標集合——該屬性之語意為「單一 Command 系字母熱鍵」且用於空狀態快篩，放寬會令其名實不符，且仍解不了組字期間。③ 令終末處理整段讓位（不設判準）——F1－F12 干擾組字區之舊疾（P243 守護）會立刻復發。④ 一併交還 `Ctrl`／`Option` 系——見上條，會把控制字元漏進客體文件。

## 已知界線

- 本 phase 之驗證止於引擎層與單元測試：事件以 `KBEvent` 合成（鍵碼與旗標等效於真 `NSEvent`），**未於真機 Chrome 內實地按鍵**——「先遞交即令客體吃得到熱鍵」係事主之實機判斷與本案之實作依據，本環境無法複驗。交還後之鏈路（`IMKSwift.m:314-317` 原樣交客體）屬既有行為，未動。
- **行為變更（刻意、及其代價）**：此後凡「輸入法未認領之 Command 系熱鍵」在**非空狀態**下，會**先把既有組字內容遞交出去**（如 `Cmd+S`／`Cmd+A`／`Cmd+Z` 亦同）。此為事主裁定之代價；空狀態與 `.ofAssociates` 之既有語義不變。
- **併跑兩倉 `swift test` 會互踩**：實測同時起跑時兩邊各有 55 項 `InputHandlerTests_Cases1` 之 cassette／狂打測項轉紅（`calligrapher` 空、`furiousTrail` 空），**單跑皆全綠**——係測試環境之既有性質（共用之使用者資料路徑／偏好 suite），非本 phase 引入，亦不在本次手術範圍。
- 只及「輸入法未認領」者：已認領之 Command 系組合鍵（`Ctrl+Cmd+[`／`]`）不受影響。`Shift+Cmd+` 系亦在交還面內——`areWeNerfing`（`= commonKeyModifierFlags == [.shift, .command]`）之讀取點僅 `performUserPhraseOperation(addToFilter:)`（`.ofMarking` 之選單動作），且其賦值早於 `triageInput`，故不受影響。
- `isCommandShortcutChord` 為協定擴充之預設實作（與 `isFunctionKey` 同款），macOS 側之 `NSEvent` 免費取得同一語意；Linux 側無 Command 旗標此概念，恆為假。
