#### ★ 兩軸命名規則（事主裁定）

> **名字指「模式／鍵盤家族」者留 `Zhuyin`；名字指「切分機制與其提交物」者用 `Phonabet`**（拼音側則用 `Pinyin`，因其提交物是 romaji）。

推導自 ⑤：機制是**族中立**的，族只決定哪一臂跑。以一臂之名去命名族中立之機制，會使後續讀者以為拼音側是特例。

| 現名 | 處置 | 理由 |
| --- | --- | --- |
| `shouldAutoChopZhuyin(byTyping:)` | → `shouldAutoChopPhonabets` | 收 `Character`、以「本鍵施於空槽」試跑——機制不依族 |
| `zhuyinAutoChopSlots()`／`zhuyinAutoChopHighestFilledSlot(_:)` | → `phonabet…` | 回傳的正是四個 phonabet 槽（**比原名更準**） |

| `performPinyinAutoChopIfNeeded` | **不動** | 運送 **romaji**、以 `replacePinyinBuffer` 重建——**是另一種機制** |
| `ZhuyinAutoChopPredicateTests`（檔名／`struct`／`MARK`） | → `PhonabetAutoChopPredicateTests` | 依賴面與族無關 |
| 兩支測試函式名 | → `phonabet…` | 同上 |
| `InputHandlerTests_ZhuyinFurious.swift` | **不動** | 驗的是**模式**，非機制 |
| `isZhuyinFuriousTypingModeEffective` | **不動** | 模式真值；與兩個同族旗子同性質 |

**候選名之取捨**：`Phonabet`（採）＞ `Phoneme`（會在同一件事上引入第二個術語；本倉已有 `Tekkon.Phonabet`／`allowedPhonabets`／`mapHanyuPinyinToPhonabets`／`SymbolCategory.Phonabets`）。

#### 檔名之取捨

事主原提案 `Tekkon_Composer_PhonabetAutoChop.swift`，經評估後改為 **`Tekkon_PhonabetAutoChop.swift`**：Tekkon 六檔一律 `Tekkon_<名詞>`（`Constants`／`Phonabets`／`PinyinTrie`／`SyllableComposer`／`SyllableIndex`／`Utilities`），**無 scope 前綴、無雙底線**；且 `Composer` 一詞在 Tekkon 內已由 `SyllableComposer` 佔用。另一條正面理由：`SyllableIndex`／`PinyinTrie` 皆為**獨立型別放在 Composer 之外**，而本判準實質上是「Composer 狀態 ＋ 本鍵 → 裁決」之純函式，與 `SyllableIndex` 同類。

#### 紅線之判讀（可重用之通則）

**先讀其自陳之理由，再讀其禁令。** §3.3 之「Tekkon 不得新增任何知曉『狂打』概念之 API」看似禁止本 phase，但其自陳之理由為「Tekkon 是**無狀態偏好、無會話概念**之音節組裝器」⇒ 該半句指**行為**而非**命名**；兩項反例（見〈五項查得〉之 ④）已存在於生產碼。故 §3.3 就地補〈範圍釐清（v26）〉，**免後人再誤判一次**。

#### CI 第一輪：Linux「誤切 7366 次」

**症狀**：判準靶①「不得在單一音節內誤切」報 **7366** 次誤切，全數為「鍵＝反引號」，全落在單音節前綴。

**根因（與 Windows 共用一條）：靶自建了「按鍵域」，而未自資料取用排列之按鍵域。**

1. **`candidateKeys` 誤收反引號與空格**。該常數是「把候選鍵餵進空 `Composer`、看它填哪一槽」之**探針集**（用以反推靜態排列之鍵表），而反引號與空格**不是任何出廠排列之按鍵**：素材檔內它們只作「本排列無此鍵」之標記（`` `NULL``、以及源自 `__` 之尾端空格）。探針集一旦收之，反推即把它們登記成某注音符號之按鍵 ⇒ **由合法讀音之前綴生成出不可鍵入之鍵序**；判準對「非按鍵」之反應本即**無定義**，各平台遂各自為政——而這正是回歸靶絕不該依賴者。
2. **語料閘過寬**：原為 `!cell.hasPrefix("`")`，凡標記不在首字元、或尾端帶空格之單元格皆矇混過關 ⇒ 改為**逐格校驗鍵面字元**（ASCII 字母或數字），兩種標記形狀就地登錄。實測剔除 38/1485 ＝ **2.56%**，全為該兩種標記。
3. **魔數下界改為結構量**：原以 `steps > 29_000`／`checked > 100_000` 間接失手，無從分辨「檔案沒讀到」與「讀到了但濾掉幾列」⇒ 改為同時曝露未濾列數與過濾後列數，下界表達「成規模」與「損失 ≤ 5%」。
4. **迴歸釘**：新增斷言「反推所得之按鍵一律須為鍵面字元」——把反引號放回探針集即當場轉紅並列出違規鍵（**此即驗證方式**）。

#### CI 第二輪：Windows「整批讀不到」

**症狀**：`AutoChopCorpus.rows` 為空、②「交界須切」受檢 0；而**新加之行數斷言報出 `rawRowCount == 0`** ⇒ **連錨點搜尋都未執行**，即檔案根本沒開成功（此即「診斷先於修法」之收益：症狀由「某魔數失手」變成「明確告知讀取失敗」）。

**修法**：① **候選路徑清單**——`URL(fileURLWithPath:).appendingPathComponent("A/B")`（Darwin 正解）／`(NSString).appendingPathComponent("A/B")`／顯式反斜線接法／顯式冒號接法，依序試並**全數回報**（附 `#filePath` 原值、以及「讀到但錨點不在」時之前 120 字）；② **行尾正規化**（`\r\n` → `\n`，Windows 之 checkout 可能回 CRLF）；③ **候選迴圈不再於「讀到但解不成 UTF-8」時中斷**（可能只是挑錯檔，其餘候選應續試）。

**已知界線（明列）**：此三項**同批入版**即綠 ⇒ **無法逐項歸因**——真因落在其中哪一項、或需兩項合力，未經隔離實驗確認。**後續如再遇同型症狀，第一件事是讀診斷字串**，而非再猜路徑形制。

#### 三則可重用之通則

1. **回歸靶之輸入域必須自資料導出，不得由靶自建**——靶自建之鍵域一旦含「非按鍵」，即等於把無定義之行為當成規格來測。此為「**靶綠而 CI 紅**」之典型：缺陷在**測什麼**，不在**測得對不對**。
2. **語料類靶須能分辨「沒讀到」與「讀到了但濾掉幾列」**——只寫下界魔數會使兩者同形；應同時曝露原始列數與過濾後列數，並以下界表達「成規模」而非釘死數字。
3. **大型靜態初始值之複雜推導會撞編譯器**——原解析器寫成「對切片之單一 `compactMap` 閉包」**令 swift-frontend 6.4 於 `TypeCheckPrimaryFileRequest` 崩潰**（`Please submit a bug report`）；改寫為帶型別標註區域變數之樸素 `for` 迴圈即過。**此形之大型靜態初始值宜預先拆解。**

#### 方法學記錄：「症狀已定位」≠「根因已定位」

CI 第二輪時之提交訊息曾斷言「路徑運算即可能之因、改寫已處理之」——**為時過早**，事實證明該改寫未解決 Windows。**日誌可確證「檔案沒讀到」（症狀），惟真因須待修法入版後之複驗**；更正已寫入該筆提交之訊息。**凡修法未經複驗者，措辭不得由「疑似」升為「已修」。**
