# 12.6 工作細節附註（一）：語系、語體、術語、命名與文案

> 本檔之條目係**依主題**自原 §12.6 抽出（原檔為時間序），共 16 條；
> 各條之次序仍照原檔。原行號： 625, 626, 627, 628, 629, 637, 641, 648, 649, 657, 658, 683, 704, 706, 726, 728 行。

- 交差前注意與 L10n 有關的內容是否全部補齊。
- **zh-Hans 之語體一律為「zh-Hans-TW」（臺灣華語、簡體字形）、非大陸普通話（事主 2026-09-24 明示）**：凡新增／修訂 zh-Hans 文案者，須先沿用本倉 zh-Hant 之對應用語、再轉為簡體字形，**不得**逕採大陸慣用語。實查之對照（本倉 zh-Hant → 本倉 zh-Hans；括號內為**不得**採用者）：**剪貼簿 → 剪贴簿**（剪贴板）、**匯入 → 汇入**（导入）、**套用 → 套用**（動詞；`应用` 於本倉只作名詞「客體應用」即 app）、**設定 → 设定**（设置）、**資料 → 资料**（数据）、**視窗 → 视窗**（窗口）、**選單 → 选单**（菜单）、**軟體 → 软体**（软件）、**標幟 → 标帜**（标识）、**拷貝 → 拷贝**（复制）、**無法讀取 → 无法读取**（“无法”與“读取”兩岸同形、可用）。四語系 `.strings` 為**全域排序**（`LocalizableFileSorter.swift`），任何增刪皆須以「複本跑排序器後逐位元組比對」複驗。
- **★ zh-Hans-TW 之稽核法（P292，2026-10-10 實證）**：以 `CFStringTransform(…, "Hant-Hans")` ＋ `Scripts/Markdown2HTML/derive-zh-Hans.swift` 之 11 組 `glyphOverrides` 把 zh-Hant 對位值轉簡體後與 zh-Hans 逐鍵／逐行比對，凡不符即偏離；大陸詞表法既會誤（ja 之「半角」「字号」為日語正字）亦會漏（「字號」於 zh-Hant 同形）。
- **ja：凡指「可交換之配置檔（exchangeable configuration profile／配置包）」此一義之 `configuration` 時，一律作「配置」、**不得**作「構成」**（事主 2026-09-24 明示，並界定此為該詞在此義下之定譯）——「構成」於本倉只作「系統構成部品」一類之**他義**（實查：`aboutWindow.DISCLAIMER_TEXT`、`InfoMessage.EndOfIMKCandidatesExplanation`），**非此義者不在此限、不必強改**。ja 之既有慣例（實查）：`読み込(む)` 優先於 `インポート`（16 : 1）、`環境設定`＝preferences、`適用`＝apply、`クリップボード`＝clipboard。
- **`i18n:Settings.ImportConfigFromClipboard`**（事主 2026-09-24 命名；舊為 `…ImportFromClipboard`）＝「自剪貼簿匯入配置資料」按鈕之五態 alert 文案群（11 條）＋ `i18n:AssistantConfig.Meta.{Unspecified, NoDescription}` 2 條；其 Swift 端落點為 `Packages/vChewing_SettingsUI/Sources/SettingsUI/PrefsExchange.swift`（`Preparation.alertTitle`／`alertMessage`）。
- **Phase 文書之用語與署名（事主 2026-09-18 定調）**：① Phase 檔頭之 `Assignee:` 行**必須同時寫明 Model 與 Harness**——形如 `Deepseek-v4-flash（Codewhale harness）。`；只寫「（harness）」而未冠 harness 之名、或把 harness 之名填進 model 位者（如 `Codewhale（harness）`），皆屬誤標。② 文書提及 GitHub issue 之發起人時：**非 ShikiSuen 者一律稱「工單樓主」**；「事主」一詞**專指 ShikiSuen 本人**（含其於 issue 串／討論區內之發言在內）。
- **設定面板之兩側命名與「Section」之形制（2026-09-25，Phase 247／248 實查）**：事主口語之 **「SessionUI」／「SessionCocoa」**即本倉 `vChewing_SettingsUI` 套件內之 **SwiftUI 面板**（`Sources/SettingsUI/SettingsUI/VwrSettingsPane*.swift`）與 **AppKit 面板**（`Sources/SettingsUI/SettingsCocoa/VwrSettingsPaneCocoa*.swift`）；全倉並無 `SessionCocoa` 一字，phase 文書見此用語時應據此對位。同一個「Section」在兩側形制不同：SwiftUI 側是 `Section { … }`（語言構造）；AppKit 側是 `NSStackView.buildSection(width:) { … }?.boxed()`（`vChewing_OSFrameworkImpl` 之工廠函式 ＋ 外框，`withDividers: false` 即令同段各列之間不留分隔線）。**分段即兩側唯一之視覺分群手段**——本二面板之各段皆無標題（原始碼內之 `// MARK: (header: Text("…"))` 是**註解**、非實作），故一個 `Section` 就是使用者在畫面上看到的一個帶框方塊。
- **★ 「位置即判準」之文案裁定，其護欄必須用 `indexOf(...) === 0` 而非 `>= 0`（2026-09-26，Phase 259 實錄）**：事主裁定 `kFuriousTypingEnabled4Zhuyin` 之 `description` 須**在最開頭**顯示警示句（「⚠︎ …」，因為插在其他位置不醒目）。此類裁定之**內容就是位置**——若護欄只驗「字串內含該句」，則任何人把警示挪回句中都不會轉紅，護欄形同虛設。故斷言取 `indexOf('\u26a0\ufe0e') === 0`，並另驗含換行（警示行須獨立成行）。**配套事實**：`.strings` 內之 `\n` 轉義，經助手導出後在 JSON 內是**真換行**——故得以 `indexOf('\n')` 驗分行。
- **★ 同一件事別在一條偏好字串內說兩次（2026-09-26，Phase 258／266 實錄）**：P258 曾在 `kFuriousTypingEnabled4Zhuyin.description` 之**句中**補一句「惟若已啟用『中英混合輸入回退』…」；P259 事主改令該警示**置首**。兩句並存會有兩個毛病：① 冗餘；② **兩種稱謂**（句中用偏好之 `shortTitle` 用語「中英混合輸入回退」、置首句用事主口語「中英文輸入回退模式」）——同一條字串內自我不一致。**處置**：以事主指定之句為唯一出處、移除句中那句。**一般化**：`description` 之警告宜**單一出處且置首**；若同一事實需要兩處，寧可改寫成互補（成因／處置）而非重述。**另一則**：該警告之**稱謂**初照事主口語原句（「中英文輸入回退模式」）而與偏好 `shortTitle`（「啟用中英混合輸入回退」）不一致，事主隨即更正（「我剛才寫錯」）⇒ **引用他項偏好時，一律用該偏好自身 `shortTitle` 之正式稱謂**，勿照口語原句抄——否則使用者拿警告裡的字去設定介面找，會找不到同名的開關。
- **★ 兩軸命名規則（2026-09-26，P261，事主裁定）**：**名字指「模式／鍵盤家族」者用 `Zhuyin`／`Pinyin`；名字指「切分機制與其提交物」者用 `Phonabet`**。故 `shouldAutoChopZhuyin` → `shouldAutoChopPhonabets`，而 `performPinyinAutoChopIfNeeded` **不動**（其運送之物是 romaji，族名有實義）——**此不對稱正是該規則之要旨，不是漏改**。**改名之最佳時機是「尚未出貨」時**：一旦隨發版出貨，改名即須等破壞性窗口。**凡「為求明確而加 scope 前綴」之提案，先查該目錄是否本來就不加。**
- **★ 文案會隨行為漂移——改動某模式之行為時，同一 phase 內即須回檢其文案（2026-09-26，P258／P259 實錄）**：P258 改了注音側之空格語義，P259 剛寫下之 `description` 當場有兩處失效。**「補上既有行為之說明」亦屬準確性之補正**（缺載與誤載同屬不準確）；**「不動」也是審計之結論，須明寫**。**並**：凡「統一文案」之裁定，**皆應落成一支護欄**（如「任何標籤不得含舊稱謂」），否則必然漂回。**引用他項偏好時，一律用該偏好自身 `shortTitle` 之正式稱謂**，勿照口語原句抄。
- **★ 窗體縮放動畫期間，繪製之矩形一律取視圖當下之 `bounds`，不得取佈局之終值（`fittingSize`／`metrics`）（2026-10-06，P288）**：終值在動畫起步時即已是最終尺寸，取之則收縮時該矩形提前收妥、窗體尚未及之部分留下一條未著色之破口（其下之 effectiveView／glass 遂透出）；生長時則圓角被裁掉。**背景視圖若以 Auto Layout 釘齊容器，於 `setFrame` 前手動指派 frame 毫無作用**——下一拍即被版面配置覆蓋（實測 480→160→480）。
- **★ `Arimitsu` 之命名緣起（2026-10-12，事主補述）**：該名源自**漢語拼音發明人周有光**——取其名「有光」之日文漢字音讀（ありみつ／Arimitsu）為模組名。其為人名之音讀轉寫、**非字面語義詞** ⇒ 凡「正名」、翻譯或重構時不得擅改；同理，該模組之別稱亦不得改以「雙拼／Dualpin」一類功能詞代替。
- **★ Schema 之標題自持（2026-10-12，P301 事主指示）**：每份 Dualpin schema 皆具 `rawTitle: String`（空 ⇒ **E7**）與 `localizedTitle: [String: String]`；鍵形以 **Apple（BCP-47）形**為準（`zh-Hant`；`-` 連接、不寫 region variant）；比對大小寫不拘、`_` 與 `-` 等價，故 ICU 形 `zh_Hant` 亦命中；解析序＝精確標籤 → 去區域（`zh-Hant-TW`→`zh-Hant`）→ 語言主標籤（`zh`）→ `en`（缺 ⇒ **W8**）→ `rawTitle`；API `title(forLocaleTag tag: String) -> String`——參數係**語系標籤字串**而非 `Locale`：公開面不引 Foundation 型別，以與 Tekkon 之 C++／C# 版共有之純值語彙相容（`_`／`-` 等價即為 Apple 之 `zh-Hant_TW` 一類與 ICU 之 `zh_Hant_TW` 兩形而設）。理由：使用者自備 JSON 之標題不可能預先落於 app 之 `.strings`，故標題須隨 schema 自持（內建亦然（收官後兩案）：微軟＝微軟雙拼／微软双拼／`Microsoft`（en／ja）、GB/T＝四語系皆 `GB/T 34947-2017`，智能ABC／拼音加加／搜狗／紫光華宇／自然碼各具四語標題）；此舉亦解「內建顯示名」之懸問。五案之四語標題改隨官網倉 JSON 之 `localizedTitle` 供給。
- **★ `String.makeNSLabel(fixWidth:)` 之回傳型別係 `NSLabelView` 而非 `NSTextField`（2026-10-12，P303 實錄）**：其為 `NSView` 子類、**無** `stringValue`；就地更新須以 `attributedStringValue = NSAttributedString(string:)`（先例 `CtlSettingsCocoa.swift:444`）。誤宣告為 `NSTextField` 即編譯失敗（`cannot convert value of type 'NSLabelView' to closure result type 'NSTextField'`）。
- **★ 後置聲調覆寫之提示字串末尾恆附聲調記號（2026-10-13，P304；事主交辦）**：`BPMFFullMatchTypewriter.performRearIntonationOverrideIfNeeded` 之 `.success` 臂把提示自「既有文案」改為「`\(既有文案) (\(聲調記號))`」——**於呼叫點拼接、四語 `.strings` 一字不動、無新 i18n 鍵**（記號係語言中立之符號）。投影：注音之**陰平於引擎內係 U+0020 空白字元**（`Tekkon.allowedIntonations` 之首案、`mapArayuruPinyinIntonation` 之 `"1"` 亦映射至此），示人時改以 **`ˉ`（U+02C9）**；`ˊ`（U+02CA）／`ˇ`（U+02C7）／`ˋ`（U+02CB）／`˙`（U+02D9）四者恆等。先例：`narrateTheComposer` 早以同一枚 `ˉ` 為陰平之朗讀記號。**陰平仍得經覆寫鍵抵達**——`guard !input.isSpace` 只擋空白鍵，而漢拼側之 `1` 鍵即陰平。測試用例 `IH-Narration-005`（五聲輪替；欲令同調亦覆寫須把 `specifyIntonationKeyBehavior` 設為 0）。
