## 落點與理由

- **判準**（初版沿用參考稿 Tekkon 倉 `05359eb`，複核後補完）：指按鍵者→`空白鍵`；指字元（分隔、插入值、寬度、ASCII／NBSP、縮排、陰平佔位）者→`空白字元`；**bare「空格」之動作義（按／敲／雙擊／固化／確認）→`空白鍵`**。參考稿只涵蓋「恰為字元義」之諸例，未暴露此分歧——係提交後抽查官網 diff 之「按鍵行為（空白字元、Tab、Shift、Caps Lock 等）」才發現，遂三倉全量重判（18 檔誤判）。

## 要解決的問題

- 事主交辦（逐字）：「新增功能：允許將 Space 插入組字區。」細則：`LXFacade` 提供 `_SPACE_HW`／`_SPACE_FW` 之 Unigram 或在 Typewriter 層直接送；偏好新增「插入空白字元（內文組字區）」、既有「插入空白字元」更名為「先遞交當前內容、再插入空白字元」、值域擴至 `-1 .. 2`；助手得對微軟新注音啟用（實作細節見下）。
- **動工前盤點：功能不存在。** 兩符記在兩倉全樹零命中；既有唯一痕跡是限長路徑（以裸 `" "` 插鍵、無偏好閘、只服務黑名單 App）。故本 phase 是**新做**。

## 落點與理由

- **虛擬索引鍵**（`LXFacade.swift`）：新增 `LXAssembly.VirtualSpaceKey`（`halfWidth = "_SPACE_HW"`／`fullWidth = "_SPACE_FW"`、`var charValue: String`（`" "`／`"　"`））。**為何另取虛擬鍵**：讓組字區內的空白享有與其它節點相同的組字器語義（可游標移動、可一同遞交），且不與「用於分隔讀音的實際空格」混淆。**必須就地合成**：`Homa.Assembler.insertKeys(_:)` 插鍵前必經 `gramAvailabilityChecker`（＝`hasGrams(for:)` ＝ `hasUnigramsForFast`），無元圖即 `throw Homa.Exception.givenKeyHasNoResults` 並還原 `segments` ⇒ 辭典查無此鍵即無從插鍵。改動三處：新 `virtualSpaceGram(forKeyArray:)`；`hasUnigramsForFast` 於 `guard noEmptyKey` 之後承認之；`unigramsFor` 於既有 `if flatKeyArray == [asciiSpace]` 早退旁加掛同一早退（**不進 LRU 快取、不走濾除表等後處理**）；`hasUnigramsFor` 走 `unigramsFor` 故自動成立。
- **偏好值域與選項**（`UserDef.swift`）：`validNumeralValueRange` 由 `0 ... 2` 改 `-1 ... 2`；`options` 增 `-1: "i18n:….option.-1"`。負數 option key 有先例（`kSpecifiedNotifyUIColorScheme` 之 `-1 ... 1`）；兩側渲染皆依 key 升冪 ⇒ `-1` 自動置於選單之首。**出廠預設仍為 1（呼出選字窗）**。
- **分診**（`InputHandler_TriageInput.swift`）：真實次序：`triageByState` 內**先 `handleComposition(input:)`**、才輪到 `triageByKeyCode()`（`.kSpace` 分支住於後者）⇒ 有未完成讀音或混打緩衝時，空白鍵在前者就被打字機吃掉。`.ofInputting` 段於**混打委派之後**、既有 fallback 之前加 `-1` 分支（附「一邊吃一邊屙」之 `commitOverflownComposition`），守衛為 `effectiveSpaceKeyBehaviorAgainstICB == -1, !spaceRevolutionBanned, !assembler.isEmpty, let spaceKey = virtualSpaceKey(for: input)`。既有之 Shift+Space 反向輪替塊增一道 `effectiveSpaceKeyBehaviorAgainstICB != -1`——否則 Shift+Space 一按下即被無條件接走、`-1` 之全形插入永遠輪不到（值 0／1／2 之下該條件恆真 ⇒ 既有行為分毫未變）。檔尾增 `private func virtualSpaceKey(for input:) -> String?`：持 Option／Control／Command 者回 `nil`（放行客體），否則 Shift ⇒ `_SPACE_FW`、不帶 ⇒ `_SPACE_HW`。
- **混打層降級**（`InputHandler_MixedAlnumConfig.swift`）：新增 `isMixedAlphanumericalLayerInEffect`（＝ `currentTypingMethod == .vChewingFactory && typingMode != .cassette && !composer.isPinyinMode && prefs.mixedAlphanumericalEnabled`）與 `effectiveSpaceKeyBehaviorAgainstICB`（混打層生效時把 `-1` 讀作 `0`）。六個消費點（分診三處、`HandleStates` 之值 1 判準、`commitsWholeMixedBufferOnSpace`）一律改讀後者，`HandleComposition` 之分派亦改用前者——**收斂為單一具名不變式**。又：`PrefMgr_Core` 之 `fixOddPreferencesCore()` 原以 `![0, 1, 2].contains(…)` 判定、會把 `-1` 靜默改回 1（**該函式每次 `activateServer()` 都跑**），乃改以 `validNumeralValueRange` 為單一正本（P241 同型病灶）。
- **空組字區之定則**：**組字區徹底為空**（`assembler.isEmpty`）時，空白鍵一概與值 0 看齊、**逕出空白字元**（Space 半形；Shift+Space 之寬度由 `specifyShiftSpaceKeyBehavior4EmptyState` 定之，出廠預設全形），四值皆然——`-1` 亦然（`.ofEmpty` 插鍵分支已**移除**）。理由：否則同一顆空白鍵在第一拍（插節點）與第二拍（已非空 ⇒ 被混打／狂打層一次遞交）便分屬兩種語義。事主實測微軟新注音亦然。

## 三條定則（durable）

1. **混打層生效時，值 `-1` 一律以值 0 解讀**（單一正本：`effectiveSpaceKeyBehaviorAgainstICB`）。
2. **注拼槽尚有未完成讀音時，值 `-1` 不生效**、落回值 0 之語義（守衛 `!spaceRevolutionBanned`）——組字器不允許在讀音槽之前插節點。
3. **組字區為空時，空白鍵一概與值 0 看齊**（不分偏好值）。

三者皆寫入 `UserDef.swift` 之註解與四語系 `description` 之末兩句。狂打固化（`spaceSolidifiedFuriousReading`）仍優先。

## 追加修正（事主回報之怪異行為）

- 事主逐字：「…對 mixedAlnum 的行為沒鎖死：會在 composition buffer 為 empty 的時候打出 in-composition-buffer 的 space、且此時再次敲擊 space 會『commit 當前 space、然後直接往 client 再插入一個 space』…提議 mixedAlnum 模式下把 `-1` 當成 `0` 解讀…你全權解決並 amend-commit。」（回報時**已開啟注音狂打**。）
- 根因：`Typewriter_MixedAlphanumerical.swift` 開頭之分支 `input.isSpace && mixedAlnumZhuyinFuriousInEffect && mixedAlphanumericalBuffer.isEmpty && !isConsideredEmptyForNow` ⇒ 一次遞交 `committableDisplayText() + " "`；第一拍之 `-1` 插鍵令第二拍之 `isConsideredEmptyForNow` 為假 ⇒ 該分支命中 ⇒ 遞交兩顆空白。
- 修法即上列兩則定則。**變異測試**（三處已還原）：存取器 guard 改 `guard false` ⇒ `-068` 得 `["appl"]` ＋組字器殘留 `["ㄍ"]`、`-070` 重現病灶；`PrefMgr_Core` 改回 `![0, 1, 2]` ⇒ 新不變式測試轉紅；`.ofEmpty` 插鍵分支加回 ⇒ `-013`／`014` 各報 4 項失敗（`015` 不受影響）。
