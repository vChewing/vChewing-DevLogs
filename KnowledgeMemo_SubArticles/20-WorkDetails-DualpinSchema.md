# 12.6 工作細節附註（五）：雙拼 schema、引擎與其精簡

> 本檔之條目係**依主題**自原 §12.6 抽出（原檔為時間序），共 10 條；
> 各條之次序仍照原檔。原行號： 697, 698, 701, 703, 705, 707-709 行；另加原檔尾 822, 829 行（其性質同 §12.6）。

- **★ 雙拼類對照表之規則是對「拼音拼寫」作尾綴改寫、不是音位正規化（2026-10-12，P301 研究實證）**：微軟雙拼（Rime `double_pinyin_mspy` 之 `algebra`）逐條作用於拼寫字串——j/q/x 後之 `u`（`ju`／`jue`／`juan`／`jun`）**保持 `u` 鍵**，唯 n/l 後以 `v` 拼寫之 ü（`nv`／`nve`／`lv`／`lve`／`lvan`）上 `Y` 鍵；初期探針曾把 j/q/x 後之 `u` 正規化為 ü、遂把 `ju` 誤編為 `jy`（已廢，凡對照表方案皆須先驗此點）。**另**：`Tekkon.mapHanyuPinyin` 係 **internal**（跨 target 不可讀）——欲取「426 條漢語拼音詞幹」之公開途徑為 `MandarinParser.ofHanyuPinyin.mapZhuyinPinyin!.keys`；而 `Tekkon.SyllableIndex.allReadings` 之 426 條係**注音**讀音、非拼音詞幹（誤用即整盤校驗錯位）。
- **★ 雙拼之非字母鍵：按鍵碼須以 Apple SDK `HIToolbox/…/Events.h` 為準，不可由 Swift 常數名反推（2026-10-12，P301 研究實證；同日經其架構定調訂正）**：`;` 係 keycode **41**（`kVK_ANSI_Semicolon = 0x29`），**不是**符號選單鍵——符號選單鍵係**波浪符號鍵**（`Sources/Shared/KBEvent.swift:284` 之 `kSymbolMenuPhysicalKeyIntl = 50` ＝ `kVK_ANSI_Grave = 0x32`；JIS 側為同檔 `:305` 之 `kSymbolMenuPhysicalKeyJIS = 94` ＝ `kVK_JIS_Underscore = 0x5E`，該鍵在 JIS 鍵盤走羊字鍵 `kYen = 93` ＝ `kVK_JIS_Yen = 0x5D`）。初稿見常數名含 "SymbolMenu" 且值為 50，逕以之為「ANSI 分號」而致連鎖誤判（誤認微軟之 11 條 `ing` 系音節須於 triage 攔截）；實則 `;` 不在 `InputHandler_TriageInput.swift:95` 之 `triageByKeyCode()` 任何 case 內 ⇒ 必抵同檔 `:341` 之 `handleComposition` ⇒ 於打字機層即可直接消化，**triage 層零改動**。設計上仍保留 schema 欄位 `keyInterception`（`.none`／`.schemeAlphabet`／`.explicit`），惟動機改為**主機保留鍵**（波浪符號鍵、`¥`／`\`、`Option` 系組合）；內建 GB/T 34947-2017 與微軟皆 `.none`。**另**：`*.wikipedia.org` 於本機被 DNS 指向偽位址（`198.18.0.25`），`web_fetch` 一律以非公網位址拒收；改以 `curl --resolve zh.wikipedia.org:443:<真實 IP>` 取 `action=raw` 即可讀。
- **★ 雙拼零聲母之三族與碼長（2026-10-12，P301 研究實證）**：①固定一鍵作零聲母＋韻母鍵（GB/T 34947-2017 固定 `a`；微軟／智能ABC／紫光／搜狗固定 `o`）；②韻母首字母＋韻母鍵（拼音加加）；③同②但雙字母零聲母照全拼（自然碼、小鶴）。**四者實測皆為二鍵碼**（自然碼 426 條得 432 個相異 2 鍵碼、重碼 4 組；小鶴 433 個、重碼 3 組），單韻母零聲母一律作 `aa`／`oo`／`ee`；零聲母音節恰 12 條（`a an ai ao ang e en ei er eng o ou`）；自然碼＝周志農 1989（勿與 iQTech「自然輸入法」混淆）。Apple 之實作則容忍 `a` 單鍵成「阿」⇒ **零聲母處置必須由 schema 宣告、不得由方案名推斷**（碼長已於 P302 收尾定為常數、撤其欄位，見本節〈雙拼 schema 之三處精簡〉）；Apple 之雙拼表不在系統內（`SCIM.app` 僅見字串 `isPinyinOrShuangpinSimplified`）。微軟拼音（Win11）之方案編輯器**即以該三態為零聲母模式之枚舉**（標籤逐字：「固定式零子音」／「母音第一個字元的按鍵」／「母音第一個字元的按鍵（2 個字元的母音是完整拼音）」），並以「音節 → 按鍵」配對編輯（`範本` 三選：無／智慧型 ABC／自然代碼）；其**內建方案不 autochop**（`abababa` 逕留原文），而 Apple／微信／搜狗三者皆「不成碼即切」、殘段處置各異 ⇒ autochop 係實作之選配；微軟另把「自動展開至完整拼音」（殘段補全）與「超級縮寫拼音」（單鍵簡拼）皆作**預設關閉之開關**。
- **★ 雙拼之 autochop 係各家實作之選配、非雙拼之義務（2026-10-12，P301 事主實測；同日內建之再令）**：五牌實測——Apple（macOS 內建）／微信／搜狗皆「不成碼即切」，殘段處置分歧（Apple 回溯為較短之合法音節〔`aba`→`a`＋`ba`〕、微信於候選列前綴延伸、搜狗回退原文 ASCII〔`aba爸爸爸爸`〕）；**微軟拼音（Win11）與谷歌拼音（2007）皆不切**（微軟：`abababa` 逕留原文；谷歌：前編輯列 `ba ba ba ba ababababa`）。**內建之再令**：集成微軟雙拼為內建預設、**先不做 autochop 支持**——理由為中國內地之電腦化公共考試（法考等）只准微軟雙拼、禁止考生改動輸入法設置、考場預裝 2007 版谷歌拼音 ⇒ 唯音須求「碼表逐條等同＋行為等同（含同樣不打聲調、不 autochop）」。落點：schema 欄位 `public var autochopPolicy: AutochopPolicy = .disabled`（`.disabled`／`.backtrackToShorterReading`／`.prefixCandidates`／`.passThroughVerbatim`；本版只實作 `.disabled`，他形載入時發 W7、不靜默降級）。
- **★ 內建方案＝同一 JSON 格式之 decodable schema，其原文固化於原始碼檔尾（2026-10-12，P301 事主指示）**：內建之雙拼方案（微軟雙拼為預設，另有 GB/T 34947-2017，共兩案）不另立 per-scheme Swift 型別與檔案、不手寫表、亦不作 bundled `.json` 資源；方案之 JSON 原文以三引號字串塊置於 `DualpinParser.swift` **檔尾**，由**與使用者自備檔完全相同之 decoder** 載入 ⇒ 格式一改，內建即於載入與測試期失敗，「Swift 表」與「JSON 格式」不致成兩份真相，內建原文亦即使用者格式之範例。**另**（2026-10-12 覆核收斂）：`finals` 由 `[{suffix, key}]` 改為 `{尾綴: 鍵}` 辭典——查表係對餘部作**全等**匹配，次序本不參與運算；與 `initials`／`overrides`／`aliases` 同制，`FinalRule` 型別與其 `Codable` 已除（原文合省 3,100 bytes）。**2026-10-13 收官覆核**：內建縮為兩案（微軟、GB/T 34947-2017；值域 200…202 含自訂 200）；智能ABC／拼音加加／搜狗／紫光華宇／自然碼五案因授權界線（各有現存權利人或無從洽談）自二進位撤出，與四通雙拼一併以可匯入之 JSON 發表於官網倉 `vChewing.github.io` 之 `valueadd/dualpin-schema-files/`（提交 `350d293`，附 JSON Schema 與 `techdocs/Dualpin_Schema.md`；該格式標準已以正式條目定義 **DIPE**——`eh` 於取碼前即略過、不列 E3／W1，亦不得列入 `acknowledgedUnreachable`）。
- **★ 雙拼之架構、身分與碼長（2026-10-12，P301 事主指示）**：①**Arimitsu 與 Tekkon 拆 Target**——Arimitsu 自成 target、單元測試獨立、`DefaultIsolation` 暫定 `MainActor`；`Tekkon.mapHanyuPinyin` 等 internal 不可直讀，故 Tekkon 曝露**一枚純值公開 API**（首選 `public static var allHanyuPinyinStems: [String]`，426 條）供其取用、`MandarinParser.ofHanyuPinyin.mapZhuyinPinyin!.keys` 降為交叉核對；依賴單向（Arimitsu→Tekkon、LibVanguard→Arimitsu），目的係縮減 Tekkon 之改動量、便於 TekkonWorkspace 之跨語言遷移。②每份 schema 以 **DNS 名為唯一 ID `rawID`**（內建＝`dualPin.Microsoft`／`dualPin.GBT17`；空／非 DNS 形／相衝 ⇒ **E9**）。③persistence 採 `UserDefaults`、**僅承載一筆**：自備者存 JSON 原文、所選為原廠者僅存其 `rawID`（無多方案庫）。④**碼長一律 2**：單鍵碼之 schema 拒收（**E8**；原 `minCodeLength`／`codeLength` 二欄亦已撤、改常數 `DualpinParser.codeLength = 2`，見本節〈雙拼 schema 之三處精簡〉），原 W6 廢止；「以 `a` 代替 `aa`」屬通用邏輯方案、非雙拼之範疇。⑤`pending` 首鍵**一律顯示原始鍵**（雙拼用戶往往沒學過注音）。⑥`TypingMode` 增 **`.DualPin`**（於 `handleComposition` 之 `switch typingMode` 分派＋生效閘）。⑦雙拼下之「單鍵簡拼」**暫時擱置**（日後得於 Arimitsu 套件內補輔助工具）。
- **★ 雙拼之歸屬、無效序與施工序（2026-10-12，P301 事主指示）**：①**Arimitsu 係 `LibVanguard` 之直屬 SubTarget**（非頂層同儕）：原始碼住 `Sources/LibVanguard/Arimitsu/`、父 target 施 `exclude: ["Arimitsu"]`；測試目標 `ArimitsuTests` 住 `Tests/LibVanguardTests/Arimitsu/`（同法）。**實測**：SwiftPM 容許「子目錄作另一 target 之 `path`」——最小 manifest（tools 6.0）以 `Sources/A/B` 為 `B` 之 `path`、`A` 施 `exclude: ["B"]` ⇒ `swift package describe --disable-sandbox` 載入成功（`B` 之 `Path` 作 `Sources/A/B`）；本機 `swift package` 因 harness 擋 `sandbox-exec`，**一律須補 `--disable-sandbox`**。②**新增 target 須同時改兩份 manifest**：`Package.swift`（tools 6.4、`ArrayBuilder` DSL、`swiftSettings` 施 `.defaultIsolation(MainActor.self)`）與 `Package@swift-5.10.swift`（**真對位版**：`.target(` 陣列式、`platforms: nil`、產品一律 `.static`、無 `defaultIsolation`／`swiftLanguageModes`、不收 `vChewingSharedCLI` 與兩測試素材目標）；`Package@swift-6.0／6.1／6.2／6.3.swift` 係 `#error` 封堵檔（6.2／6.3 因 `#ConformanceIsolation` 不能編本閉包）。產品 `Vanguard` 之 target 清單本即明列整個閉包 ⇒ 新增 target 亦須列入。③**無效兩鍵序之處置＝直接 Beep ＋ Drop**：兩鍵皆丟（首鍵不 passthrough、次鍵不另作新碼之首鍵）、**不進組音區**（否則即複現 `q → ㄑ`）、**不落字面**；響鈴由**打字機側**呼叫 `SessionHost.shared.soundBuzz()`（`Sources/LibVanguard/Session/SessionHost.swift:94` 之 `public var soundBuzz: () -> () = {}`；macOS 側 `Packages/vChewing_MainAssembly4Darwin/Sources/MainAssembly4Darwin/SessionHostWiring.swift:59` 接 `NSSound.buzz()`；呼叫先例 `Sources/LibVanguard/Session/InputSession_Delegates.swift:175`）——Arimitsu 係 OS-neutral、**自身不發聲**。此與 `autochopPolicy`（管未滿碼之殘段）**分屬兩事**。④小鶴雙拼「先不討論」（作者迄未回信；**2026-10-12 補**：作者已覆示不予免費授權 ⇒ 永不內建，見本節末條）⇒ 不在未裁定之列；原「無效兩鍵序之提示形」一項亦收束 ⇒ 未裁定僅餘二項（`keyInterception` 之預設、macOS 側界面之歸屬）。⑤**P302 施工序**：手術範圍限 `vChewing-LibVanguard`；凡動 Tekkon 者**獨立一筆 commit 先行**（本倉標題 `Tekkon // <DirectConcernedNameSpace>: <WhatChangedInTheMember>.`），其後方為 LibVanguard 之餘；鏡照（`vChewing-macOS/Packages/vChewing_OSNeutral_LibVanguard`、`TekkonWorkspace` 三倉）**不由本倉手術 session 兼任**（P268），本 session 止於「交付報告指明待鏡照之 commit」。
- **★ 雙拼設定界面（macOS 側）之掛載點與三項硬事實（2026-10-12，P301 產出之 P303 規劃稿）**：①『拼音輸入種類』下拉之資料源為 `KeyboardParser.allCases`（`Packages/vChewing_OSNeutral_LibVanguard/Sources/Shared/Shared.swift:79-96`），SwiftUI 版住 `UserDefRenderableImpl.swift:311-330`、AppKit 版住 `UserDefRenderableCocoa.swift:220-273`（Int 身分走 `bind(.selectedTag,…)`，`nil` 選項 ⇒ `dropMenu.addItem(.separator())`）⇒ 欲於下拉**底部**另立段落，唯一手段是**擴張值域並令新案之首命中分隔線集合**（現值 `[7, 100]`，SwiftUI `:327`／Cocoa `:52`），而值域擴張與偏好鍵註冊皆屬 LibVanguard 側（P302，該目錄係鏡像、非本側工作面）。②**沙箱為實、惟由建置期注入**：`Sources/vChewingIME_macOS/Resources/vChewing.entitlements` 內並無 `app-sandbox` 鍵，然 `Plugins/BundleApps/plugin.swift:313-317` 與 `BuildPKG.sh:171-176` 於簽章時疊加 `app-sandbox`／`network.client`／`files.user-selected.read-write`（該註解明言不補即 strips the app sandbox）⇒ 讀取使用者所選檔案可行，惟 UI 端宜比照 `VwrSettingsPaneDevZone.swift:75-81` 做 `startAccessingSecurityScopedResource()` ＋ `defer`（Cassette／Cocoa 諸先例皆未做，兩派不一致）。③**外部寫入 `UserDefaults` 繞過 `@AppProperty`**（IME 為長駐行程、`didSet` 一概不觸發）⇒ 匯入偏好後必須 `PrefMgr.shared.reconcileAfterExternalPrefsImport()`（`PrefMgr_Utilities.swift:47-74`；既有呼叫者 `PrefsExchange.swift:114-117`；新鍵若帶 `didSet` 須同步其清單與 `PrefMgrReconciliationTests.swift:36` 之鍵數）。④**兩份導出物之硬鏈（不得手改）**：`ValueAdd/WebConfigAssistant/assets/userdef-metadata.json`（`make metadata` 逐位元組比對／`metadata-update` 入庫／`metadata-audit --strict`）與 `assets/settings-surface.json`（`tools/settings-surface.js` 讀 `UserDef.k*` 之引用、`Shared.swift` 之 parser 宣告序、**及 `UserDefRenderableImpl.swift` 內 `if [ … ].contains(item.rawValue)` 之分隔線字面**；改後跑 `make surface`、`make surface-check` 驗收）⇒ 新增 parser 案與改分隔線**皆**使之漂移。另：`UserDefaults.current` 即 `.standard`（`SwiftFoundationImpl.swift:207-228`），偏好之跨視圖同步靠共用 `UserDefaults`（cfprefsd）、**非** DistributedNotificationCenter 亦**非** KVO；以字串承載整包 JSON 於本倉**無先例**（`.arrayOfStrings`／`.dictionary` 之僅有二鍵皆在黑名單 `UserDef.swift:248-255`）。
- **★ 雙拼 schema 之三處精簡（2026-10-12，事主 m01201；P302 之 B 就地 amend）**：①`zeroInitial` 正名 **`nullOnset`**——零聲母即 null onset，型別作 `NullOnsetPolicy`，JSON 鍵與其錯誤字串同步（「無法辨識之 nullOnset。」）；②撤 **`codeLength`／`minCodeLength`** 二欄：全案皆二鍵，改 `public static let codeLength = 2`，E8 只餘 `overrides` 之碼非二鍵一途（他日真有三鍵方案再立欄）；③撤 **`alphabet`** 欄：`public let alphabet` 仍存，於 memberwise init 與 JSON decoding 時由 `public static func derivedAlphabet(initials:finals:nullOnset:)` 推算——兩表之值之聯集，再按政策併入固定鍵（`.fixedKey`）／尾綴鍵首字元（`.finalInitial`）／尾綴鍵首字元與雙字元尾綴之兩字元（`.finalInitialOrVerbatimDigraph`）。實測七案與原宣告值**全等**（微軟／搜狗／紫光 27 鍵含 `;`、餘四案 26 鍵）〔此係七案內建期之量測；2026-10-13 收官後內建只餘兩案，五案之表隨官網倉 JSON 供給〕⇒ 既不誤報 E1 亦不誤報 W5；JSON 因而不載 `alphabet`，使用者自備檔亦免宣告。
- **★ 雙拼首鍵之可行性與「死首鍵」之處置（2026-10-15，P310；`074df406`／`5fb1f5ac`）**：碼鍵空間（`alphabet`）內之鍵未必能居首鍵——微軟雙拼之零聲母前綴鍵為 `o`（啊＝`oa`），故 `a`／`e`／`;` 皆只能居次鍵之位。收之為 `pending` 者其後諸鍵必不成碼，且 copilot 候選窗無由成立（`dualpinPendingPrefixReadingKeys()` 空），中斷鍵遂落於「有素材待結算、實則無物可結算」之窘境：`solidifyFuriousFrontReading()` 因桶空而回 false，再由 `handlePunctuation` 之 `guard isComposerOrCalligrapherEmpty else { errorCallback?("A9B69908D"); return true }` 吞鍵＝noop＋蜂鳴。故可行性之判定須落於純邏輯層（`DualpinTranslator.firstKeys`，由併攏別名後之碼表反推；新 `Action.invalidFirstKey`），示警與丟棄歸打字機（`DualpinTypewriter`：`errorCallback` ＋ `i18n:ErrorMessage.InvalidDualpinFirstKey` 之 redAlert tooltip 1.2 秒、吞鍵、**不切態**）。**凡「待配素材」之判準皆須先問其有無可結算之物**——「有 pending 即必可結算」是 P309 之前提，P310 揭其例外。此判準落在碼鍵判定之初、先於一切狂打分流，故狂打與非狂打皆然（事主 2026-10-15 明示範圍）。
